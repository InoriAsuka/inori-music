# v5.34.1 — Meilisearch 起着但 API 从来不连它

v5.34.0 修了两个「配置写了、代码不读」的静默失败 bug，汇报里额外报告了第三个同类 bug，当时不在任务范围内没动。本 phase 核实属实并修掉，同时给这个方向补上守卫测试，把 v5.34.0 汇报里列出的全部 13 个 `INORI_*`/`MEILI_*` 变量认真扫了一遍。纯 Go 服务端改动，`services/api/` 之外只动了仓库根的 `docker-compose.prod.yml`。

---

## Bug 3 — `MEILI_HOST`/`MEILI_SEARCH_KEY` 从未接入 `api` 服务

### 根因

`docker-compose.prod.yml` 定义了 `meilisearch` 服务并让它无条件启动，但 `api` 服务的 `environment` 段里没有 `MEILI_HOST`/`MEILI_SEARCH_KEY`（v5.34.0 修完之后这段依然没有——核对过）。

`services/api/cmd/server/main.go:114`：

```go
if meiliHost := os.Getenv("MEILI_HOST"); meiliHost != "" {
    ms, err := search.NewMeilisearch(meiliHost, os.Getenv("MEILI_SEARCH_KEY"))
    if err != nil {
        log.Printf("meilisearch init: %v", err)
    }
    if ms != nil {
        searchSvc = ms
        catalogService.WithSearchService(searchSvc)
        log.Printf("meilisearch enabled at %s", meiliHost)
    }
}
```

变量为空就整段跳过，且跳过分支里**没有任何日志**——只有启用成功才会打印 `meilisearch enabled at %s`。这比 v5.34.0 的 Bug 1（迁移未接线，至少建表失败时日志能看到端倪）和 Bug 2（`INORI_DATABASE_URL` 未设时至少有明确的 in-memory fallback 日志）都更隐蔽：容器正常运行，搜索功能表面正常（静默退回 PostgreSQL 全文检索，响应 schema 不变），没有任何错误、没有任何提示指向「Meilisearch 其实完全没被用上」。结果是一个跑着但完全没被使用的 meilisearch 容器。

**参考事实**：同一台 Unraid 主机上跑着的 v5.4.0 部署确认设了 `MEILI_HOST`/`MEILI_SEARCH_KEY`。三个 bug 里已经有两个（Bug 2 的 `INORI_DATABASE_URL` 改名、这次的 Bug 3）指向「实际部署比仓库的 `docker-compose.prod.yml` 正确」——这份 compose 文件大概率从未被真正跑通过一次完整部署。

### 修复

```yaml
      MEILI_HOST: "http://meilisearch:7700"
      MEILI_SEARCH_KEY: "${MEILI_SEARCH_KEY:?MEILI_SEARCH_KEY required}"
```

- `MEILI_HOST` 写成 compose 内部固定地址（服务名 + 端口），照抄 `INORI_DATABASE_URL` 用 `postgres` 服务名、`NEXT_PUBLIC_API_BASE_URL` 用 `http://api:8080` 的既有写法——不做成可留空的 `${VAR:-}`，因为这份 compose 里 `meilisearch` 服务本来就无条件启动，没有理由允许 `api` 不接它。
- `MEILI_SEARCH_KEY` 用跟 `meilisearch` 服务**完全相同**的插值表达式 `${MEILI_SEARCH_KEY:?MEILI_SEARCH_KEY required}`，两处永远从同一个 `.env` 变量取值，不会出现两边配置漂移导致鉴权失败。
- 顺带补上 compose 头部 `# Environment variables (set in .env)` 注释块里漏掉的两个 `:?required` 变量：`INORI_STREAM_SIGNING_KEY`（v5.34.0 就已经是必填，头部注释一直没提，部署的人照注释准备 `.env` 会漏）和 `MEILI_SEARCH_KEY`（现在被 `meilisearch`、`api` 两个服务同时依赖，更需要在头部说明）。

### Meilisearch master key 与 search key 语义核实（任务明确要求查证、不能凑合）

查了 Meilisearch 官方文档（`meilisearch.com/docs/resources/self_hosting/security/master_api_keys`）确认：

- **Master key**：拥有实例的全部权限，是唯一能创建/删除 API key 的凭据；同时是所有其他 key 权限的超集（能做任何 key 能做的事，反过来不成立）。
- **Default Search API Key**（Meilisearch 自动生成的默认「search key」）：仅有 `search` 这一个 action，只能查询，**不能**创建/删除索引、不能更新可搜索属性或其他 index settings、不能增删文档、不能管理 key。
- **Default Admin API Key**：除 key 管理外的全部权限——但这是一个独立生成的值，既不是 master key 也不是 search key，要拿到它需要在 Meilisearch 启动之后额外调用一次 `GET /keys`（用 master key 认证）来读取，docker-compose 的静态环境变量插值语法做不到这一步。

而本仓库 `internal/search/meilisearch.go` 的 `NewMeilisearch` 在**启动时**就会调用 `CreateIndex`/`UpdateSearchableAttributes`（`ensureIndexes()`），运行中还会经 `IndexTrack`/`IndexAlbum`/`IndexArtist`/`ClearIndexes` 调用 `AddDocuments`/`DeleteAllDocumentsWithContext`——这些全部是管理级操作，一个真正意义上的「search key」权限完全不够用。如果真的接一个范围仅限 `search` 的 key：`UpdateSearchableAttributes` 会失败并打印 `search: update searchable attributes for %s: %v`；`CreateIndex` 的错误则会被当前代码整体吞掉（`// Index may already exist — ignore` 那段注释掩盖了这是「所有错误」，不只是「已存在」错误）——首次部署在全新 Meilisearch 实例上会导致索引从未真正创建成功,只是不容易第一时间看出来是权限问题。

**结论**：`api` 服务的 `MEILI_SEARCH_KEY` 必须与 `meilisearch` 服务的 `MEILI_MASTER_KEY` 是完全相同的值——这不是偷懒或权宜之计，而是当前 `ensureIndexes()` 实现方式下的硬性要求。代价：Go 后端持有的是 master key 而非最小权限凭据，不符合 Meilisearch 自己文档里「master key 不该用于日常操作」的建议。但这个 key 全程只存在于 compose 内部服务间通信（Go 进程环境变量 → meilisearch-go 客户端 → meilisearch 容器），从未流向任何浏览器或客户端，不是「把 master key 发给前端」那种量级的安全问题。给它置备一个范围恰好覆盖「索引管理 + 文档增删 + 搜索」但又不含 key 管理的自定义 key 技术上可行，但需要一次额外的运行时置备步骤（用 master key 调 `POST /keys`），超出本 phase 范围，如实记录、不强做。

仓库对 `MEILI_SEARCH_KEY` 这个名字的用法本身也值得注意：在 Meilisearch 自己的术语体系里「search key」特指仅有搜索权限的受限 key，而本仓库这个 `.env` 变量名从 v4.3.0 起就一直是「部署者要提供的唯一 Meilisearch 密钥」的代称，实际功能等价于 master key。这个命名沿用自更早的版本，不是本次引入的新歧义，本 phase 未重命名（重命名是更大范围的清理，且会让已有部署的 `.env` 失效，超出范围）。

### 守卫：`compose_env_test.go` 新增反方向检查

v5.34.0 的 `TestComposeAPIEnvVarsMatchSource` 只做单向检查（compose 写了、源码不读的名字），刻意如此避免对 `INORI_CORS_ORIGINS`、`INORI_SESSION_TTL` 这类留空也能正常工作的可选变量产生误报。本次新增反方向的 `TestComposeAPIEnvVarsIncludeSilentlyDegradingVars`：

1. 在测试文件里维护一份手工登记的 `silentlyDegradingEnvVars map[string]string`（变量名 → 不设时会静默发生什么），而不是自动扫描 `main.go` 里的全部 `os.Getenv` 调用——因为「不设会不会造成实质性功能损失」是语义判断，静态分析做不出来,自动化会重新掉进对 `CORS_ORIGINS`/`SESSION_TTL` 之类合法可选项的误报陷阱。
2. 断言清单里每一项都出现在 `docker-compose.prod.yml` 的 `services.api.environment` 里，否则精确报出变量名 + 登记的「不设会怎样」说明。
3. 额外做了自校验：清单里的名字如果在 `main.go` 里已经找不到对应的 `os.Getenv(...)` 调用（例如未来改名或删除了这个读取点却忘了同步清单），测试同样失败，防止清单自身腐化成检查一个不存在的东西。

两条测试（`TestComposeAPIEnvVarsMatchSource` 与新的 `TestComposeAPIEnvVarsIncludeSilentlyDegradingVars`）共享同一套 Go AST 解析（`sourceEnvVars`）与 YAML 解析（`composeAPIEnvVarNames`）逻辑。唯一改动是把原先写死在两处的 `strings.HasPrefix(name, "INORI_")` 抽成一个共享的 `hasTrackedPrefix`（`trackedEnvPrefixes = []string{"INORI_", "MEILI_"}`），因为 `MEILI_HOST`/`MEILI_SEARCH_KEY` 现在也合法地出现在 compose 里，原来只认 `INORI_` 前缀的过滤会把它们完全过滤掉，导致新测试拿到空集合。这个改动不影响 `TestComposeAPIEnvVarsMatchSource` 的既有行为——它比较的两个集合（source 里的 `INORI_`/`MEILI_` 名字、compose 里的 `INORI_`/`MEILI_` 名字）现在完全对称扩展了前缀范围，不会把「compose 有一个 source 不认识的 MEILI_ 名字」误判成 bug（因为 source 现在确实读取 `MEILI_HOST`/`MEILI_SEARCH_KEY`）。

### 认真扫过 v5.34.0 汇报列出的全部 13 个 `INORI_*`/`MEILI_*` 变量

判断标准：变量不设时，是否存在「compose 已经为它配了专属基础设施（跑着一个容器）、源码却完全没打日志就悄悄绕过」这种「意图与现实脱节」的强信号——这正是 Meilisearch 这个 bug 的形状，也是区分「真 bug」与「设计上就是可选项」的分界线。逐项过了一遍：

| 变量 | 不设时的行为 | 是否登记进清单 |
| --- | --- | --- |
| `MEILI_HOST` | 整段跳过，零日志；meilisearch 容器跑着但从未被查询 | **登记**（本次修复的 bug） |
| `MEILI_SEARCH_KEY` | `MEILI_HOST` 设了但这个没设 → 鉴权失败 → 健康检查判定不可达 → 同样退回 PG（有一条「not reachable」日志，但实际原因是未授权，日志描述具有误导性） | **登记**（与 `MEILI_HOST` 成对，二者缺一都无法真正启用） |
| `INORI_ADMIN_TOKEN` | compose 里已是 `:?required`，未设置时 `docker compose up` 直接拒绝启动；源码侧也有明确日志（`/api/v1/admin routes will return 503`） | 不登记（已有更强的 compose 硬约束，清单机制是为了补「compose 没管」的空子，这里没有空子） |
| `INORI_STREAM_SIGNING_KEY` | 同上，compose 里已是 `:?required` | 不登记 |
| `INORI_DATABASE_URL` | 不设时 4 个服务构造点（auth/playerstate/searchhistory 等）各打一条明确日志说明走内存态，不是「零日志」 | 不登记（Bug 2 已经修过命名问题，且不满足「静默」这一条） |
| `INORI_INITIAL_ADMIN_USER`/`INORI_INITIAL_ADMIN_PASSWORD` | compose 注释里已写明留空即跳过、不是错误，是刻意设计的可选项，且有另一条路径（直接在 Postgres 建管理员）兜底 | 不登记 |
| `INORI_CORS_ORIGINS` | 有日志（`CORS middleware running in permissive mode`），且是文档化的合法宽松模式；任务原文明确点名不该误纳入 | 不登记 |
| `INORI_SESSION_TTL` | 兜底为源码硬编码默认值 `24h`，功能完全不受影响，只是一个配置旋钮；任务原文明确点名不该误纳入 | 不登记 |
| `INORI_STORAGE_REFRESH_INTERVAL` | 不设时零日志，关闭周期刷新调度器——本次判断上最接近边界的一项 | **不登记**，理由见下 |
| `INORI_STORAGE_REPOSITORY_FILE`/`INORI_MEDIA_OBJECT_REPOSITORY_FILE` | 只在 `pool == nil` 分支才会被读取；本 compose 里 `INORI_DATABASE_URL` 恒非空，`pool` 永远非 nil，这两个变量在当前拓扑下其实**永远读不到** | 不登记（性质不同：不是「未设置会静默降级」，而是「设置了也用不上」的死配置，见下） |
| `INORI_HTTP_ADDR` | compose 里已显式设为 `0.0.0.0:8080`；若真的缺失，默认回落 `127.0.0.1:8080` 会让容器网络内的其他服务连接被拒绝——是响亮失败（健康检查/依赖服务立刻报错），不是静默失败 | 不登记 |

`INORI_STORAGE_REFRESH_INTERVAL` 判断说明：它和 `MEILI_HOST` 一样「不设时零日志」，但缺少 Meilisearch 那个决定性信号——compose 里没有为它单独跑一个会被浪费的容器/基础设施，只是关掉一个进程内的 `time.Ticker`；compose 注释也早已把它写成刻意的可选项并说明默认行为，不存在「意图与现实脱节」。判定它更接近 `INORI_CORS_ORIGINS`/`INORI_SESSION_TTL` 那一类，不登记。

`INORI_STORAGE_REPOSITORY_FILE`/`INORI_MEDIA_OBJECT_REPOSITORY_FILE` 是扫描过程中顺带发现的另一个、性质不同的小问题：不是「不设会静默降级」，而是「即使设置了，在当前 compose 拓扑下也从不会被读取」（死配置，因为 `pool` 分支恒真）。这不属于本 phase 要修的「反方向」bug 形状，如实记录，未处理。

另外发现仓库根目录下还有一个 `docker-compose.v484-test.yml`（v4.8.4 时为了在 `root@192.168.58.34` 上做临时验证而加入版本库的一次性测试 overlay，见 `git log -- docker-compose.v484-test.yml` 的提交信息）。它的 `api` 服务环境段仍是修复前的 `INORI_DB_DSN`/`INORI_AUTH_SECRET`（v5.34.0 修的 Bug 2 那两个死名字），也同样没有接 `MEILI_HOST`/`MEILI_SEARCH_KEY`。任务范围明确限定在 `docker-compose.prod.yml`，且这份文件本身描述为「temp testing」、状态明显早于 v5.34.0 的修复，不在本次修改范围内——如实记录，避免被误认为遗漏未修。
