# v5.37.2 — macOS 登录后钥匙串授权弹窗反复出现：拦截器每个请求读两次钥匙串

macOS 用户反馈：登录成功之后，系统钥匙串授权弹窗接连不断——输入密码点「允许」，弹窗马上又跳出来，如此循环，观感上像是卡进了死循环。

## 根因：请求数 × 每请求两次钥匙串读取

定位到 `lib/src/api/api_client.dart` 的 dio 拦截器 `onRequest`：

```dart
onRequest: (options, handler) async {
  final storage = ref.read(secureStorageProvider);
  final token = await storage.read(key: _kTokenKey);        // 钥匙串读取
  final baseUrl = await storage.read(key: _kBaseUrlKey) ?? _kDefaultBaseUrl;  // 钥匙串读取
  ...
}
```

**每一次 HTTP 请求**都会执行两次钥匙串读取。v5.37.1 已经把 macOS 切到旧版文件式钥匙串（`mOptions: MacOsOptions(useDataProtectionKeyChain: false)`），而旧版钥匙串的行为是「调用方不在条目的 ACL 里就弹窗要求授权」。本应用是 ad-hoc 签名（`CODE_SIGN_IDENTITY = "-"`，无 `DEVELOPMENT_TEAM`），身份不稳定，读取可能被反复判定为「未受信任的调用方」而弹窗。

打开一个艺术家详情页会并发发出艺术家 + 专辑 + 三十多首曲目 + 逐专辑封面查询等几十个请求，弹窗数量因此直接与请求数成正比——这就是「反复弹出、看起来像死循环」的真实成因，而不是某处逻辑真的在无限循环。

## 顺带发现：三个非密钥值也被塞进了钥匙串

`base_url`、`user_id`、`username` 都不是凭证，却和 `auth_token` 一起存在 `FlutterSecureStorage` 里，每一个都是多一次 ACL 检查的代价。`auth_notifier.dart` 里 `_kLastModeGuestKey` 常量上原本就写着约定：

> non-secret UI preference, deliberately kept out of FlutterSecureStorage (that's reserved for real credentials)

这三个键正是这条约定想要防住的反例，却一直没人对照检查过。

## 修复一：`AuthCache` 进程内读穿透缓存

`api_client.dart` 新增 `authCacheProvider` 持有的 `AuthCache`：

```dart
class AuthCache {
  Future<String?>? _tokenFuture;
  Future<String>? _baseUrlFuture;

  Future<String?> token(FlutterSecureStorage storage) {
    return _tokenFuture ??= storage.read(key: _kTokenKey);
  }

  Future<String> baseUrl(SharedPreferences prefs, FlutterSecureStorage storage) {
    return _baseUrlFuture ??= _loadBaseUrl(prefs, storage);
  }
  ...
}
```

`token`/`baseUrl` 各自缓存成一个 `Future` 而不是缓存已解析的值：首次调用真正触发读取，之后所有调用——包括与首次读取赛跑的并发调用——都复用同一个 `Future`。`??=` 赋值在函数体内同步执行，早于它存下的那次读取的第一个 `await`，因此天然合并同一时刻并发发出的首访请求（例如艺术家页不等待地并发拉取艺术家/专辑/曲目，都会共享同一次读取而不是各自发起）。

`login()`、`logout()`、401 强制登出三条路径都调用 `cache.setToken(...)`/`cache.setBaseUrl(...)` 立即覆盖缓存：

- 登出后不能仍拿着旧 token 发请求。
- 登录时切换服务器地址后，紧接着的请求不能仍悄悄连着旧地址。

dio 拦截器与 `AuthNotifier` 读的是同一个 provider 实例的 `AuthCache`（`ref.read(authCacheProvider)` 在同一个 `ProviderContainer` 下永远拿到同一个对象），口径统一，不会出现两边各自维护一份缓存、互相不知道对方已经失效的问题。

## 修复二：非密钥值迁移到 SharedPreferences

`base_url`/`user_id`/`username` 迁到 `SharedPreferences`，钥匙串只留 `auth_token`。

**迁移是硬要求，不能跳过**：v5.37.0/v5.37.1 装机的用户，这三个值已经写在钥匙串里。如果直接把读取位置改成 `SharedPreferences` 而不做迁移，`SharedPreferences` 里什么都没有，用户升级后会发现已配置的服务器地址「凭空消失」、看起来像被登出——这比弹窗问题本身更糟。

做法（`AuthCache._loadBaseUrl` 和 `AuthNotifier._migrateToPrefs`，两处逻辑一致）：

1. 先查 `SharedPreferences`，有值直接用，不碰钥匙串。
2. 没有值，读一次钥匙串。
3. 读到了：写回 `SharedPreferences`，删除钥匙串副本，返回该值——此后这个值再也不会触碰钥匙串。
4. 没读到：返回默认值/`null`（`base_url` 落到 `http://localhost:8080`，`user_id`/`username` 为 `null`）。

这次一次性读取允许弹一次授权窗，属于自限成本：只会发生一次，此后永久消失。三个键各自独立按需迁移，没有额外引入一个全局「是否已完成迁移」的标记位——考虑过要不要加，但一个从未在钥匙串写过这三个键的全新安装（或已经迁移完成、钥匙串副本已删除的设备），`SecItemCopyMatching` 对不存在的条目直接返回 `errSecItemNotFound`，不需要评估 ACL、不会触发授权 UI，因此没有必要为这种情况额外记账。

`AuthNotifier._clearStorage()`（登出/401 强制登出/token 校验失败三处共用）现在只清 `auth_token` 与 `user_id`/`username`，**不清 `base_url`**——退出一个账号不应该忘记这台设备原本连的是哪台服务器。

## 测试适配：`login_failure_visibility_test.dart`

非本次目标，但改了 `base_url` 的存储位置就绕不开。

该文件里三条「钥匙串写入失败要正确冒泡到界面」的用例（v5.37.0/v5.37.1 留下的守卫），原本的触发机制是：`login()` 先把 `base_url` 写进钥匙串，测试用的 `_KeychainRejectingStorage` 拒绝一切写入，于是 `login()` 在发出任何网络请求之前就已经抛出——测试因此不需要处理网络。

`base_url` 改存 `SharedPreferences` 之后，这条写入不再经过钥匙串、不再抛错，`login()` 会继续往下走到真正的登录 POST。测试补了一个 `_FakeLoginAdapter`（`HttpClientAdapter` 的桩实现，直接返回固定的登录成功 JSON，不触碰网络），让流程能够走到现在**唯一还会失败**的钥匙串写入——`auth_token`。三条用例改为在这一步验证同样的错误文案（`-34018`、授权类 OSStatus 提示语）是否正确冒泡，覆盖的行为没有变化，只是触发失败的写入从 `base_url` 换成了 `auth_token`。

## 守卫测试

新增 `services/mobile/test/keychain_read_scaling_test.dart`（2 条）：

- `_ReadCountingStorage`：继承 `FlutterSecureStorage` 的计数桩，覆写签名照抄 `login_failure_visibility_test.dart` 里的 `_KeychainRejectingStorage`，每次 `read` 调用计数 +1。
- `_StubAdapter`：`HttpClientAdapter` 桩实现，任何请求都立即返回 `200 {}`，不联网。
- 用计数桩覆盖 `secureStorageProvider`，但不覆盖 `authCacheProvider`——要测的正是真实的 `AuthCache` + 真实的 `dioProvider` 拦截器。
- 第一条：顺序发出 12 个请求，断言 `read` 调用次数 `<= 1`。
- 第二条：用 `Future.wait` 并发发出 8 个请求（不等待前一个完成），同样断言 `<= 1`——单独验证并发首访的合并逻辑，不只是"缓存已预热后"的情形。
- `setUp` 里给 `SharedPreferences` 预置 `base_url`，模拟「已完成迁移」的稳态设备：这样两条用例测的是普通用户日常使用时的常态，而不是升级后第一次启动那种允许有一次性钥匙串读取的迁移路径。

### 非空洞证明（证伪）

把拦截器临时改回修复前的写法（逐请求直接调用 `storage.read`，不经过 `AuthCache`），重跑 `keychain_read_scaling_test.dart`：

```
issuing many sequential requests reads the keychain at most once, not once per request [E]
  Expected: a value less than or equal to <1>
    Actual: <24>

a burst of concurrent requests also coalesces onto a single keychain read [E]
  Expected: a value less than or equal to <1>
    Actual: <16>
```

12 个顺序请求 × 2 次读取/请求 = 24，8 个并发请求 × 2 次读取/请求 = 16——两个数字都与请求数精确成比例，证明修复前确实是「钥匙串读取数 = 请求数 × 2」的线性放大，而不是巧合。验证完毕后已恢复修复代码并重新跑绿（见下方验证）。
