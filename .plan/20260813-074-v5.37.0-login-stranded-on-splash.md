# v5.37.0 — 登录点下去就永远停在 logo 页：三个缺陷叠出来的死局

用户实机反馈（v5.36.0 构建）：

> 表单的三个元素填好后，点击登录，然后跳转到 logo 页面就没有动静了，完全不知道是什么情况，也不像游戏登录的时候有 1/16 5/16 等进度显示，也没动态加载效果，同样没有任何内容输出，给人的感觉就是卡死了。

v5.36.0 补上的平台联网能力是必要的，但**不充分**——登录路径在发出任何网络请求之前就已经死了，所以那批修复根本没被走到。

## 完整因果链

1. `AuthNotifier.login` 第一句 `state = const AsyncLoading()`。
2. `router.dart` 的 redirect：`if (authState is AsyncLoading) return AppRoutes.splash;`——**无条件**。用户被立刻从 `/login` 拽到 `/splash`，这就是「跳转到 logo 页」。
3. `login()` 里第一个真正的操作是 `_storage.write(key: _kBaseUrlKey, ...)`，而它写在 **`try` 块外面**。
4. macOS 上这次写入必然失败（见根因一），抛 `PlatformException`。
5. `login()` 只有 `on DioException`，接不住；`_submit()` 直接 `await login()` 也没有 try/catch，于是成为**未捕获异步错误**——界面上没有任何痕迹。
6. `state` 永远停在 `AsyncLoading`，redirect 每次求值都返回 `/splash`。
7. `SplashScreen` 是按「绝不可能卡住」设计的（源码注释原话：*"a transient gate, not a screen a user should ever need to act on"*），260ms 淡入动画跑完就是一张**完全静止的图**：没有 spinner、没有状态文字、没有超时、没有出口。

第 3–5 步决定了它会卡住，第 2 步和第 7 步决定了卡住之后**用户和开发者都拿不到任何信息**。

## 根因一：macOS keychain 写入从来没成功过

`flutter_secure_storage` 9.2.4 在 macOS 上联邦到 `flutter_secure_storage_macos` 3.1.3，其 `MacOsOptions` 默认 `useDataProtectionKeyChain = true`（`lib/options/macos_options.dart`），而 `api_client.dart` 的 `secureStorageProvider` 只传了 `aOptions` / `iOptions`，**`mOptions` 从未传过**，吃的就是这个默认值。

macOS 上启用 data protection keychain 要求应用属于某个 keychain access group，而这需要 entitlement 里有带 Team ID 前缀的 `keychain-access-groups`。本工程 `macos/Runner.xcodeproj/project.pbxproj` 是 `CODE_SIGN_IDENTITY = "-"`（ad-hoc 签名）且**没有 `DEVELOPMENT_TEAM`**，全仓库 `macos/`、`ios/` 目录里 `keychain` 零命中。于是每次 `SecItemAdd` 返回 `errSecMissingEntitlement (-34018)`。

**为什么潜伏这么久——读写不对称**（读 `macos/Classes/FlutterSecureStorage.swift`）：

- `read()`：`errSecItemNotFound` → 显式改写成 `FlutterSecureStorageResponse(status: errSecSuccess, value: nil)`。全新安装 keychain 是空的，查不到 → **返回 null，不是错误**。所以 App 冷启动一切正常，登录表单照常显示。
- `write()`：`SecItemAdd` 必须选一个 access group 写进去，没有 entitlement 就是硬失败。`FlutterSecureStoragePlugin.swift` 的 `handleResponse` 把任何非 `noErr` 的 status 原样包成 `FlutterError` → Dart 侧 `PlatformException`。

**只有写会炸，而唯一触发写的动作就是登录本身。**

### 修法选择：不是补 entitlement

第一直觉是照搬 v5.36.0——往两份 entitlements 里补 `keychain-access-groups`。**这个修法在本工程是错的**：该 entitlement 的值形如 `$(AppIdentifierPrefix)com.inori.music`，而 ad-hoc 签名根本没有 `AppIdentifierPrefix` 可解析，加了也不会生效。

改为 `mOptions: MacOsOptions(useDataProtectionKeyChain: false)`，走旧版文件式 keychain——App Sandbox 下应用访问自己的 keychain 条目**不需要任何 entitlement**。没有迁移问题：macOS 构建从来没写成功过哪怕一条记录。iOS 不受影响（该选项只作用于 macOS，且 iOS 应用总是从 provisioning 拿到合法的 application-identifier）。

## 根因二：`login()` 不是全函数

它要做三次 keychain 写入、一次 SharedPreferences 操作、两次类型转换（`data['token'] as String` / `data['userId'] as String`），**没有一个会抛 `DioException`**，而它只 catch 这一种。任何一个逃逸，`state` 就永久钉在 `AsyncLoading`。

顺带排除的一个嫌疑：服务端实际响应是 `{token, expiresAt, userId}`（对生产实例 `http://10.100.121.134` 实测），与客户端的 cast 完全对得上，**类型转换这条不是本次成因**——但它和 keychain 写入共用同一条逃逸路径，所以一并纳入 catch-all。

另一条决定性排除：dio 配了 `connectTimeout: 15s` / `receiveTimeout: 30s`，**纯网络问题最多卡 30 秒就会抛 `DioException` 并被正确显示**。用户描述的「完全没动静」本身就证明了故障点在网络请求之前。

修复：把 `_kBaseUrlKey` 的写入移进 `try`；补 `catch (e)` 兜底；新增 `_describeUnexpected` 把 `PlatformException` 的平台码原样带到界面上——`-34018` 是打包缺陷，不是密码打错了，**折叠成笼统的 "Login failed" 几乎和冻结的 splash 一样没用**。

同一形状的另一处：`continueAsGuest()` 直接绑在按钮的 `onPressed` 上，SharedPreferences 抛异常就是「按钮点了没反应，永远」。游客模式纯本地、根本不需要存储，因此改成存储失败也照样进入游客模式（只是下次冷启动不记得）。

## 根因三：路由把用户从登录页抢走

`login_screen.dart` 里 `isLoading` 时按钮上有 `CircularProgressIndicator`（170–188 行），失败时字段下方有内联错误文案（151–167 行）——**代码一直都在，但从来不可达**，因为 redirect 在 `AsyncLoading` 的第一时间就把用户送去 `/splash` 了。登录页本来就是照「自己显示加载与错误」设计的。

修复：`if (authState is AsyncLoading && !isLoginRoute)`。交互式登录本来就是**从 `/login` 出发**的，不该被自己触发的加载态赶走。冷启动时的初始鉴权仍然正常走 splash。

顺带把整段 gate 规则从 GoRouter 闭包里抽成顶层纯函数 `resolveAuthRedirect({authState, location})`。这些规则决定用户看到哪一屏，其中一条错了足够久、久到把人困在静止的 splash 上，**而它此前只存在于闭包里，想测就得起整个 shell（含 AudioService）**。实践上不可测，正是这么关键的规则一直没人校验的原因。

## 根因四：splash 没有"我还活着"的信号

即便前三条都修好，一个没有出口的 gate 本身就是错的形状。改造：

- **常驻**进度指示（不是一次性淡入动画）——它唯一的职责就是区分「在干活」和「已经死了」，而这恰恰是此前用户无从判断的事。
- 状态文字，新增三条 l10n（`splashConnecting` / `splashTakingLonger` / `splashBackToSignIn`，en/ja/zh 三语齐全）。
- 超过 8 秒（够跑完 dio 的 15s connect 里的常见慢路径，又不至于让人干等）改文案并给出「返回登录」出口，调用新增的 `AuthNotifier.abandonPendingAuth(reason)` 把状态拉回 unauthenticated，让路由的常规规则重新接管。

## 守卫测试：`test/login_failure_visibility_test.dart`

10 条，三组：`login()` 的全函数性（含 `-34018` 必须出现在用户可见文案里）、`secureStorageProvider` 的 macOS 选项、`resolveAuthRedirect` 的全部分支。

### 非空洞证明（逐项退回修复前，实测确认失败）

| 退回的改动 | 实测失败的守卫 | 观察到的失败 |
|---|---|---|
| 删掉 `mOptions` | macOS 选项守卫 | `Expected: 'false' / Actual: 'true'` |
| redirect 恢复无条件 `AsyncLoading → splash` | 登录中不离开表单 | `Expected: null / Actual: '/splash'` |
| 删掉 `catch (e)` 兜底 | login 全函数性 ×2 | `PlatformException(-34018)` 从 `auth_notifier.dart:178` 的 `login()` 逃逸 |
| 写入移回 `try` 外（保留 catch-all） | login 全函数性 ×2 | 同上——**证明两处改动各自独立必要** |

最后一行是有意单独验的：只补 catch-all 而不搬动写入位置，仍然会漏。
