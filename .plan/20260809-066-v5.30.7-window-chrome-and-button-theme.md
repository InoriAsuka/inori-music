# v5.30.7 — FilledButton 主题真 bug + macOS 窗口装饰 + 播放条交互精修

用户实机验证 v5.30.6 后给了六条反馈，按优先级排列：F（已定位的真 bug）优先，其余按 A-E 顺序处理。

## F. 全局 `FilledButtonTheme` 无限宽（真 bug）

### 根因

`skin_definition.dart` 的 `filledButtonTheme` 里 `minimumSize: Size(double.infinity, 48)`
让每个 `FilledButton` 都要求"最小宽度无限"。Flutter 的 `ConstrainedBox.enforce()` 会把这个无限
minWidth 钳制到父级实际提供的约束区间——落在什么位置取决于父级是谁：

- **`ListTile.trailing`**：父级给出的是一个**有限但较窄**的宽度上限，无限 minWidth 被钳到"消耗
  trailing 分区的全部宽度"，`title`/`subtitle` 分区被挤到只剩几像素——这正是用户截图里"文字被挤成
  竖排"的样子。用 `flutter_test` 复现，Flutter 甚至有专门针对这个形状的断言："Trailing widget
  consumes the entire tile width"。
- **纯 `Row` 的非 `Expanded` 子节点**（如 `play_actions_row.dart` 的"Play"按钮、
  `local_library_screen.dart` 的"播放全部"按钮、`user_playlist_detail_screen.dart` 的"Play All"
  按钮）：Flutter 给 `Row` 里没被 `Expanded`/`Flexible` 包裹的子节点的主轴约束**本身就是无限**
  （`BoxConstraints(maxWidth: infinity)`），无限 minWidth 在这里不是被钳制，而是**直接触发**
  `BoxConstraints.debugAssertIsValid()` 的硬断言："BoxConstraints forces an infinite width"——
  这是在排查过程中额外发现并确认的**三处真实存在的潜在崩溃点**，此前没人报告是因为：(1) debug 断言
  在 release 构建里被 strip 掉，不会崩到用户看得见；(2) 这三个测试文件（`play_actions_row_test.dart`
  / `local_library_screen_test.dart`）此前的 `_buildApp` 用的是裸 `MaterialApp`（Flutter 默认主题），
  从未真正套用过本 app 的 `FilledButtonTheme`，测试因此从未跑到这条崩溃路径上。
- **`AlertDialog.actions`**（`OverflowBar`）：经验证会把无限 minWidth 钳制回按钮内容的自然宽度，
  不会撑满、也不会崩，全仓库约 16 处对话框按钮实际上**从未受这个 bug 影响**。
- **`Column` 的非 `stretch` 子节点**（各屏幕的错误重试按钮、空态 CTA）：会被钳制成"占满 Column
  可用宽度"——视觉上恰好像是"有意为之的整宽按钮"，这正是这些位置从未被当作 bug 报告的原因。
- **`CrossAxisAlignment.stretch` 的 `Column`**（`login_screen.dart` 提交按钮、
  `settings_screen.dart` 背景图选择器的按钮组）：整宽完全来自 `stretch` 本身给出的 tight
  约束，跟按钮自己的 `minimumSize` 无关，主题改动对这些位置零影响。

### 修复

1. `skin_definition.dart`：`minimumSize` 改成 `Size(0, 48)`——只保留高度约束（48 是有意的，未改动），
   宽度交回调用点自行决定。
2. **逐个核对全仓库 32 处 `FilledButton`**（含 `.icon`/`.styleFrom` 引用行；去重后共 29 个真实按钮
   实例）后的结论：**没有一处需要在调用点补显式整宽包装**。原因见上面五类归属——真正"应该整宽"的
   两处（登录页提交按钮、设置页背景图选择器按钮组）已经通过祖先 `CrossAxisAlignment.stretch` 拿到整
   宽，不依赖按钮自身的 `minimumSize`；其余全部要么本来就不该整宽（对话框按钮、Row 内联按钮），要么
   整宽是钳制的副作用、变成自然宽度反而是更正确的观感（重试按钮、空态 CTA）。这一条逐文件核对清单
   写在"测试"一节。
3. **删除设置页游客态整个 Account 登录区块**：用户明确说"设置里面也不需要登录了"。
   `settings_screen.dart` 的 `if (isGuest) ListTile(...)` 分支整段删除；连同
   `const _SectionHeader(title: 'Account')` 一起收进 `if (!isGuest) ...[]`，避免游客态下留下一个
   下面空空如也的孤儿标题（紧跟着的 Sessions 分区本来就已经是 `!isGuest` 门控）。第 297 行附近那句
   "游客退出路径是 Account 区块里的登录按钮"的注释同步改写，指向侧栏账号区（`_GuestSignInPrompt`）
   这个真正剩下的入口。

   **⚠️ 需要用户复核的发现**：`_GuestSignInPrompt` 只存在于 `_DesktopSidebar`（≥1200dp 桌面布局）。
   Mobile（<600dp）和 Tablet（600-1199dp）布局完全没有等价入口——`shell_scaffold.dart` 通读一遍，
   `exitGuestMode()` 在整个 `lib/` 里现在只有一个调用点。删除 Settings 页的登录按钮后，**窄于
   1200dp 的访客将没有任何 UI 路径退出访客模式登录**。这不是本次可以自行判断是否要处理的产品决策
   （用户说"侧栏账号区已经有入口了"时大概率是在桌面宽窗口下做的这个判断），按指示删除了，但这个
   衔接缺口必须点出来。

## A. macOS 红绿灯落在悬浮面板内

### 根因

`_DesktopLayout` 给侧栏套 `Padding(EdgeInsets.fromLTRB(8,8,8,8))`；macOS 原生红绿灯由系统绘制在
固定的**窗口坐标**（约 x:20, y:20，12pt 直径），不会因为 Flutter 这边加了 margin 就跟着挪动。面板从
`(8,8)` 起、圆角 16——红绿灯因此正好骑在面板左上角的圆角接缝上，从视觉上看像是"从面板里溢出来"。
加更多 margin 治不好这个问题（红绿灯是固定坐标，永远够不到"面板内部"），唯一办法是让面板的坐标
去凑红绿灯，而不是反过来。

### 修复

- macOS + 自绘标题栏时，侧栏外边距从 `(8,8,8,8)` 改成 `(0,0,8,8)`——左、上两边贴窗口边缘，右、下
  仍浮空（窗口右上角、左下角没有类似的固定坐标覆盖物，不需要同样处理）。抽出共享谓词
  `_macTrafficLightGutterNeeded(ref)`，`_DesktopLayout`（决定 padding）和 `_DesktopSidebar`（决定
  标题行内边距、面板圆角）共用同一次判断，不再各自重复计算同一个三段式门禁（这正是 v5.30.0 那次
  红绿灯 bug 的成因——两处各管各的，谁都没有真的对齐）。
- 贴边后左上角圆角改用 macOS 窗口自身的圆角（12，Big Sur 之后的通常测量值，苹果未公开精确数字），
  其余三角维持面板原本的 16。`GlassPanel` 新增可选的 `borderRadiusOverride`（`BorderRadius?`），
  为 null 时保持原来"单一 `double borderRadius`"的行为完全不变，全仓库其余调用点零改动。
- `_macTitleRowTopInset` 重新推导：面板原点从窗口坐标 y=8 移到 y=0，红绿灯下沿（窗口坐标 y=26）在
  面板本地坐标系里从 26-8=18 变成 26-0=26。两条独立路径互相印证同一个数字：(a) 按旧值的"18 加同样
  12px 缓冲"算，26+12=38；(b) 直接保留贴边前标题行的**绝对**屏幕位置（旧 margin 8 + 旧 inset 30 =
  38，这个位置本来就是调好的），两者都得到 **38**，因此没有采用任务描述里估算的"约 44"，改用推导
  出的 38 并把推导过程写进代码注释——如果真机视觉上跟 44 更接近，这是一个命名常量，改起来是一行的
  事，值得用户实机确认。

### 绿灯（zoom）禁用问题排查结果

顺着代码走了一遍完整链路：`AuthState.isPastGate`（游客也算过闸）→
`DesktopIntegration._initWindow()`/`applyWindowForAuthState()` → `window_manager` 插件 →
macOS 原生 `WindowManager.swift` 的 `setResizable()`（`mainWindow.styleMask.insert(.resizable)`，
AppKit 直接依据这个 styleMask 决定 zoom 按钮是否可点）。逻辑本身没有问题：游客/已登录状态下
`isPastGate` 为真，`setResizable(true)` 应该被调用。

但发现了一处**真实存在的竞态**：`_initWindow()` 用
`_ref.read(authProvider).valueOrNull?.isPastGate ?? false` 做**一次性同步读取**，发生在
`windowManager.ensureInitialized()`（本地插件握手，几乎瞬时）之后——而 `AuthNotifier.build()`
要 `await` 两次 `FlutterSecureStorage.read()`（真实 IO，通常比插件握手慢）才会 resolve。这意味着
一个**已经持久化为游客/已登录**的用户冷启动时，这次同步读取几乎总是还停留在 `AsyncLoading`，
`?? false` 让窗口先按"未过闸"打开（小尺寸、不可缩放）——`main.dart` 的 `ref.listen(authProvider)`
之后会correct 过来，但这中间有一段窗口已经显示、状态尚未修正的窗口。这跟路由层"过闸前显示 splash
避免内容闪烁"是同一类问题，只是窗口 chrome 这一侧从来没有对应的等待逻辑。

已修复：`_initWindow()` 改为 `await _ref.read(authProvider.future).timeout(300ms)` 取代一次性同步
读取——命中超时（例如已存 token 还要等 `_fetchMe` 网络校验，服务器慢/离线时可能真的超过 300ms）时
回落到原来的行为（假设未过闸），不会让离线场景把开窗卡住等一个可能很久的网络请求。

未能验证的部分：这个竞态是否就是用户截图里那次绿灯变灰的**唯一**成因，需要真机复现——已修的这处
只是排查中确认存在、且此仓库自己已经用 `.future` 模式解决过同类问题（`player_notifier.dart`/
`cover_palette_provider.dart` 均有先例）的一个真实 bug，不是照抄用户描述硬猜的修复。

## B. 侧栏菜单项贴边

`_SidebarTile` 的 `ListTile` 没有横向外边距，选中态背景铺满整个 ListTile 自身的边界，跟
`GlassPanel` 的发丝边框在同一批坐标上，读起来像溢出。

外面套 `Padding(horizontal: 8, vertical: 2)`，把选中态药丸的可视范围从面板边缘收进来。同时把
`ListTile` 自己的 `contentPadding`（继承自全局主题的 `horizontal: 16`）改成 `horizontal: 8`——
`8(外边距) + 8(内容内边距) = 16`，跟 `_SectionHeader`/`_AccountBlock` 的 `16` 左内边距对齐，图标/
文字的视觉左边界不会因为多了外边距就跟标题错位。

## C. 播放条只有封面能展开播放页

`MiniPlayerBar` 原本把整个内容行包在一个 `InkWell` 里跳转播放页；`_nowPlayingInfo` 现在拆成三个
独立手势：封面（`MouseRegion` + `GestureDetector` 跳 `AppRoutes.player`）、标题（跳专辑，见 D）、
歌手（跳歌手，见 D）。移除外层 `InkWell` 不影响内部按钮——它们原本就是各自独立的 `IconButton`/
`SpringInteraction`，在 gesture arena 里已经优先于外层响应，删掉外层纯粹是少了一层不该有的兜底
手势，没有改动任何内部控件自身的实现。

## D. 歌名/歌手超链接

新增共享 widget `HoverLinkText`（`lib/src/shared/widgets/hover_link_text.dart`）：`onTap` 为
`null` 时渲染纯文本（不套任何手势/`MouseRegion`）；非空时 hover 加下划线 + 手型光标，不改变默认
文字颜色（这个 app 的视觉方向是封面驱动流体色场，常驻蓝色链接色会跟整体风格冲突）。

`PlayerNotifier._makeMediaItem`/`_stubMediaItem` 的 `extras` map 补上 `artistId`（此前只有
`albumId`）；本地（游客）曲目对应的 `_localMediaItem` 没有加这个字段，`HoverLinkText` 对 `null` id
渲染纯文本，两者自然衔接、不需要额外判断"是不是本地曲目"。

`mini_player_bar.dart`（`_nowPlayingInfo`）与 `full_player_screen.dart`（`_playerBlock` 的标题/
歌手块）两处都接入，跳转复用已有路由 `AppRoutes.albumDetailPath`/`AppRoutes.artistDetailPath`
（`context.push`，保留返回栈）。

## E. 进度条间距 + 特效

- **间距**：`_MiniPlayerSeekRow`（桌面宽播放条）的时间标签此前跟滑轨零间距，两侧各加 10px
  `SizedBox`。`full_player_screen.dart` 的时间行也顺手加了 4px 左右内边距，虽然它跟滑轨本来就不在
  同一行，没有"贴着"的问题，属于顺带的一致性打磨。
- **位置平滑插值**（优先级最高的一项）：新增 `positionTweenDuration`（260ms）常量 +
  `TweenAnimationBuilder<double>` 包住两处播放条滑块的展示值（`_MiniPlayerProgressBar`、
  `_MiniPlayerSeekRow`）和播放页滑块（`full_player_screen.dart`）。`TweenAnimationBuilder` 而不是
  手写 `AnimationController`：中途被新 tick 打断时框架自己接着当前值继续补，不需要手动处理"两次
  tick 打架"；它的 controller 跟 widget 生命周期绑定，天然规避了 `cover_fluid_background.dart` 那次
  "`late final` 延迟初始化、`dispose()` 时对着失活 element 建 Ticker"的教训——不是靠"记得注意"，是
  这条路径根本不需要手写 controller。拖拽时旁路掉动画（直接读 `_dragValue`），保证拖拽手感不受
  影响。
- **渐变滑轨**：新增 `GradientSliderTrackShape`（`lib/src/shared/widgets/seek_bar_effects.dart`），
  基于 Flutter 内置 `RoundedRectSliderTrackShape` 简化改写（去掉本项目用不到的次级轨道/RTL 分支），
  active 段画 `activeTrackColor → 自身提亮` 的双色渐变，颜色来源仍是各处已有的 `activeTrackColor`
  设置，调用点只需加一行 `trackShape: const GradientSliderTrackShape()`。
- **播放中光晕**：新增 `GlowingSliderThumbShape`，`glowing` 为真时在滑块正常大小外画一圈模糊光晕
  （`MaskFilter.blur`），静态绘制、不常驻动画——每次滑块本来就要重绘（位置在动），光晕跟着一起重绘，
  没有额外的 Ticker。宽播放条的滑块本来就有"平时半径 0（隐形）、hover/拖拽时才半径 7"的既有设计
  （`_MiniPlayerSeekRowState` 的 `active` 状态），光晕的开关条件是 `isPlaying && active`——只在滑块
  本来就可见的时候才叠加光晕，不违反"平时无侵入"的既有设计；播放页滑块没有这层隐藏机制，直接绑定
  `isPlaying`。
- **缓冲进度次级轨道**：跳过。`PlaybackEngine` 抽象接口（`lib/src/playback/playback_engine.dart`）
  没有暴露任何缓冲位置的 stream/属性，加一条要先扩展这个跨引擎抽象，超出本次视觉打磨的范围——按
  任务里"拿不到就跳过，别硬造"的指示处理。
