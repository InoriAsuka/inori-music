# v5.30.0 — 主界面重做（悬浮侧栏 + EchoMusic 播放条/菜单）+ Cover Flow + v5.29.0 遗留三小修

完整规划见 `/Users/inorihimea/.claude/plans/smooth-toasting-manatee.md` 的 Phase v5.30.0 一节，
外加它上面「v5.29.0 实机验收结论」里注明并入本批的三个小修。v5.30.5（macOS 窗体统一）、
v5.31.0（插件 ABI）、v5.32.0（media_kit 过渡引擎）本次不碰。

## A. 悬浮侧栏

`_DesktopLayout` 原来是 `SizedBox(width:220, child:_DesktopSidebar)` + `VerticalDivider` 贴边
布局。改成 `Padding(EdgeInsets.fromLTRB(8,8,8,8))` 包住同一个 `SizedBox`，`VerticalDivider`
直接删掉——外边距 + `GlassPanel` 自带的发丝边框已经承担了原来分割线的视觉职责，两者都留会
是重复。

`_DesktopSidebar` 内部把最外层从 `Material(color: context.skinColors.surface)` 换成
`GlassPanel(padding: EdgeInsets.zero, borderRadius: 16)`——选 `EdgeInsets.zero` 是因为侧栏
自己每一处（标题行、账号区、列表行）已经在管自己的内边距，`GlassPanel` 默认的
`EdgeInsets.all(16)` 会跟这些内边距叠加而不是单纯框住悬浮面板的边缘。`GlassPanel` 内部本来
就是 `Material`，v5.22.0 那次「`ListTile` 的墨水画在最近 `Material` 祖先上，中间夹带背景色
`DecoratedBox` 会吃掉」的坑不会重演。

## B. 侧栏账号区仿 EchoMusic：未登录显示登录入口

`_AccountBlock` 原来给游客模式渲染 `username = t.guest`（"Guest"）当作一个真用户名在显示——
一个套着身份外壳的占位符，点了什么也不会发生。EchoMusic 的账号区把"未登录"当成它自己的一
个状态：主文字"未登录"，副文字"点击登录账号"，整行可点。

拆成两个 widget：`_AccountBlock`（未登录时直接返回 `_GuestSignInPrompt`；已登录保留原来的
头像+用户名+设置按钮）和新的 `_GuestSignInPrompt`（人形图标头像占位 + `t.tapToSignIn` 文字 +
`chevron_right`，整行 `InkWell`，`onTap` 调用 `ref.read(authProvider.notifier).exitGuestMode()`
——跟 Settings 页那个"登录"按钮调用的是同一个方法，不是重新实现一遍退出游客模式的逻辑，路由
的 `isPastGate` 重定向本来就会在状态翻转后接管，把用户带到 `/login`）。

新增 l10n key `tapToSignIn`（en: "Tap to sign in" / zh: "点击登录" / ja:
"タップしてログイン"），写进三个 arb 文件后跑 `flutter gen-l10n` 重新生成——这个 key 之前
不存在，跟三小修那条"`nowPlaying` 已存在、只是没接上"是不同情况。

## C. 播放条仿 EchoMusic 尺度

`MiniPlayerBar` 原来的内容区没有明确的高度约束（自然堆叠 44px 封面 + 一行按钮），仿
EchoMusic 的 `PlayerBar.vue`（`h-21`=84px 圆角浮层，封面 56px，传输图标 22px，三段式
`justify-between`）：

- 内容区套 `SizedBox(height: 84, key: MiniPlayerBar.contentKey)`——键是给测试用的，量出的
  是**内容区**（顶部细进度条之外的部分），不是含进度条的整张卡片。
- 封面从 44px 提到 56px（`_MiniPlayerArtwork` 加 `size` 参数，图标和圆角按 EchoMusic 的比例
  `24/56` 和 `10/56` 跟着缩放，不是写死数字）。
- 传输图标（上一首/下一首）从 24px 改成 EchoMusic 的 22px；播放/暂停保持原有的 28px（比
  两侧的传输图标大一圈，跟 v5.30.0 之前的比例关系一致）。
- 布局从"标题 `Expanded` + 传输按钮 + 睡眠定时器"改成显式三段：左（封面+标题，`Expanded`）
  / 中（传输三件套，`Row(mainAxisSize:min)`）/ 右（睡眠定时器，`Expanded`+`Align(centerRight)`)。
  左右两段用相同的 flex，中间三件套无论标题多长、右边有没有睡眠定时器都保持在正中——这是
  `full_player_screen.dart` 播放页传输行已经在用的同一个居中技巧，之前迷你播放条从来没有
  这个保证（睡眠定时器紧跟在"下一首"后面，没有对侧配重）。

顶部细进度条条**留在 84px 预算之外**，不是从里面抠出来——EchoMusic 没有等价物（它的进度条
长在中间那一列里），把它叠到内容区顶部会需要它在命中测试优先级上赢过下面的内容，这是一个
本 phase 没打算做的 UX 取舍，写进了 doc comment 里避免以后被误解成疏漏。

## D. Cover Flow 封面模式

新文件 `lib/src/player/cover_flow_artwork.dart`：`CoverFlowArtwork` 是纯 UI 组件，不自己碰
`PlayerState`/`artworkUrlProvider`——`itemCount`/`currentIndex`/`itemBuilder` 都由调用方传入
（`_playerBlock` 已经有现成的 `state.queue`，重复一份到组件内部只会有两份数据可能不同步的
风险）。核心是一个纯函数 `visibleSideCount({width, centerSize})`：每侧能放下几张由
`(半区宽 - 半张封面宽) / (封面宽 × 0.68 步进)` 决定，封顶 3 张——这是"可见张数由播放器宽度
决定"这条要求的字面落点，可以脱离 widget 直接单测。渲染上用 `Transform`（`rotateY` + 透视
`setEntry(3,2,0.001)`）做两侧封面的斜置和缩放（`_sideScale=0.72`），点击两侧封面会调用
`onSelect`（`_playerBlock` 接的是 `playQueue(..., initialIndex: index)`，复用 `_QueueList`
已经在用的同一个跳转方法）。

只接进宽屏（`canSplit`）分支——窄屏的 `PageView` 已经占用了水平滑动手势在封面和歌词之间切换，
Cover Flow 再引入一套水平手势去翻队列会跟它打架而不是共存。单曲队列（`queue.length<=1`）也
回退到普通封面——没有邻居可以"流"的 Cover Flow 没有意义。这两条都是范围内的收窄，不是漏做，
写进了 `full_player_screen.dart` 的行内注释。

设置项：新文件 `lib/src/player/cover_flow_mode_provider.dart`，`CoverFlowModeNotifier` 跟
`BilingualLyricsNotifier` 完全同构（`SharedPreferences` 持久化的一个布尔开关），Settings 页
"外观"分组下加一条 `SwitchListTile`。

## E. 三个小修（并入本批）

1. **`'Now Playing'` 走 l10n**：`app_en.arb` 里 `nowPlaying` 早就存在，直接换成
   `AppLocalizations.of(context).nowPlaying`。

2. **顶栏对比度——诊断出的根因比原计划描述的更深一层**。原计划的假设是"`artworkOverlaySkin`
   按 dominant 色算的是一个全局明暗档，局部（`CoverFluidBackground` 是动态多色场）跟全局判断
   不一致"。写了一个探测测试直接验证：给一个很暗的封面 + 一个鲜艳的强调色，读取渲染出来的
   "Now Playing" 文字颜色——**结果跟 `artworkOverlaySkin()` 算出来的颜色完全对不上，倒是跟
   环境皮肤（Sakura Dusk）写死的 `onSurfaceVariant` 逐位相等，不管喂进去什么封面/强调色都不
   变**。

   真正的原因：顶栏那段 `Padding(...)` 是直接在 `_FullPlayerScreenState.build(BuildContext
   context)` 的作用域里构造的，用的是**外层** `context`（`FullPlayerScreen` 自己的
   element）。而 `LyricsBackground` 插入的 `SkinScope`（携带按封面算出的派生皮肤）是
   `build()` **即将返回**的树里的一个后代节点——继承查找只能往祖先方向走，找不到还没建好、
   将要建在自己下面的东西。顶栏因此从 v5.26.0 开始就从来没有真正跟着封面变过颜色，一直读的
   是环境皮肤给浅色背景配的暗灰字——这正好解释了为什么它在深色背景上会看不清（暗灰字配
   任意亮度的封面，深色区域自然低对比度），跟"局部 vs 全局明暗"的猜测是两个不同的机制。

   参照 `Scaffold.of(context)`/`LayoutBuilder` 那类"要读刚创建出来的祖先，得从更深的 context
   拿"的标准 Flutter 写法，把整段顶栏包进 `Builder(builder: (context) => ...)`——同名
   `context` 遮蔽外层变量，内部原有代码一字不改就自动切换到正确的（`SkinScope` 后代）
   context。用探测测试确认修复后颜色确实跟 `artworkOverlaySkin()` 算出的值一致，再删掉探测
   测试，把断言正式收进 `full_player_layout_test.dart`（"再生中" 出现、"Now Playing" 不出现，
   跑在日语 locale 下——中文/日语原文和硬编码英文字符串在英文 locale 下永远撞车，无法区分
   到底有没有真的接上 l10n）。

   在这个修复的基础上再叠加计划要求的顶栏渐变遮罩（`_topBarScrim`）：色板极性跟随刚修好的
   `context.skinColors.onBackground` 亮度（暗底白字→黑色渐变，亮底黑字→白色渐变），从上到下
   `alpha 0.5→0`，作为对抗色场局部起伏的第二道防线——现在建立在正确解析的颜色之上，而不是
   建立在一个从来没变过的错误颜色上。

3. **播放/暂停键跟随强调色——按计划先证伪**。写了一条断言：给定封面 + `lightVibrant`
   强调色，取播放/暂停按钮外层 `Container.decoration.color`，判断它是否等于
   `CoverPalette.accentOverArtwork`。**测试第一次跑就通过**——代码原来就是对的
   （`artworkOverlaySkin` 里 `sakuraPink: accent`，按钮读 `context.skinColors.sakuraPink`，
   两者本就在同一个正确解析的 `SkinScope` 之下，跟顶栏那个 bug 不是同一处代码路径）。**没有
   改任何实现代码**，断言原样保留成回归测试收进 `full_player_layout_test.dart`。

## 与计划的一处偏离

计划把顶栏对比度问题诊断成"全局 vs 局部明暗不一致"，据此只要求加一层渐变遮罩。实测发现
根因更深——顶栏从来没有接上派生皮肤，读的是环境皮肤的固定颜色，是一个 `BuildContext`
作用域错误，不是明暗判断精度问题。按任务要求"发现计划某处写错了，不要硬做，如实记录偏离"：
补上了 `Builder` 包装这个根因修复，再叠加计划要求的渐变遮罩作为第二道防线，两者不冲突，都
保留。
