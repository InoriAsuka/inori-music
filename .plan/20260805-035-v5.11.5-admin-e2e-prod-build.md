# v5.11.5 — Admin E2E 改用生产构建，根治 storage tab 计时不稳定

日期：2026-08-05
状态：已完成

## 背景

v5.11.4 把 `storage tab` 用例的超时从 8s/30s 放宽到 15s/45s 后推送观察，
远端结果反而更差：18.9s（首次尝试，仍超过新的 15s 断言超时）/ 45.1s
（重试，撞满新的 45s 整体超时），比放宽前的 11.9s/30.1s 还慢。这说明
"加大超时"是在追一个不断后退的目标，不是单纯余量不够。

## 根因

`.github/workflows/build.yml` 的 `admin-e2e` job 用 `npm run dev`
（Turbopack 开发模式）起 admin 服务。开发模式下每个路由是第一次被访问
时才编译。`storage` 恰好是套件四个用例里唯一"第一次真正执行到断言阶段"
的路由——此前 middleware/baseUrl 两个缺陷（v5.11.3 已修）让全部用例
都卡在登录阶段，`storage` 从未真正跑到过这一步。在 CI 共享 runner 的
资源约束下，这次首访编译的延迟足以吃掉整个超时预算；且预算给得越松，
观察到的实际耗时也跟着涨——这是资源竞争下的可变延迟特征，不是一个可以
靠固定超时预算覆盖住的固定缺口。

## 实现

`.github/workflows/build.yml` 的 `admin-e2e` job：
- 新增 `Build admin` 步骤：`npx next build`（生产构建，全部路由在构建期
  预编译）。
- `Start admin dev server` 改名 `Start admin server`，命令由
  `npm run dev` 改为 `npx next start -p 3001`（生产模式启动，运行期不
  再有按需编译的方差）。
- `NEXT_PUBLIC_API_BASE_URL` 保留在启动步骤的 env（`next.config.ts` 的
  `rewrites()` 与 `client.ts`/`store/auth.ts` 的 SSR 分支都是运行期读取
  `process.env`，客户端分支已在 v5.11.3 改为硬编码 `/admin`，不依赖这个
  变量，故不需要在构建期设置）。

v5.11.4 放宽的超时（15s/45s）保留作为额外余量，不再是承载修复的主力。

## 验证

```bash
cd services/admin
NEXT_PUBLIC_API_BASE_URL=http://localhost:8080 npx next build   # 构建通过
NEXT_PUBLIC_API_BASE_URL=http://localhost:8080 npx next start -p 3011 &
E2E_USERNAME=ci_viewer E2E_PASSWORD=ci-password-123 npx playwright test
# 连续跑两次，均 4 passed；storage tab 耗时 6.7s / 6.3s，
# 与其余三个用例（5.6s–10.2s）同一量级，不再是异常值
```

远端 CI 待本次推送最终确认。
