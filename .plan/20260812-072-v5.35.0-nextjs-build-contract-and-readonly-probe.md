# v5.35.0 — Next.js 构建期配置契约 + `local` 存储后端只读探测

2026-08-11 生产环境（Unraid）出了一次登录事故，追出的根因是本仓库反复出现的「静默失败」模式的又一个变种：构建期配置缺失时不报错，只是悄悄退到一个错误的兜底值，直到运行时才在一个完全不相关的地方（浏览器 500）表现出来。本 phase 四项工作：(1) 把这类构建期配置缺失从「静默兜底」改成「响亮失败」，(2) 给这个契约加不空洞的守卫测试，(3) 顺带修一个同源但独立发现的存储后端健康探测设计缺陷（只读挂载永远报 unhealthy），(4) 按流程收尾发布。`services/mobile` 未触碰。

---

## 一、构建期配置契约

### 事故根因链

1. 用户直连 web 容器的 `IP:3000`，绕开了 nginx 网关。
2. 浏览器侧 `services/web/lib/api/client.ts` 的 `baseUrl` 在 `typeof window !== "undefined"` 时是 `""`（同源相对路径，依赖 Next.js 的 `rewrites()` 转发），`/api/v1/auth/login` 因此落到 `next.config.ts` 自己的 rewrite 上。
3. `next.config.ts` 原写法：`const apiBase = process.env.NEXT_PUBLIC_API_BASE_URL ?? "http://localhost:8080"`。`services/web/Dockerfile`、`services/admin/Dockerfile` 的 builder stage 都**没有 `ARG NEXT_PUBLIC_API_BASE_URL`**。
4. `.github/workflows/docker.yml` 的 `publish-web`/`publish-admin` job 其实一直在传 `--build-arg NEXT_PUBLIC_API_BASE_URL=http://api:8080`（`docker.yml:106,152`，已核实存在）——但 Dockerfile 没有对应的 `ARG` 声明，BuildKit 判定这个 build-arg「未被消费」，只打一条非致命警告，构建照常成功。容器内 `RUN npm run build` 执行时，进程环境里的 `NEXT_PUBLIC_API_BASE_URL` 其实是空的。
5. `next build` 就地求值 `rewrites()`，兜底值 `http://localhost:8080` 被**永久烤进**产物 `.next/routes-manifest.json`（已用未修复代码实测复现，见下）。
6. `docker-compose.prod.yml` 给 web/admin 服务设置了运行时环境变量 `NEXT_PUBLIC_API_BASE_URL: "http://api:8080"`——但完全无效：`next start`（含 standalone `server.js`）不会重新执行 `next.config.ts` 的 `rewrites()`，只读预编译好的 manifest。
7. web 容器里没有任何东西监听 8080，登录请求 `ECONNREFUSED`，前端只看到裸的 500，没有任何指向真实原因的线索。

### 修复

**Dockerfile（web + admin 各一份）**，在 builder stage、`RUN npm run build` 之前：

```dockerfile
ARG NEXT_PUBLIC_API_BASE_URL
ENV NEXT_PUBLIC_API_BASE_URL=${NEXT_PUBLIC_API_BASE_URL}
```

`docker.yml` 已经在传这个 build-arg，缺的只是 Dockerfile 侧的声明——这一步本身就让 CI 构建的镜像行为发生改变（`http://api:8080` 真正流入 `next build`）。

**`next.config.ts`（web + admin 各一份）**，从静态对象导出改成 Next.js 官方支持的函数式导出 `(phase) => NextConfig`：

```ts
import { PHASE_PRODUCTION_BUILD } from "next/constants";

const nextConfig = (phase: string): NextConfig => {
  const apiBase = process.env.NEXT_PUBLIC_API_BASE_URL;
  if (!apiBase && phase === PHASE_PRODUCTION_BUILD) {
    throw new Error(/* 点名变量名 + 指向 requirement.md 的事故记录 */);
  }
  const resolvedApiBase = apiBase ?? DEV_FALLBACK_API_BASE_URL; // 只在非生产构建阶段用到
  return { /* ...rewrites() 用 resolvedApiBase */ };
};
```

### 关键判断：用什么条件区分"生产构建"

任务要求这个判断自己核实并写明理由。核实过程：

- 读 `node_modules/next/dist/bin/next`（CLI 入口）：`const defaultEnv = commandName === 'dev' ? 'development' : 'production'; process.env.NODE_ENV = process.env.NODE_ENV || defaultEnv;`——**`next start` 和 `next build` 一样，NODE_ENV 未显式设置时都默认落到 `"production"`**。如果拿 `NODE_ENV === "production"` 做判断条件，`next start`（正在跑的生产服务）和 `next build`（正在构建）无法区分，缺变量的判断分支一旦被触发就可能直接打断一个正在运行的生产服务，而不只是让构建失败——风险模型不对。
- 读 `node_modules/next/dist/build/index.js:384`：`next build` 用 `loadConfig(PHASE_PRODUCTION_BUILD, dir, ...)` 加载配置；`process.env.NEXT_PHASE` 也在同文件 1002 行被设为同一个值。
- 读 `node_modules/next/dist/server/next.js:192`、`node_modules/next/dist/server/lib/router-server.js:105`：`next start`（非 dev 模式）用 `PHASE_PRODUCTION_SERVER` 加载配置，与 `PHASE_PRODUCTION_BUILD` 是两个不同的字符串常量，精确不重叠。
- 读 `node_modules/next/dist/server/config-shared.js` 的 `normalizeConfig`：`if (typeof config === 'function') config = config(phase, { defaultConfig })`——函数式导出、按 `phase` 分支，是 Next.js 官方文档记录在案的机制，不是 hack。

结论：用 `phase === PHASE_PRODUCTION_BUILD`（从 `next/constants` 导入）而不是 `NODE_ENV`。效果：缺变量只可能让 `next build` 本身失败（响亮、发生在犯错的当下），`next start` 阶段哪怕将来 `rewrites()` 真的被重新求值也不会被这条判断打断——即使当前生产环境的运行时变量本来就设置正确、理论上不会触发，这个判断仍然更贴合"构建失败"这个诉求本身，而不是恰好因为当前配置凑巧安全。`next dev` 走 `PHASE_DEVELOPMENT_SERVER`，兜底值不受影响，开发体验不变。

### CI 连带修复（非范围外新增，是本次改动的直接后果）

排查 `.github/workflows/build.yml` 全部 `next build`/`npm run build` 调用点时发现：`admin-e2e` job 的「Build admin」步骤（`npx next build`，改动前第 280 行附近）**从来没有设置 `NEXT_PUBLIC_API_BASE_URL`**——一直是静默兜底值 `http://localhost:8080` 在悄悄撑住这一步（凑巧这个 CI job 里 API 确实监听在 `localhost:8080`，所以从未暴露）。这是同一个 bug 模式在 CI 里独立存在的第三处实例。本次的 `throw` 一旦生效，这一步会被直接炸穿，CI 转红——这是本次改动的必然连带后果，不修就是留下一个新炸的坑，因此一并补上：

```yaml
      - name: Build admin
        working-directory: services/admin
        run: npx next build
        env:
          NEXT_PUBLIC_API_BASE_URL: http://localhost:8080
```

同一 workflow 里另外 4 处 `next build`/`npm run build`（web 的 Build 步骤、admin 的 Build 步骤、admin-e2e 的 Start admin server 步骤）核对过，均已设置该变量，无需改动。

## 二、守卫测试

任务要求：断言构建产物 `.next/routes-manifest.json` 的 rewrite destination 不含 `localhost`，并且要把守卫拿去对修复前代码跑一遍证明它会失败。

### 放两层，理由

- **单测层**（`services/web/next.config.test.ts`）：直接 `import nextConfig from "./next.config"` 调用导出的函数，不跑真实 `next build`，秒级完成，随 `npm test`（`vitest run`）常规执行。覆盖四种场景：缺变量炸构建 / 变量为空字符串炸构建 / 变量正确设置时不炸且 rewrites 目的地不含 localhost / dev phase 下兜底值不受影响。
- **构建产物层**（`scripts/verify-production-build-requires-api-base-url.mjs`，web/admin 各一份）：真实跑两次 `npm run build`（就是 Docker builder stage 里跑的同一条命令），直接读磁盘上的 `.next/routes-manifest.json`，逐字匹配任务要求的断言对象。这一层慢（两次完整生产构建），不适合塞进日常 `npm test` 循环，因此做成独立脚本 + `package.json` 的 `verify:build-config` 命令，接入 `.github/workflows/build.yml` 的 web/admin 两个 job（各自「Build」步骤后新增「Verify build-time config contract」步骤）。

**admin 没有配单测层**：核实发现 `services/admin` 完全没有 Vitest（无依赖、无 config、此前 0 个 `*.test.ts` 文件，只有 Playwright e2e）。一开始按 web 的样子写了一份 `services/admin/next.config.test.ts`，随即意识到——没有任何脚本会执行它，是一个看起来像测试、实际上永远不会跑的死文件，比"空洞测试"更差（空洞测试至少会跑、只是断言太弱；死文件连跑都不会跑）。已删除，改为只依赖构建产物层（该层不依赖任何测试框架，两端行为对等、都是真实会被执行的检查）。是否给 admin 补齐 Vitest 基建判定为超出本次任务范围（构建配置契约的 bugfix，不是补测试基建），不擅自扩大，如实记录。

### 一个容易踩的坑（记录下来避免以后重犯）

`process.env` 是 Node 的特殊自动字符串化对象。写 `next.config.test.ts` 第一版时用了 `delete process.env.X` 做清理，Biome 的 `noDelete` 规则建议改成 `process.env.X = undefined`——**这个建议对 `process.env` 是错的**：赋值 `undefined` 会被字符串化成字面量 `"undefined"`，不是真正删除键，会悄悄让"变量未设置"这个测试前提失真。已用一次性脚本实测确认（`process.env.X = undefined` 后 `process.env.X === "undefined"` 为真，键仍然 `in` 对象里），改用 vitest 官方的 `vi.stubEnv(name, undefined)`（内部真正做 `delete`，已读源码 + 实测双重确认）配 `vi.unstubAllEnvs()` 收尾。`scripts/verify-...mjs` 里同名的 `delete env.X`（`env` 是 `{...process.env}` 的**普通对象**副本，传给 `spawnSync` 的 `env` 选项）则是另一回事——实测确认 `spawnSync` 会正确丢弃值为 `undefined` 的 key、不会字符串化，这里应用 Biome 的建议是安全的，已改。两处看似同一个 lint 规则、同一个"删除环境变量"意图，正确修法却相反，取决于操作对象是不是 `process.env` 本身。

## 三、`local` 存储后端只读探测

### 根因

`services/api/internal/storage/probe.go` 的 `FilesystemProber.Probe` 对所有挂载类后端（local/nfs/smb/distributed 的 `mounted-filesystem` adapter）统一走同一条路径：`os.Stat` 确认是目录后，无条件 `os.CreateTemp` 写一个探针文件、写入内容、range read、删除。音乐服务器把媒体库以只读方式挂进容器（`docker-compose.prod.yml` 里现成的注释例子 `# - /mnt/music:/mnt/music:ro`）是常态，写探针在这种拓扑下必然因权限被拒而失败，探测结果与后端真实可达性无关——一个完全健康、可以正常提供读流量的后端会被永久判定 unhealthy。

### 设计选择：显式字段，不做"写失败自动降级"

`LocalConfig`/`NFSConfig`/`SMBConfig`/`DistributedConfig` 均无既有的"只读"概念，需要新增。考虑过两种方案：

1. **显式配置字段**——运营者在注册后端时声明"这个后端就是只读的"，探针据此选择只读检查。
2. **自动探测**——先照常尝试写，捕获到 `EROFS`/`EACCES` 一类权限错误时自动降级为只读检查、判定健康。

选了方案 1。理由：任务原话明确要求"保持对可写后端的原有语义不变（可写后端仍应能探测出能写）"——只读挂载的权限报错和"本该可写但配置/权限出了真问题"的权限报错，在操作系统层面是**同一类错误**（`EACCES`/`EROFS`），自动探测方案没有任何办法区分"这是设计上的只读，健康"和"这是运维事故，不健康"，会把真正的写权限故障也一并静默判定为健康，直接违反任务这条硬约束。显式字段把判断权交给注册后端时的运营者意图，而不是靠错误码猜测。

### 修复

`services/api/internal/storage/types.go`，`LocalConfig` 新增：

```go
type LocalConfig struct {
	RootPath string `json:"rootPath"`
	ReadOnly bool   `json:"readOnly"`
}
```

零值 `false`，对所有既有后端配置（未显式设置这个字段的历史数据）完全无感，原写探针语义原样保留。

`services/api/internal/storage/probe.go`，`Probe` 在原有 `os.Stat` + `IsDir` 检查之后分支：

```go
if backend.Type == BackendTypeLocal && backend.Config.Local != nil && backend.Config.Local.ReadOnly {
	return probeReadableDirectory(root)
}
```

新增 `probeReadableDirectory`：`os.Open(root)` + `Readdirnames(1)`，把 `io.EOF`（目录为空）视为健康而非失败——刚挂载的空只读库是合法状态，不该因为"还没有文件"被判定不健康。

### 范围：只做 `local`，不做 nfs/smb

任务原话与事故场景（`/media/music:ro`）都指向本地 bind mount，`FilesystemProber.Probe` 虽然内部对 local/nfs/smb/distributed 共享同一段探测代码，但四者的配置结构（`LocalConfig`/`NFSConfig`/`SMBConfig`/`DistributedConfig`）各自独立、没有共享基类，要给 nfs/smb 也加 `ReadOnly` 需要各自改各自的 struct + OpenAPI schema，是比本次任务描述更大的改动面。nfs/smb 挂载理论上有完全相同的只读诉求，但不在本次任务范围内，未改动，如实记录，留作后续候选。

### 测试与证伪

`services/api/internal/storage/probe_test.go` 新增 4 个测试：

- `TestFilesystemProberReadOnlyLocalSkipsWriteProbe`——目录真实 `os.Chmod(root, 0o555)`（不是只设配置字段，是操作系统层面真的只读），`ReadOnly: true` 的 local 后端探测必须成功。这是本次改动的核心回归测试：如果 `Probe` 曾经又开始无条件写探针，这个测试会在真实的权限拒绝上失败，而不是靠 mock。
- `TestFilesystemProberReadOnlyLocalAcceptsEmptyDirectory`——空目录（不 chmod，只测"空"这个语义）必须探测健康，防止 `Readdirnames(1)` 的 `io.EOF` 被误判成错误。
- `TestFilesystemProberReadOnlyLocalRejectsMissingRoot`——只读分支指向不存在的路径仍必须报 `ErrProbeFailed`，证明这不是"只读就永远健康"的开关，只是换了一种探测方式。
- `TestFilesystemProberWritableLocalStillFailsOnReadOnlyMount`——差分测试：同一个真实 chmod 只读的目录，**不带** `ReadOnly` 标记的（默认零值）后端必须仍然探测失败。这条证明修复没有把"可写后端能探测出能写"这条既有语义连带破坏掉。

`requireChmodEnforced` 辅助函数在 root 用户或 Windows 下跳过 chmod 相关测试（两种环境下目录权限位的语义都不能保证阻止写入，会导致误判），本仓库 Go CI 只在 `ubuntu-latest` 非 root 用户下跑，本地开发机 `whoami` 确认非 root，两个环境都会正常执行这些测试而非被跳过。

证伪：`git stash push -- services/api/internal/storage/probe.go` 只回退这一个文件（`types.go` 的 `ReadOnly` 字段保留，代码仍可编译），跑：

```
=== RUN   TestFilesystemProberReadOnlyLocalSkipsWriteProbe
    probe_test.go:110: Probe() error = storage backend probe failed: create probe file: open .../.inori-music-probe-...: permission denied, want nil (a read-only mount must not be reported unhealthy)
--- FAIL: TestFilesystemProberReadOnlyLocalSkipsWriteProbe (0.00s)
```

精确复现了事故本身的错误信息（`permission denied`）。其余 3 条新测试在回退版本下仍然 PASS（符合预期——它们分别测试"空目录"“缺失路径”“可写后端仍报错"，这些语义在回退版本下要么不涉及 `ReadOnly` 分支、要么本来就成立，不是本次修复要catch的那个特定 bug；只有 `TestFilesystemProberReadOnlyLocalSkipsWriteProbe` 是专门盯着"是否无条件写探针"这一点的）。`git stash pop` 恢复后全部 4 条转绿。

## 四、发布收尾

- `VERSION`: `5.34.1` → `5.35.0`。
- `requirement.md`：新增 `### v5.35.0` 条目，最新在前。
- OpenAPI：`packages/api-contract/openapi/storage-admin.v1.json` 的 `LocalConfig` schema 新增可选 `readOnly` 属性（不进 `required`，向后兼容）；`info.version` 从 `5.4.0` 改为 `5.35.0`。这份契约版本历史上不是每次发布都跟着跳（只在 schema 真变化时才动，例如 v5.5.0 时从 `5.0.0` 跳到 `5.4.0`，当时也不严格等于当时的发布版本号），本次选择直接对齐当前发布号 `5.35.0` 而不是继续沿用它自己的独立序号——理由是"同步"最直白的含义就是让两个版本号一致，便于以后一眼看出"这份契约最后一次改动是哪个发布"，没有找到理由继续维护一套平行的、容易漂移的独立序号。
- `TestStorageAdminOpenAPIContractSchemasAndErrors`（`services/api/internal/httpapi/openapi_contract_test.go`）只断言 schema 存在、不校验具体属性列表，新增的 `readOnly` 不影响该测试，已跑过确认仍 PASS。
