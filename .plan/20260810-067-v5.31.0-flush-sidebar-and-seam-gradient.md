# v5.31.0 — 侧栏齐平化 + 中缝渐变层 + macOS 拖动区回归 EchoMusic

用户战略决策（记于规划文档「批次三：统一设计语言」，2026-08-10 定）：**不再追单一 OS 原生保真**，改用 EchoMusic 式自洽跨平台设计语言。理由是 v5.30.5/.6/.7 三个版本证明了追 macOS 原生保真每修一处就长一道新缝，而四端各自追原生等于维护四套 chrome。**唯一例外：macOS 红绿灯保持系统绘制**——自绘一眼假，且会丢掉双击标题栏/右键菜单/全屏行为。Windows/Linux 继续用自绘三键，但样式跟统一语言走，不做 WinUI3 那种强原生效果。

## 问题诊断（查实，非推测）

用户反馈窗口和 EchoMusic 并排看「割裂感很明显」，具体框了两处：侧栏与内容之间的竖缝，以及侧栏底部的空白区。

拉取 EchoMusic 源码（`github.com/hoowhoami/EchoMusic`）核对后确认：**骨架本来就是对的**。`MainLayout.vue` 是 `flex` 左右栏，`PlayerBar` 在右列 `flex-col` 的末尾——不是横贯全宽。本仓库的 `_DesktopLayout` 结构一致，不需要动。

**差别在侧栏的表面处理。** `Sidebar.vue` 根节点是 `h-full flex flex-col bg-bg-sidebar border-r border-[var(--border-subtle)]`——齐平一整列，通铺背景色，只有右侧一条 hairline 边框，没有外边距、没有圆角、没有阴影。顶部是一段纯拖动区，macOS 48px、其他平台 24px。本仓库的侧栏在 v5.30.0–v5.30.7 期间一直是 `Padding(8) + GlassPanel(圆角+hairline+阴影)` 的四边浮空面板，于是「面板右边框 + 8px 间距 + 内容区左缘」叠成一道粗缝，侧栏底部导航列表下面也空出一块视觉上悬空的白。

EchoMusic 明确处理过中缝：`MainLayout.vue` 里有 `layout-accent-gradient` 一层，注释原文「主题色顶部渐变氛围层（横跨侧栏与内容，盖住中缝避免出现分隔白线）」，铺在 flex 容器里、横跨侧栏与内容两栏的顶部渐变。

参考的播放条已经匹配（v5.30.0 起对齐 EchoMusic `PlayerBar.vue` 尺度），本批不改。

## A. 侧栏从悬浮面板改成齐平列

`lib/src/shared/widgets/shell_scaffold.dart`：

- `_DesktopLayout` 去掉侧栏外面那层 `Padding`——侧栏贴着窗口左、上、下三边（`SizedBox(width: 220, child: _DesktopSidebar(...))` 直接放进 `Row`，`Row` 本身 `crossAxisAlignment: CrossAxisAlignment.stretch` 已保证纵向撑满）。
- `_DesktopSidebar` 不再用 `GlassPanel`，改成 `DecoratedBox`（`color: context.skinColors.surface` 通铺背景 + `border: Border(right: BorderSide(...))` 仅右侧发丝边框，无圆角无阴影）套一层 `Material(type: MaterialType.transparency)`。`ListTile` 需要 `Material` 祖先才能画选中背景和 ink，`GlassPanel` 内部原本提供这个，换掉之后必须显式补一层——这个坑本仓库在 v5.22.0（`ColoredBox` 吞掉 ink）和 v5.30.7（换皮 `GlassPanel` 后重新验证过一次）各踩过。这次用 `type: transparency` 的空 `Material` 显式声明"这里需要 Material 上下文，但不画任何颜色"，颜色完全交给外层 `DecoratedBox`。
- 侧栏宽度维持 220（EchoMusic 是 230，差别不到 10px，不值得为此改动）。
- 因「让红绿灯落进悬浮面板」而在 v5.30.7 引入的特判——macOS 下 `EdgeInsets.fromLTRB(0,0,8,8)` 贴边 + 左上角单独取窗口圆角（`_macWindowCornerRadius`）——连同 `_macTrafficLightGutterNeeded` 共享谓词一并删除。`GlassPanel.borderRadiusOverride`（v5.30.7 为这个特判专门扩展出的入参）核对全仓库后确认除本次删除的调用点外没有其他使用者（`full_player_screen.dart` 的两处 `GlassPanel` 调用都只传 `padding`/`child`，从未用过这个字段），因此退回到扩展前的形状：`GlassPanel` 只保留原来的单一 `double borderRadius` 字段。

## B. macOS 顶部拖动区改用 EchoMusic 的做法

`_DesktopSidebar` 删除 `_macTitleRowTopInset`（38，从红绿灯精确几何反推而来，三个版本内改了两次数值——v5.30.0 的 24→v5.30.5 的 30→v5.30.7 的 38，一路都在"重新推导同一个像素常量"，这本身就是方法论层面的信号：不该继续按精确坐标反推，该换整个机制）与 `_defaultTitleRowTopInset`（24），改成：

- 侧栏第一个子节点是一段纯空白拖动区：`DragToMoveArea(child: SizedBox(height: isMac ? 48 : 24, width: double.infinity))`。macOS 48px 舒适覆盖红绿灯最低点（窗口坐标 y=26）而不需要知道精确像素；非 macOS 24px 纯粹是跟 EchoMusic 保持视觉一致 + 提供一个顺手的拖动手柄（Windows/Linux 的自绘窗口按钮在内容列的 `DesktopAppBar` 上，不在侧栏）。
- 品牌行（`InoriMark` + "Inori Music"）恢复固定内边距 `EdgeInsets.fromLTRB(16,24,16,12)`——这是 v5.30.0 的原始值，不再靠一个跟红绿灯对齐算出来的数字把自己顶下去。
- 拖动区仅在 `DesktopIntegration.isDesktop && !ref.watch(systemTitleBarProvider)` 时渲染（新增私有静态方法 `_usesCustomChrome`，与 `DesktopAppBar` 判断"是否使用系统标题栏"的既有惯例一致）。系统标题栏开启时，真实原生标题栏已经横跨整个窗口宽度（侧栏也在其下方），再叠一条自绘空白拖动区只是死重的额外留白，不会有任何实际拖动收益。
- 移动端不受影响——`_DesktopSidebar` 只在 ≥1200dp 使用。

## C. 中缝渐变氛围层

新增 `_LayoutAccentGradient`，铺在 `_DesktopLayout` 用 `Stack` 包起来的 `Row` 之上（`Positioned(top:0,left:0,right:0)`），`IgnorePointer` 包裹保证不吃点击——侧栏标题行、账号区、前几个导航项都要能透过这层渐变继续响应点击。

- **颜色**：跟随当前播放曲目封面取色。Shell 层从未套用过 `artworkOverlaySkin` 那层覆盖皮肤（只有播放页/歌词页会套），所以 `context.skinColors.sakuraPink` 在这里就是环境皮肤的静态品牌色，不会自动带上封面色——要让渐变真的"跟着封面走"，必须直接 `ref.watch(coverPaletteProvider(...))` 拿到当前曲目的调色板，再用 `CoverPaletteAccent.accentOverArtwork`（`artworkOverlaySkin` 给播放页控件选强调色用的同一套优先级）挑一个色标；没有调色板（未在播放 / 还没提取完）时退回 `context.skinColors.sakuraPink`。
- **高度**：240px，实测而非估算得出。`shell_scaffold_nav_test.dart` 新增的拖动区测试量出：macOS（48px 拖动区）场景下侧栏头部堆栈（拖动区+品牌行+账号区+分割线+分组标题）让第一个导航项中心落在 y=226；非 macOS（24px 拖动区）落在 y=202。240 在两种情形下都留出十几像素余量，让渐变确实"轻微探入"第一个导航项而不是刚好在头部边界切断——这也是"点击穿透渐变仍能选中导航项"测试要求有真实重叠区域才成立的前提。
- **透明度**：按环境皮肤的明暗分两档——`layoutAccentGradientMaxAlpha(Brightness)` 纯函数，深色皮肤（月靛）0.24、浅色皮肤（樱花薄暮）0.12。依据：同样饱和度的强调色叠在浅色皮肤上会显脏（周围没有足够深的底色吸收色相），需要更低的顶部不透明度。**这里比对的是环境皮肤本身的明暗**，不是 `artwork_overlay_skin.dart` 里的 `isLightBackdrop`——后者判断的是播放页封面背景经过 `brightness(1.5)` 提亮 + 24% 黑遮罩后的实际亮度，跟 shell 层的场景没有对应关系（shell 层的背景永远是环境皮肤的固定表面色，不存在"取决于封面亮度"的背景）。

## D. 侧栏底部空白

齐平化本身解决了这个问题：导航列表 `Expanded` 之后的空白就是 `DecoratedBox` 自身的通铺背景，跟上方连成一片，不再是悬浮面板边界内一块视觉上孤立的白色区域。本批不往里塞下载/装置入口——那是 v5.32.0（侧栏菜单重做）的范围。

## 顺带修复：v5.30.7 造成的访客登录回退

v5.30.7 按用户要求删除了设置页游客态的 Account 登录区块，理由是"侧栏账号区已经有入口了"。但 `_GuestSignInPrompt`（`exitGuestMode()` 在全 app 内唯一的调用点）只存在于 `_DesktopSidebar`，只在 ≥1200dp 渲染——窄于 1200dp 的访客从那时起就没有任何 UI 路径退出访客模式登录。

修法：设置页补回一个登录入口，判据用 `ShellChrome.of(context) == null`（只由 `_DesktopLayout` 提供，直接读"当前屏幕上方是否存在桌面侧栏祖先"），不用窗口宽度硬判——`ShellChrome` 本来就是为这类"某个祖先是否已经处理过某事"的场景设计的信号，用宽度阈值会引入第二份跟 `shell_scaffold.dart` 里实际断点脱节的判断逻辑。补回的入口渲染为一个普通 `ListTile`（图标 + `t.tapToSignIn` 文案 + 箭头），点击调用 `ref.read(authProvider.notifier).exitGuestMode()`，与侧栏账号区的登录入口共享同一个方法，不是重新实现一遍。

## 测试

基线 359 → 最终 **364**（净增 5）。

### `shell_scaffold_nav_test.dart`（净增 4）

- 新增 `desktopSidebarKey`/`desktopSidebarDragStripKey`/`layoutAccentGradientKey` 三个公开测试钩子（`shell_scaffold.dart` 顶层 `const`）——`_DesktopSidebar`/`_LayoutAccentGradient` 都是库私有类型，测试文件在另一个 library 里无法直接 `find.byType`，需要显式 Key 才能定位，做法与既有的 `MiniPlayerBar.contentKey` 一致。
- 「floats with a margin」测试整体替换为「sits flush against the window's top-left corner」——断言从 `greaterThan(0)` 反转为 `Offset.zero`。
- 「spans the window's full height」「no longer runs full-width beneath the sidebar」「selected pill sits inset」三个既有测试的 `find.byType(GlassPanel)` 全部换成 `find.byKey(desktopSidebarKey)`；高度断言从 `1000 - 8 - 8` 改为 `1000`（不再有外边距）。
- 新增「paints only a right-edge hairline」：直接读取 `DecoratedBox.decoration`，断言 `border.right.width > 0`、`top`/`left`/`bottom` 均为 `BorderSide.none`、`borderRadius`/`boxShadow` 均为空。
- 两个 macOS 贴边/圆角测试整体删除（断言的机制——`_macTitleRowTopInset`、`GlassPanel.borderRadiusOverride`——已经不存在），替换为两个拖动区测试：非 macOS 24px + 品牌行 `closeTo(24+24, 3)`；macOS 48px + 侧栏仍然贴边 `Offset.zero` + 品牌行 `closeTo(48+24, 3)`。两个测试都显式设置 `debugDefaultTargetPlatformOverride`（`TargetPlatform.windows`/`.macOS`）并在测试体末尾同步重置——测试运行器的默认平台不是任何一个桌面平台，`DesktopIntegration.isDesktop` 缺省是 `false`，不显式覆盖的话拖动区根本不会渲染。
- 新增「sidebar tiles still paint their selected background and ink after losing GlassPanel's built-in Material」：用 `startGesture` + `pump` 而非单纯 `tap`+`settle`，确保真的触发了 ink 飞溅的绘制帧（缺失 Material 祖先是在绘制时抛错，不是点击那一刻）。
- 新增两个渐变层测试：「spans both the sidebar and the content column」断言渐变矩形左上角在原点、宽度等于整窗宽度（1400）；「does not intercept clicks」动态遍历所有 `ListTile`，找到第一个「未选中且中心点落在渐变底边以上」的导航项再点击验证选中态转移——不写死具体是哪一项，因为账号区高度、`Divider` 默认高度等都不是这个测试应该硬编码的输入；找不到符合条件的项时测试本身失败并给出诊断信息（"渐变高度可能不够深"），而不是静默通过。用 macOS（拖动区最高、最难覆盖到导航项）作为测试平台，通过即代表其余桌面平台也通过。

### `settings_screen_test.dart`（净增 1，重构 2）

- 原「guest mode shows no Account section at all」测试的前提（裸 `MaterialApp(home: SettingsScreen())`，没有 `ShellChrome` 祖先）在新逻辑下应该**显示**登录入口，这是本次修复的直接目标，不是可以照旧的既有断言——整组重写为三个测试：
  - 「a signed-in user still sees the Account section...」不变（沿用原断言）。
  - 「guest mode with no ShellChrome ancestor ... shows its own entry point, and tapping it reaches exitGuestMode」：新增 `_SpyAuthNotifier`（覆写 `exitGuestMode()` 记录调用而非跑真实实现，避免测试依赖 `SharedPreferences` 在测试环境下的行为——那是 `exitGuestMode()` 自身的关注点，不是这个屏幕的），断言点击后 `exitGuestModeCalled == true`。
  - 「guest mode under a ShellChrome ancestor ... does not duplicate the sign-in entry point」：`home` 换成 `ShellChrome(reservesTrafficLightGutter: true, child: SettingsScreen())`，断言 Account 区块和登录行均不存在。
