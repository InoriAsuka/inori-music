# v5.38.0 — Windows 从没能播放过音频：接入第二个 `PlaybackEngine` 实现（media_kit/libmpv）

`just_audio` 0.9.x 只为 android/ios/macos/web 注册插件实现。Windows 上，`AudioPlayer` 的每一次方法调用都会直接抛 `MissingPluginException`——这不是回归，是这个应用从第一行 Windows 相关代码起就有的事实：Windows 客户端从来没有播放能力。

`lib/src/playback/playback_engine.dart` 的类文档其实早就写明了这一点：

> The immediate reason this exists is that Windows has no `just_audio` implementation at all, so the app cannot play there and never could. The fix is a different engine, not a patch to this one — and a swap is only cheap if the seam is already in place.

这句话是 v5.27.0（`PlaybackEngine` 接缝落地）写下的。四个版本过去了，接缝一直只有 `JustAudioEngine` 一个实现在用。本次任务：把 `media_kit`（Flutter 对 libmpv 的封装）接成第二个实现，选中 Windows 时启用。

## 这次真正的目标，比"Windows 能播放"更重要

一个只有一份实现的接口，从未被真正验证过是不是名副其实地"引擎无关"——它完全可能在哪里偷偷长成了唯一那个实现的形状，而没有第二个实现去戳破它。接上 `media_kit` 因此有两个同等重要的目的：

1. 让 Windows 能播放音频。
2. 逼出 `PlaybackEngine` 里那些"只因为目前只有一个引擎所以从没被检验过"的隐含假设。

第 2 点不是事后包装的说辞——逐个核对 `PlaybackEngine` 的每个方法在两个引擎下的真实语义后，确实找到了三处需要代码修正、一处已知但本次不修的 gap，记录在下面。

## 依赖：只加 Windows 音频包

`media_kit` 按平台 × 媒体类型拆分原生库分发：`media_kit_libs_video`（各平台视频+音频）、`media_kit_libs_audio`（各平台纯音频元包）、以及每个平台各自的 `media_kit_libs_<platform>_audio`/`_video` 包。本次只加：

```yaml
media_kit: ^1.2.6
media_kit_libs_windows_audio: ^1.0.9
```

`flutter pub add` 完成，没有手改 `pubspec.yaml`/`pubspec.lock`。特意不加的：

- `media_kit_libs_windows_video` — 这个应用不播视频。
- 任何 `media_kit_libs_macos_*`/`_linux_*`/`_android_*`/`_ios_*` — 这些平台继续用 `just_audio`，加了也不会被用到，只会让其余平台的构建体积和攻击面无端变大。

`flutter pub get` 自动同步了两个 Windows 生成文件（工具生成，非手改，`windows/.gitignore` 只忽略 `flutter/ephemeral/`，这两个文件本来就该入库）：

```diff
# windows/flutter/generated_plugins.cmake
 list(APPEND FLUTTER_PLUGIN_LIST
   connectivity_plus
   flutter_acrylic
   flutter_secure_storage_windows
   hotkey_manager_windows
+  media_kit_libs_windows_audio
   screen_retriever_windows
   ...
```

```diff
# windows/flutter/generated_plugin_registrant.cc
+#include <media_kit_libs_windows_audio/media_kit_libs_windows_audio_plugin_c_api.h>
...
+  MediaKitLibsWindowsAudioPluginCApiRegisterWithRegistrar(
+      registry->GetRegistrarForPlugin("MediaKitLibsWindowsAudioPluginCApi"));
```

`media_kit` 核心包本身没有原生插件注册（它是纯 Dart + FFI 直连 libmpv），只有 `media_kit_libs_windows_audio` 这个"打包 mpv 动态库"的包需要注册——这也是 macOS/Linux/Android/iOS 三个生成文件完全没有变化的原因，`flutter pub get` 只会为真正声明了该平台原生代码的包生成注册项。

## 引擎选择抽成纯函数

`main.dart` 原来只有一行 `final engine = JustAudioEngine.create();`，没有平台分支。新增 `lib/src/playback/engine_selection.dart`：

```dart
enum EngineKind { justAudio, mediaKit }

EngineKind choosePlaybackEngineKind(String operatingSystem) =>
    operatingSystem == 'windows' ? EngineKind.mediaKit : EngineKind.justAudio;
```

这个文件故意零 import（连 `playback_engine.dart` 都不 import）——纯到只是一个字符串进、一个枚举出的函数，`test/engine_selection_test.dart` 因此完全不需要伪造 `dart:io` 或起任何 Flutter binding 就能断言"Windows 选 media_kit，其余四个平台（macOS/Linux/Android/iOS）选 just_audio，未知平台字符串也不抛异常、落到 just_audio"。`main()` 是唯一读取 `Platform.operatingSystem` 的地方，也是唯一调用这个函数的地方：

```dart
final PlaybackEngine engine =
    switch (choosePlaybackEngineKind(Platform.operatingSystem)) {
      EngineKind.mediaKit => MediaKitEngine.create(),
      EngineKind.justAudio => JustAudioEngine.create(),
    };
```

`MediaKit.ensureInitialized()`（定位并加载 libmpv 原生库）被放进 `MediaKitEngine.create()` 内部而不是 `main()` 里，和 `JustAudioEngine.create()` 自己处理 Android-only 均衡器构造是同一个原则：每个工厂方法自己负责只在自己会被调用的那个平台上才成立的初始化，`main()` 不需要知道任何一个引擎的内部细节。

## 发现的接口泄漏点

逐一核对 `PlaybackEngine` 每个方法在 `media_kit` 下的真实语义时（直接读了 `~/.pub-cache/hosted/pub.dev/media_kit-1.2.6` 的源码，不是只看 pub.dev 文档），找到三处接口文档从没写清楚、恰好被 `just_audio` 的具体行为掩盖了的假设。

### 1. `setVolume` 的取值范围从未写明

`PlaybackEngine.setVolume(double volume)` 原来的签名没有任何取值范围说明。`just_audio` 原生就是 0.0–1.0，`PlayerNotifier._applyVolumeWithGain` 也确实是按 0.0–1.0 在 clamp 和调用。`media_kit`/libmpv 原生范围是 **0–100**（`Player.setVolume` 自己的文档："Defaults to `100.0`"）。如果直接把 App 算出来的 0.0–1.0 透传给 `media_kit`，不会报错——它就是个合法的 volume 值——只是每首歌都会被放到几乎听不见的音量。这种"不抛异常、只是错"的 bug 在 Windows 构建里几乎不可能被人在测试阶段意外发现。

修复两处：

- `playback_engine.dart` 的 `setVolume` 加一句文档，把范围钉死为 0.0–1.0，并点名 `media_kit` 是不同范围的先例。
- `MediaKitEngine.setVolume`：`_player.setVolume(volume.clamp(0.0, 1.0) * 100)`。

### 2. `durationStream`/`duration` 的 `null` 语义

`just_audio` 用 `null` 表示"时长未知"（源文件还没解析出元数据）。`media_kit` 的 `PlayerState.duration` 类型是不可空的 `Duration`，默认值 `Duration.zero`，从元数据到达前的这段时间里就是"真实的零"，不是"未知"。`PlayerNotifier._setupPlayerListeners` 的监听器写法是：

```dart
_engine.durationStream.listen((dur) {
  if (dur != null) state = state.copyWith(duration: dur);
});
```

如果把 `media_kit` 的 `Duration.zero` 直接当 `Duration?` 透传（Dart 允许，`Stream<Duration>` 是 `Stream<Duration?>` 的子类型），`dur != null` 恒真，每次切歌都会先把总时长显示成 `0:00`，闪一下才跳到真实值——现实中没有真正零时长的音轨，所以 `MediaKitEngine` 把 `Duration.zero` 折算回 `null`，还原接口原本想表达的"未知"语义：

```dart
static Duration? _nullIfZero(Duration d) => d == Duration.zero ? null : d;
```

### 3. `seekToIndex` 隐含的播放状态契约

读 `media_kit` 原生实现 `real.dart` 的 `jump()`：

```dart
Future<void> jump(int index, {bool synchronized = true}) {
  Future<void> function() async {
    ...
    await play(synchronized: false);
    await _setPropertyInt64('playlist-pos', index);
  }
  ...
}
```

`jump()` 内部会先调用 `play()` 再移动播放位置。而 `JustAudioEngine.seekToIndex` 是 `_player.seek(Duration.zero, index: index)`——只改位置，不动播放/暂停状态。`PlaybackEngine.seekToIndex` 自己的文档只写了"Jump to a queue position"，对播放状态该怎么处理只字未提——因为写这句文档的时候，世界上只有一个引擎，这个引擎凑巧不会有这个副作用，没人需要去想这件事。

不处理的话：用户在 Windows 上暂停时点"下一首"（`PlayerNotifier.next()`/`previous()` 都是直接调 `seekToIndex`），音频会自己恢复播放——这是一个只在 Windows 构建上才会出现、且完全不在任何人预期之内的行为差异。`MediaKitEngine.seekToIndex` 记录跳转前的播放状态，跳转后如果原本是暂停就补一次 `pause()`：

```dart
Future<void> seekToIndex(int index) async {
  final wasPlaying = _player.state.playing;
  await _player.jump(index);
  if (!wasPlaying) await _player.pause();
}
```

### 4.（已知但本次不修）`crossfadeSeconds` 是裸 setter，且滑块 UI 本身也没有能力位门控

`CrossfadeNotifier.setSeconds`/`_restore` 都是无条件调用 `ref.read(playbackEngineProvider).crossfadeSeconds = clamped`，不像均衡器那样先判空。往上一层查到 `settings_screen.dart` 的"切歌淡入淡出"滑块本身：

```dart
Consumer(
  builder: (context, ref, _) {
    final seconds = ref.watch(crossfadeProvider);
    return ListTile(
      ...
      subtitle: Column(children: [
        Text(seconds == 0 ? '关闭' : '$seconds 秒'),
        Slider(value: seconds.toDouble(), ..., onChanged: (v) => ...),
      ]),
    );
  },
),
```

——完全没有读 `playbackCapabilitiesProvider`。这与均衡器区块（`_EqSection`，`settings_screen.dart:1034`）和侧栏输出设备入口（`shell_scaffold.dart:946`）形成了直接对比：那两处都严格按能力位门控，crossfade 滑块从 v5.27.0 引入至今都没有。四个版本以来只有一个引擎、且那个引擎恰好支持 crossfade，这个 gap 完全没有暴露的机会——用户在 Windows 上会看到一个能拖动、数字会变、但底层什么也不会发生的滑块。

`MediaKitEngine` 端把 `crossfadeSeconds` 实现成显式的空 setter（接受赋值、不抛异常、不做任何事），并在代码注释里写清楚为什么：这是唯一能让 `CrossfadeNotifier` 现有的无条件调用不炸的做法。但 UI 层的门控缺口本身不在这次改动范围内——是否要给这个滑块加能力位门控、还是走另一套"禁用态"视觉，需要单独决定，如实报告，留作后续。

## 接口空缺：输出设备三件套（不是引擎限制）

`PlaybackCapabilities` 早就声明了 `outputDeviceSelection`/`exclusiveOutput`/`outputFormatControl` 三个字段，`shell_scaffold.dart:946` 的侧栏"输出设备"入口就是照这三个字段中的第一个门控的：

```dart
final canSelectOutputDevice = ref.watch(
  playbackCapabilitiesProvider.select((c) => c.outputDeviceSelection),
);
...
if (canSelectOutputDevice)
  _SidebarBottomEntry(icon: Icons.speaker_outlined, label: t.outputDevice, ...),
```

libmpv 三者都真的支持——`audio-device`/`audio-device-list`（枚举 + 选择输出设备）、`--audio-exclusive`（WASAPI 独占/hog 模式）、`--audio-format`/`--audio-samplerate`（采样格式控制）都是真实存在的 mpv 选项，`media_kit` 的 `Player.setAudioDevice(AudioDevice)`/`state.audioDevices` 也确实把设备枚举和选择暴露出来了。

**但 `PlaybackEngine` 接口本身没有任何方法可以把这件事说出来**——三个能力位从 v5.27.0 起就只是声明，从来没有配套的"枚举设备"/"选择设备"方法给引擎去实现。如果这次顺手把 `outputDeviceSelection` 翻成 `true`，`shell_scaffold.dart` 的侧栏入口会立刻出现，但点了以后除了跳到设置页什么也做不了（现有的 `onTap: () => context.go(AppRoutes.settings)` 只是一个占位跳转，设置页里根本没有对应的设备选择器）——这正是本仓库最近几个版本一直在到处修的"死入口"形状（参见 `silent-failure-pattern` 系列问题）。

三个能力位继续诚实报 `false`，`media_kit_engine.dart` 里用一整段注释把"这是接口跟不上，不是 libmpv 做不到"钉死。设备选择——枚举/选择 API 本身、以及配套的选择器 UI——留作独立的后续 phase。

## 范围决定

- **只有 Windows 换引擎**。macOS/Linux/Android/iOS 的 `JustAudioEngine` 一行没动（`just_audio_engine.dart` 唯一的改动是删掉零调用的 `rawPlayer`，见下）——macOS 播放能力刚在 v5.37.0/v5.37.1/v5.37.2 三个版本里从彻底不可用修到正常，这个时间点没有理由去动它的引擎选择路径。
- **不加"选择播放引擎"的用户设置**。引擎完全由平台决定，用户没有切换的必要也没有入口。
- **crossfade 与均衡器在 `media_kit` 上都诚实报不支持**：`capabilities.crossfade`/`capabilities.equalizer` 均为 `false`，`equalizer` getter 返回 `null`。两者都是自研 Rust/Symphonia 引擎落地时最可能被整体推倒重做的部分——`JustAudioEngine` 的 crossfade 本身也只是手搓的音量渐变（不是 `just_audio` 原生能力），没有必要在一个明确说了是过渡方案的引擎上复刻同一套手搓逻辑。

## 顺带删除死代码

`JustAudioEngine.rawPlayer`（`just_audio_engine.dart:65`）的文档声称"for the audio_service bridge and the Android equalizer only"。`grep -rn "rawPlayer" lib/ test/` 核实为零调用——`InoriAudioHandler` 早在 v5.27.0 就已经完全脱耦到只依赖 `PlaybackEngine`，这句文档描述的用途从一开始就不存在（或者说,存在过但在 v5.27.0 重构时已经清空,文档没有跟着更新)。删除后重新跑 `flutter analyze`/`flutter test` 确认没有任何隐藏调用点，两者都通过。

- **`test/playback_boundary_test.dart`**：`_engineImplementations` 加入 `lib/src/playback/media_kit_engine.dart`；新增一条与 just_audio 版本完全对称的测试，断言除 `media_kit_engine.dart` 外没有任何 `lib/` 文件 `import 'package:media_kit/'`。原测试自己的注释就写着"加引擎要在这里加文件，而不是放松规则"——这条新测试就是照做。
- **`test/engine_selection_test.dart`**（3 条）：Windows → media_kit；macOS/Linux/Android/iOS/Fuchsia → just_audio；未识别的平台字符串不抛异常、落到 just_audio（防的是未来 `dart:io` 报出一个这里没预料到的字符串时变成一次运行时崩溃而不是静默走安全默认值）。
- **`test/media_kit_engine_capabilities_test.dart`**（1 条）：`MediaKitEngine` 的构造函数会真的创建一个 `Player()`，进而触发 libmpv 原生库加载——本机是 macOS 且只打包了 Windows 的 libmpv，真实实例化在本机必然失败（这也是"Windows 播放本身无法在本机验证"的直接原因之一）。因此 `capabilities` 被拆成模块顶层常量 `mediaKitCapabilities`，测试直接对这个常量断言，不实例化引擎——依然是对真实生产代码的断言（`import` 的是 `media_kit_engine.dart` 本体），不是照抄一份影子常量做的空对空测试。

## 未做 / 已知限制

- **Windows 播放本身完全无法在本机验证**。本机是 macOS，只有 Command Line Tools，没有完整 Xcode 也没有 Windows 环境；`media_kit`/libmpv 的真实播放行为、原生库加载、`jump()`/`setShuffle()` 等方法在真实 mpv 上的确切行为，都是依据 `media_kit` 1.2.6 包自身源码（本机 `~/.pub-cache` 内完整可读，已逐一核实关键路径，不是只凭 pub.dev 文档推测）与官方文档得出的，但没有任何一次真实跑通过 Windows 构建。这次改动能做到的最大程度是"逻辑上自洽、有真实源码依据、有静态测试兜底"，发布后的真实播放验证只能交给用户在 CI 构建产物上完成。
- **crossfade 滑块的能力位门控缺口**（见上文"发现的接口泄漏点 4"）本次如实报告、未修。
- **输出设备选择**——枚举/选择 API 本身、以及配套的选择器 UI——是独立的后续 phase（见上文"接口空缺"一节）。
- iOS ATS 拦播放（v5.36.0 记录）仍未修。
- 专辑封面入库缺口（v5.37.1 记录，划归 v6 媒体摄取）仍未做。
