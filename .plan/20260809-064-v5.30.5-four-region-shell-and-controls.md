# v5.30.5 — 桌面四区布局 + 播放控制条补齐 + Cover Flow 顶栏入口 + macOS 红绿灯让位修复

（2026-08-09）」一节里的「Phase v5.30.5」。同一节拆出的「Phase v5.30.6」（macOS 工具栏高度统一、

## 背景

用户给了四张 v5.30.0 实机截图：红绿灯位置和圆角违和；悬浮立体效果跟苹果差一截；主界面布局应该
按红框摆（侧栏贯穿全高、右列三段）而不是当时"侧栏悬浮但仍与全宽播放条共享一个 `Column`"的形状；
播放控制区缺音量/随机/循环；Cover Flow 没有显示出来。第 1、2 条里的材质/阴影/工具栏高度留给
v5.30.6，但第 1 条里的红绿灯让位坐标 bug 属于本 phase——诊断下来它不是审美问题，是坐标钉错了地方。

## A. `_DesktopLayout` 从"两行"改成"两列"

原来：

```dart
Column[
  Expanded(Row[侧栏(padding 8, width 220), Expanded(内容)]),
  播放条,  // 全宽，铺在侧栏正下方
]
```

侧栏和内容共享一个 `Row`，播放条在外层 `Column` 独占最后一行、横跨全宽——侧栏的可用高度因此
是"窗口高度 − 播放条高度"，永远比窗口矮一截，播放条也永远铺到侧栏下方去。

改成：

```dart
Row[
  侧栏(padding 8, width 220, 全高),
  Expanded(ShellChrome(child: Column[Expanded(内容), 播放条])),
]
```

播放条现在嵌进右列自己的 `Column`，只占内容列宽度；侧栏的 `Padding(8,8,8,8)` 外边距直接由窗口
高度决定，不再被"减去播放条高度"这一步吃掉。`ShellChrome` 见 E 节。

只改 `_DesktopLayout`（≥1200dp）；`_TabletLayout`/`_MobileLayout` 未动，仍是全宽播放条。

## B. 曲目信息块搬到侧栏底部

`MiniPlayerBar` 新增 `showNowPlaying`（默认 `true`）。为 `true` 时行为跟改动前逐位相同（既有
测试全部原样通过，没有跟着调）；为 `false`（桌面播放条传入）时第 1 段（封面+标题/艺术家）不
渲染，换成随机/循环按钮。

原来私有的 `_MiniPlayerArtwork` 提升为公开的 `MiniPlayerArtwork`——现在被侧栏和播放条两处复用。
新增 `SidebarNowPlaying`（同文件）：封面 + 标题/艺术家，点击 `context.push(AppRoutes.player)`，
跟播放条原来那层 `InkWell` 行为一致。钉在 `_DesktopSidebar` 的 `Column` 底部，`Expanded(ListView)`
之后再补一条 `Divider`，跟 `_AccountBlock` 上下已有的分隔处理保持同一套语汇。

## C. 播放条补齐控件

目标布局（不显示曲目信息后腾出的空间）：

```
[进度条]
[随机 循环]  ...  [上一首 播放/暂停 下一首]  ...  [音量 睡眠定时器 队列]
```

- **随机/循环**：从 `full_player_screen.dart` 的内联代码抽成共享 widget `RepeatModeButton` /
  `ShuffleButton`（新文件 `lib/src/player/playback_mode_buttons.dart`）。两处调用同一份状态机
  （`none→all→one→none` 循环、`shuffle` 布尔翻转），播放页原有实现原样迁移，不是重写。
- **音量**：`PlayerNotifier.setVolume`/`PlayerState.volume` 早就存在，UI 从来没接过。新文件
  `lib/src/player/volume_control.dart`：
  - `VolumeControl`——喇叭图标（按音量分三档 `volume_off`/`volume_down`/`volume_up`）+ 90px
    横向 `Slider`；点图标切静音、再点恢复。
  - `volumeBeforeMuteProvider`——记住静音前音量的 `StateProvider`，**跨 widget 共享**而不是每个
    `VolumeControl` 实例自己的本地 `State`：播放条和播放页各挂一份独立实例，静音记忆若各自为政，
    从一边静音、另一边恢复就会对不上（已用两个 `VolumeControl` 实例的往返测试验证）。
  - `compact: true` 时收成纯图标 + `showMenu` 弹出同一套控件。播放页固定用这个形态——那一行宽度
    是精算过的 `playerControlWidth`（v5.29.0 的产物），硬塞一条 90px 滑条正是历史上撞过墙的那类
    加法，不值得为音量控件重新校准那套指标。
  - 播放条右段自己的宽度低于阈值时也会自动收成 `compact`——判断基准是**该分区 `LayoutBuilder`
    量出的实际宽度**，不是窗口宽度。
- **队列入口**：桌面没有独立于 `FullPlayerScreen` 之外的队列 UI（`_QueueList` 只挂在播放页自己
  的侧栏面板 / 底部弹层里），新按钮直接跳 `AppRoutes.player`，没有为此再搭一套队列视图。

### 阈值校准过程（务必记录，不是拍脑袋定的数）

第一版把 `_volumeCompactThreshold` 定成 200，`test/mini_player_bar_desktop_test.dart` 在把播放条
分区宽度实测钉到 600px 时炸出 `RenderFlex overflowed by 26 pixels`：600px 分区宽度换算出的右段
分配宽度是 208px——**大于** 200（不触发收起）但**小于**展开态实际需要的 234px（3 个默认 48px
`IconButton` + 90px 滑条，行内没有额外间距），落进一段"判定为不用收、但确实放不下"的真实溢出
区间。改成 240（略高于实测的 234），同一个测试转为验证"分区收窄到 600px 时正确收起、且不再
溢出"。窗口宽度 1200（`_DesktopLayout` 生效的下限）换算出的播放条分区宽度约 964px，无论展开还是
收起态都远超所需，因此这条收起路径在当前断点下更多是防御性设计，不是日常会命中的分支——但既然
写了就要经得起实测，不能只停留在"看起来应该够用"。

## D. Cover Flow 门控验证：门控本身没有问题

按计划要求，先写测试证伪、测试通过再确认问题只是入口问题：`test/full_player_layout_test.dart`
里 v5.30.0 就有的三条门控测试（开关开+队列 4 首+宽窗 → 出现；单曲目即使开着也回退；开关关着
不出现）本次原样跑通，**没有改动 `canSplit && ref.watch(coverFlowModeProvider) &&
state.queue.length > 1` 这行判断或 `_splitBreakpoint`**。

真正的问题是入口太深——此前只有 Settings → 外观里一个开关，跟播放页本身隔着好几次导航。在播放页
顶栏加了一个并排图标（`Icons.view_carousel_outlined`，跟歌词/队列切换按钮同一行），读写同一个
`coverFlowModeProvider`；Settings 里的开关保留，仍是持久化来源，不重复实现一份开关状态。新增
端到端测试：关闭状态点按钮 → `CoverFlowArtwork` 出现 → 再点一次 → 消失，证明按钮确实接上了这个
provider。

## E. 红绿灯让位坐标修复

**根因**：`DesktopAppBar`/`DesktopSliverAppBar` 里 `EdgeInsets.only(left: 70)` 此前无条件对 macOS
生效。v5.30.0 把侧栏改成悬浮面板后，窗口左上角实际归侧栏所有，但这 70px 还留在内容区的
`AppBar` 上（该 `AppBar` 在桌面 shell 内只会渲染在 x ≥ 236 处，本来就撞不到红绿灯）——两边各管
各的，谁都没有真的把空间让给红绿灯，红绿灯因此直接压在侧栏的圆角和 "Inori Music" 字样上。

**修复**：

1. 新增 `ShellChrome`（`lib/src/shared/widgets/shell_chrome.dart`）：只携带一个
   `reservesTrafficLightGutter` 布尔值的 `InheritedWidget`，由 `_DesktopLayout` 包在内容列外面
   （见 A 节代码）。`DesktopAppBar`/`DesktopSliverAppBar` 读到这个祖先且值为真时跳过 70px 让位；
   读不到时（登录页 `gate_window_chrome.dart` 独立处理、全屏播放页 `full_player_screen.dart` 自己
   的 `_needsMacTrafficLightGutter` 逻辑——两者都不在桌面 shell 里、没有侧栏在旁边）保留原行为。
   没有用窗口宽度做判断——那是这个仓库已经栽过两次的基准错位类型。
2. `_DesktopSidebar` 接过真正的让位职责：标题行（`InoriMark` + "Inori Music"）顶部内边距在
   macOS + 自绘标题栏（`!systemTitleBarProvider`）下从 24 提到 30，非 mac 或用户选了系统标题栏
   时维持 24（渲染不变）。数值推算：macOS 红绿灯距窗左 20pt 起、按钮 12pt 直径、20pt 中心距、
   垂直中心约 y=20pt——底边落在窗口坐标 y=20+12/2=26；侧栏面板本身在 `_DesktopLayout` 里就有
   8px 外边距，窗口坐标 y=26 换算到面板局部坐标只有 26-8=18px，紧到标题行文字的大写字高会直接
   贴着红绿灯下沿而不是明显留白——这才是截图里"挤"的观感来源，不是字面意义上的像素重叠。30
   在这基础上留出大约一个按钮半径的呼吸间距。
3. 这段留白同时包了一层 `DragToMoveArea`（`needsTrafficLightGutter` 为真时）——此前侧栏完全没有
   可拖动区域，全靠内容区那条 `DesktopAppBar`；现在跟 Apple Music 一样，侧栏顶部空白也能拖动
   整个窗口。只在触发让位的同一个 mac 分支生效，没有扩大到 Windows/Linux（见下方"实现说明"）。

只动 macOS 分支：Windows/Linux 侧栏顶部内边距维持 24（未变），`DesktopAppBar`/
`DesktopSliverAppBar` 在两个平台上的窗口按钮/拖动区域渲染路径未改动，靠新增测试守住
（`ShellChrome` 祖先存在/不存在两种情况 × macOS/非 macOS）。

## 实现说明（非偏离，供复核）

- **`DragToMoveArea` 只加在 macOS 分支**：计划原文把它写在 macOS 让位那一段里，随后又说"只动
  macOS 分支，Windows/Linux/移动端渲染必须无变化"。按此从紧解读——Windows/Linux 侧栏顶部维持
  原来的不可拖动状态，没有借这次顺手把它们也变成可拖动区域。如果本意是三个桌面平台都要能拖，
  这里需要用户确认后再补。
- **新增的音量/队列/Cover Flow 提示文案（`'Volume'`/`'Mute'`/`'Unmute'`/`'Queue'`/`'Cover
  Flow'`）沿用硬编码英文**，跟这一行其余按钮（`'Sleep timer'`/`'Favorite'`/`'Karaoke'` 等）已有
  的写法保持一致，没有新增 l10n key。这不同于 v5.29.0 对 `'Now Playing'` 的处理——那是**可见的
  标题文字**且 l10n key 早已存在只是没接上；这里是新控件的悬浮提示，且没有现成 key，跟这一行
  其余按钮的既有约定一致，判断不属于同一类问题。
- **30px 顶部让位是几何常量推算值，不是真机像素校验值**——见 E 节推算过程。这条数值请用户在真实
  macOS 设备上重点复核，跟 Safari/Apple Music 的侧栏顶部比对一下松紧。
