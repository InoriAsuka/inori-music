# v5.30.6 — 播放条曲目信息回迁 + 本地封面修复 + 进度条重做 + 悬浮阴影

## 背景

用户实机验证 v5.30.5 后给了三条反馈：

1. 专辑封面需要跟音乐控制块一起——否掉了 v5.30.5 把封面钉到侧栏底部的解读。
2. 本地曲库的曲目在播放条里封面不显示（列表里正常）。
3. 时间条样式需要优化，"太丑了"。

外加上一轮遗留的"悬浮立体感跟苹果差一节"。四件事一次处理完，其中第 1 件是**回退 v5.30.5 的一个
决策**，不是新需求；第 2 件是**真 bug**，优先级最高。

## A. 曲目信息块搬回播放条

v5.30.5 把封面+标题钉在侧栏底部（`SidebarNowPlaying`），依据是对用户红框的解读——这个解读错了。

- 桌面布局改回播放条自带曲目信息：`_ShellScaffoldState.build()` 里桌面/移动端/平板三个布局分支
  现在共用同一个 `const MiniPlayerBar()`，不再有单独的 `desktopBottomBar` 变量。
- `SidebarNowPlaying` 从 `_DesktopSidebar` 里移除后**没有任何调用点**，判断是删干净：连同它的类
  定义、测试断言一并删除，不留死代码。`_DesktopSidebar` 的 `Column` 收尾恢复到
  `Expanded(ListView(children: rows))`，跟 v5.30.0（v5.30.5 之前）的形状一致。
- `_DesktopLayout` 的四区布局（侧栏贯穿全高、播放条只占右列）**没有改动**——用户只否掉了信息块的
  位置，没否掉布局本身。
- `shell_scaffold_nav_test.dart` 里 v5.30.5 加的两条测试反过来断言：原来验证"侧栏底部有曲目信息、
  播放条没有"的用例，改成验证"播放条有曲目信息、侧栏没有"；原来"点侧栏曲目信息块跳播放页"的用例，
  改成"点播放条自己的曲目信息区跳播放页"。

## B. 修复本地曲库封面不显示（真 bug）

根因：`MiniPlayerArtwork` 只接 `albumId`，走 `artworkUrlProvider` 拿服务端封面 URL；本地曲库的曲目
没有 `albumId`（`PlayerNotifier._makeMediaItem` 给服务端曲目的 `extras` 里塞 `albumId`，给本地曲目
的 `extras` 里只有 `trackId`），它们的封面是从文件里抽出来的内嵌图，存在 `MediaItem.artUri` 这个
`file://` URI 里。游客模式下播放条封面因此永远是占位图标，即使同一首歌在列表行（直接读本地库）
里封面正常。

`full_player_screen.dart` 的 `_FullPlayerArtwork` 早就有正确的取图优先级（`localArtUri` 且
scheme 是 `file` 时走 `Image.file`，否则退回 `artworkUrlProvider`，都没有则占位），只是这段逻辑从
没同步到 `MiniPlayerArtwork`。

新增共享 widget `TrackArtwork`（`lib/src/player/track_artwork.dart`），把"选源 + 处理加载/错误态"
这段完全相同的逻辑收成一份，`_FullPlayerArtwork` 与 `MiniPlayerArtwork` 都改为委托给它：

- `TrackArtwork` 只负责产出图片内容本身（或调用方传入的 `fallback` 构建器），不管外层容器。
- `_FullPlayerArtwork` 保留自己原来的裸 `ClipRRect` + 80px 大图标占位（`_ArtworkFallback`）。
- `MiniPlayerArtwork` 保留自己原来带背景色的圆角方块容器，新增 `localArtUri` 参数，内部委托给
  `TrackArtwork`，`fallback` 传入按比例缩放的小图标。

两者的外层装饰（容器、圆角、占位图标大小）本来就不一样，没有为了"抽成一个 widget"硬凑成同一种
视觉；真正相同的只有"该走哪个数据源"这一段，也只共享了这一段。

`MiniPlayerBar` 的调用点（新的共享函数 `_nowPlayingInfo`）现在把 `mediaItem?.artUri` 传给
`MiniPlayerArtwork` 的 `localArtUri`。

## C. 进度条与时间显示重做

只重做桌面宽播放条；窄播放条（手机、较窄平板）原样保留，见下一节。

两张参考截图的取舍：进度条位置学参考图 A（传输键下方居中的第二行，两端各一个时间标签），不学
参考图 B（顶部通栏——那正是现状被吐槽"丑"的形状）。

宽播放条中段变成两行：

```
[随机][上一首][ ▶ ][下一首][循环]
00:02 ─────────●───────── 05:55
```

- 删掉顶部那条通栏细线（`_MiniPlayerProgressBar`），新增 `_MiniPlayerSeekRow` 放进中段第二行，跟
  上面传输键行共享同一个 `SizedBox(width: _transportBlockWidth)`，保证"同宽同轴"——没有用
  `IntrinsicWidth` 之类的度量技巧，两行本就该等宽的东西直接放进同一个已知宽度的容器里更可靠。
- 时间标签：`mm:ss`，超过一小时 `h:mm:ss`；`FontFeature.tabularFigures()` 等宽数字，避免秒数跳动
  时整行左右抖。
- 轨道加粗到 4px；inactive 轨道从 `outline`（读起来像描边色）改成低透明度的 `onSurfaceVariant`
  （真正的"前景色"）；active 轨道对 `sakuraPink` 做轻度降饱和（`HSLColor` 调 `saturation` 后转回
  `Color`），跟播放/暂停键的满饱和强调色区分开——两张参考图的轨道都不是纯高饱和色。
- 滑块默认隐藏（`enabledThumbRadius: 0`），hover（`MouseRegion`）或拖拽时才出现
  （`enabledThumbRadius: 7`）——两张参考图都是这个处理。
- 随机/循环从播放条最左边（v5.30.5 的位置）归位到传输键两侧，跟两张参考图一致：
  `[随机][上一首][播放][下一首][循环]` 连成一组。
- 播放/暂停键改成 `sakuraPink` 实心圆 + 白色图标，跟 `full_player_screen.dart` 已有的播放键
  同一套装饰；白色前景沿用该按钮已有的做法和 `FilledButtonTheme` 的
  `foregroundColor: Colors.white` 约定，没有另外计算对比色。

## 移除 `showNowPlaying`，改成按播放条自身测到的宽度分流

v5.30.5 引入的 `MiniPlayerBar.showNowPlaying` 布尔值原本用来区分"桌面：隐藏封面、腾地方放随机/
循环+音量/队列"和"移动端/平板：保留封面"。A 节把封面在所有布局下都改回常驻后，这个开关唯一的历史
职责消失了——桌面和移动端/平板此后永远传同一个值，`false` 分支变成生产代码永远不会触发的死路径。
按照"不留死代码"的同一个判断标准（跟 `SidebarNowPlaying` 一样的判断依据），直接删掉了这个参数。

替代方案：`MiniPlayerBar.build()` 用 `LayoutBuilder` 量出播放条自己的实际宽度（不是
`MediaQuery.sizeOf(context).width`），按 `_wideBreakpoint`（640px）分流：

- **宽播放条**（≥640px，覆盖桌面 shell 的内容列宽度，也覆盖足够宽的平板横屏）：C 节的两行中段 +
  随机/循环 + 音量/队列一起出现。
- **窄播放条**（手机、较窄平板）：保留 v5.30.6 之前的单行形状——封面+标题 | 上一首/播放/下一首 |
  睡眠定时器，连同原来那条通栏细进度条（`_MiniPlayerProgressBar`）一起**原样不动**。用户原话"窄
  宽度下保留一条简化的进度表现即可"最贴切的读法是"保留现有那条"，不是另做第三种形状；这也是本次
  改动里风险最低的选择——窄播放条的代码路径完全没有改写。

这个决定跟计划原文字面（"桌面布局改回 `MiniPlayerBar(showNowPlaying: true)`"）不完全一致——计划
原文暗示保留参数、只改调用点的值。可见结果（桌面播放条重新带封面）完全达到了计划要求，只是机制从
"标志位"换成了"实测宽度"，见下面"实现说明"一节。

### 阈值校准（抓到一次真实溢出）

`_transportBlockWidth`（宽播放条传输键行 + 进度行共享的宽度）第一版估成 232px，`flutter test`
在默认测试视口（约 800 逻辑像素宽，落进宽播放条区间）下直接炸出
`RenderFlex overflowed by 8.0 pixels`——五按钮组（随机/上一首/播放/下一首/循环）实际需要 240px。
调到 248px（比精确值多留 8px 余量，跟 `_volumeCompactThreshold` 的 240（比实测 234 多留 6px）
同一个风格）后，在 375 / 700 / 900 / 964 四档宽度下都不再溢出，用
`test/mini_player_bar_desktop_test.dart` 的多档宽度测试钉住。

`_wideBreakpoint` 定在 640px：小于移动端 shell 的最大宽度上限（<600 才会进桌面/平板判断），大于
宽播放条实际渲染所需的最小宽度，两头都留了余量，用 375dp（手机）和 964px（1200dp 桌面窗口换算出
的播放条实际宽度）两个边界场景验证。

## D. 悬浮阴影改用显式两层 BoxShadow

`mini_player_bar.dart` 的 `Material(elevation: 8)` 和 `GlassPanel`（侧栏、播放页控制面板/侧面板
公用同一个组件）都换成新 helper `floatingShadow()`（`lib/src/shared/widgets/floating_shadow.dart`）：

- 两层：一层贴边紧阴影（模糊半径 10、y 偏移 3）+ 一层大而淡的扩散（模糊半径 28、y 偏移 8，落在
  Apple 参考的 24–32 模糊 / 4–8 偏移区间内）。单层 `BoxShadow` 没法同时做到"贴边有实感"和"扩散
  发软"——模糊大到发软的程度贴着边缘反而看不出来，模糊小到贴边有实感的程度又不会扩散。
- 阴影颜色读皮肤已有的 `SkinColors.miniPlayerShadow` token，而不是写死黑色：樱花薄暮（浅色皮肤）
  的 token 是低透明度（约 15%）暗梅色，本来就落在参考的 0.10–0.18 透明度区间；月靛（深色皮肤）的
  token 是更高透明度（40%）纯黑——深色地面需要更强的阴影才压得住，这个差异是皮肤作者原本就调好
  的。两层阴影的透明度都按这个 token 自身的透明度等比例缩放（乘 1.3 和 0.75 两个系数），而不是
  给所有皮肤共用一个绝对透明度常量。
- 层级坑：`GlassPanel` 内部是 `ClipRRect(BackdropFilter(Material(...)))`，`ClipRRect` 会把画在它
  里面的阴影直接裁掉，阴影必须包在 `ClipRRect` 外面的容器上。这个仓库自己的
  `login_screen.dart` 的 `_GlassCard` 早就用过"外层 `Container` 扛阴影、内层 `ClipRRect` 扛模糊"
  这个写法（单层版本）——这次是把它推广成两层 helper，`GlassPanel` 和 `MiniPlayerBar` 都改用
  这个 helper 而不是各自重复实现。

只改阴影/景深，没有动 macOS 工具栏高度、vibrancy 材质、失焦态红绿灯变灰——那些留给后续 phase。

## 实现说明（非偏离，供复核）

- **`showNowPlaying` 参数的删除是主动简化，不是对计划的偏离**：计划原文的字面指令
  （"桌面布局改回 `MiniPlayerBar(showNowPlaying: true)`"）暗示参数本身继续存在。实现时判断继续
  保留它会立刻产生一个只有一个可能取值、`false` 分支永远不可达的参数——这跟计划里对
  `SidebarNowPlaying` 明确要求的"没有调用点就删干净、别留死代码"是同一类判断，因此把它一并应用到
  了这个参数上。可见的最终效果（桌面播放条重新带封面+标题）跟计划要求完全一致；用宽度分流替代
  标志位分流，也跟"通用注意"里反复强调的"用区域实际宽度判断，不用外部标志/窗口宽度"一致。
- **窄播放条的进度条样式完全没有改动**：C 节列出的所有新样式（时间标签、4px 轨道、降饱和、
  hover 缩放缩略）只应用在宽播放条的 `_MiniPlayerSeekRow` 上；窄播放条的 `_MiniPlayerProgressBar`
  是 v5.30.6 之前的原始代码，一行没改。这是本次唯一一处"用户反馈的丑陋样式在某个分支下没有直接
  修"的地方，原因见上面"窄播放条原样保留"一节——两张参考截图都是宽屏桌面播放器，用户的"太丑"反馈
  在语境上也是针对桌面播放条；窄播放条的改动收益/风险比在本次评估中不划算。

## 测试

新增 17 例（324 → 341）。

两个新文件：

- `test/track_artwork_test.dart`（5 例）：`TrackArtwork` 的取图优先级——`file://` 的 `localArtUri`
  优先于 `albumId`；非 `file` scheme 的 `localArtUri`（如 `content://`）视同缺失，落回 `albumId`
  查找；`albumId` 解析出 URL 时走 `CachedNetworkImage`；解析出 `null` 时回落到 `fallback`；两个
  来源都没有时直接回落，不触发任何 provider 查询。
- `test/floating_shadow_test.dart`（7 例）：纯函数 `floatingShadow()` 覆盖层数（恰好两层）、第二层
  模糊半径大于第一层、两层都落在参考区间内、深色皮肤 token 产生的强度大于浅色皮肤 token、透明度
  不会越界（即使传入已经不透明的底色）、两层都向下偏移；另加一条 `GlassPanel` 级别的结构断言，
  确认扛阴影的 `DecoratedBox` 确实是 `ClipRRect` 的祖先而不是被包在里面。

两个既有文件的改动：

- `test/mini_player_bar_desktop_test.dart` 整体重写（原 4 例测 `showNowPlaying: false` 这个已删除
  的参数，现 6 例测按宽度分流出的宽/窄两种形状：宽播放条同时带封面和随机/循环/音量/队列、窄播放条
  保持无这些控件、音量控件在宽播放条内部按自身宽度再分流一次 compact/expanded、964px（1200dp 桌面
  窗口换算出的播放条实际宽度）和 375dp（手机）两档不溢出回归）。
- `test/mini_player_bar_test.dart` 追加 3 例：本地曲目（有 `artUri`、无 `albumId`）在播放条里渲染
  出 `Image.file`；服务端曲目（有 `albumId`、无 `artUri`）仍走 `artworkUrlProvider`
  （`CachedNetworkImage`）；播放条的阴影确实来自显式 `BoxShadow`，`Material.elevation` 确实归零
  （不是叠加了新阴影却没关掉旧的）。
- `test/shell_scaffold_nav_test.dart`：用例数不变，两条断言反过来写（见 A 节）。

校准过程中还抓到一个测试自身的逻辑漏洞：`track_artwork_test.dart` 的 `_app()` 帮助函数第一版用
`artworkUrl != null` 判断要不要给 `artworkUrlProvider` 打桩，这让"服务端解析出无封面"
（`artworkUrl: null`）这个用例从未真正打桩，落到了真实的 `ArtworkUrlNotifier`（真 `Dio` 请求），
遗留的重试/超时计时器在测试收尾时触发 `!timersPending` 断言失败。改成独立的 `stubArtwork` 布尔值
（不再从 URL 是否为 null 反推要不要打桩）后测试本身也更准确地表达了意图。
