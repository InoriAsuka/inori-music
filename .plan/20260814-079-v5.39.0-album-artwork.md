# v5.39.0 — 专辑封面全线占位：两个独立缺口叠加，服务端按需解析 + 客户端相对 URL 补全

生产环境实测：全部 5 张专辑的 `GET /api/v1/catalog/albums/{id}/artwork` 无一例外返回

```json
{"error":{"code":"no_artwork","message":"no artwork"}}
```

客户端表现为清一色的占位音符图标。这个 gap 在 v5.37.1（`.plan/20260813-075-v5.37.1-relative-stream-url.md`）就已经诊断记录：

> FLAC 文件本身元数据齐全（stream 端点的前几百字节里能直接读到完整 Vorbis comment：album / ALBUMARTIST / artist / composer / ISRC / UPC……），说明入库时没有提取内嵌封面。这是媒体摄取的缺口，按路线图属于 v6，不在本次范围。

本次任务把它从 v6 提前排入 v5.39.0，完整诊断分两个独立的缺口，**任何一个单独修都没用**。

## 缺口一：从来没有任何东西写过封面

`Album.ArtworkMediaObjectID`（`internal/catalog/types.go:45`）字段存在：

```go
type Album struct {
    ...
    ArtworkMediaObjectID string    `json:"artworkMediaObjectId,omitempty"`
    ...
}
```

持久化路径存在（`internal/catalog/postgres/repository.go`），更新入口也存在（`handler_catalog.go:683` → `catalog/service.go:236` 的 `UpdateAlbum`）。但 `ImportTrack`（`internal/catalog/service.go:435`）是**纯元数据操作**——调用方直接提供 title/artist/album 字符串，服务端从未打开过音频文件本身：

```go
// ImportTrack validates a media object and creates a Track record that references it.
func (s *Service) ImportTrack(ctx context.Context, req ImportTrackRequest) (Track, error) {
    ...
    info, err := s.mediaReader.GetMediaObjectInfo(ctx, req.MediaObjectID)
    // 只读 asset_kind / lifecycle_state 两个元数据字段，从不读文件内容
    ...
}
```

没有任何扫描/发现端点，`go.mod` 里此前也从未有过音频元数据解析库。换句话说：不是"提取失败"，是"从来没有人打开过文件去提取"。

## 缺口二：就算封面链接对了，当前部署形态也没有能力送出字节

`getAlbumArtwork`（修复前的 `internal/httpapi/handler_catalog.go`）产生 URL 只有一条路：

```go
url, err := handler.storage.GeneratePresignedURL(r.Context(), mo.BackendID, mo.ObjectKey, artworkTTL)
if err != nil {
    writeAPIError(w, http.StatusServiceUnavailable, "presign_failed", "failed to generate artwork URL")
    return
}
```

而 `InferCapabilities`（`internal/storage/validation.go:52`）对 `BackendTypeLocal` 的能力声明是：

```go
case BackendTypeLocal:
    return CapabilitySet{ServerRangeReads: true}   // PresignedURLs 恒为 false
```

生产环境正是 `backendId: "local-music"`、`backendType: "local"`。`GeneratePresignedURL` 内部会检查 `backend.Capabilities.PresignedURLs`，local 类型上这个值永远是 `false`，函数必然返回 `ErrProbeUnsupported`，端点必然答 **503 `presign_failed`**——哪怕 `ArtworkMediaObjectID` 真的填对了也一样。

音轨播放没有这个问题：`getTrackPlayback` 对不支持预签名的后端会退回 `internal/streamsign` 签发的 HMAC 签名 URL，由 `streamTrack` 端点代理字节。封面此前完全没有等价路径——这正是本次要补的。

## 设计约束：为什么不是"入库时补提取"

1. **不能重新导入、不能重新扫描、不能重建数据库。** 用户的生产曲库已经导入完毕，且明确表态生产数据库不会再被删除重建。修复必须让**已经导入的**曲库直接出封面，不要求任何迁移。这条约束直接排除了"在 `ImportTrack` 里顺手加提取逻辑并落库"作为主要手段——那种做法只对未来新导入的曲目生效，对已经在库里的曲目毫无帮助。
2. **绝不写媒体挂载。** 挂载可能是只读的——`LocalConfig.ReadOnly` 字段（v5.35.0 为音乐服务器常见的 `:ro` 挂载专门加的）就是明证。不能尝试把提取出的图片缓存写回媒体后端。
3. **保留现状能正常工作的部分。** `ArtworkMediaObjectID` 已设置、且后端支持预签名 URL（S3）时，原样返回预签名 URL，与今天完全一致。

**结论**：按需解析封面，直接读音频文件，走 API 代理——完全复刻音轨流媒体已经在本地后端上验证过的模式。

## 库选型：`github.com/dhowden/tag`

没有网络访问默认被沙箱阻断，`go get` 需要显式放开沙箱（一次性操作，用于拉取依赖；后续所有 `go build`/`go test` 均在无网络沙箱下正常运行，模块已落盘缓存）。

选型前实测验证了其对本任务的适配度，而不是只看文档：

- **格式覆盖**：`tag.ReadFrom` 支持 FLAC、OGG/Vorbis、MP4、ID3v2（v2.2/2.3/2.4，即 MP3）、ID3v1、DSF——覆盖生产库实际在用的 FLAC，也覆盖常见的 MP3/MP4/OGG。
- **API 形状**：`Metadata.Picture() *Picture`，`Picture{MIMEType string; Data []byte; ...}`——直接给出可以原样塞进 HTTP 响应的字节和 MIME 类型，不需要额外转换。
- **FLAC reader 的宽容度**（`flac.go` 源码实测确认）：只要求 `"fLaC"` 魔数后跟任意数量的元数据块、以一个标了 last-block 位的块收尾，**不要求 STREAMINFO 存在或排在最前**。这意味着测试夹具可以纯手工拼字节（见下文守卫测试），不需要下载真实音频文件或依赖外部编码器——这也是任务要求"创建一个最小夹具文件——不要下载任何东西"能够被满足的关键前提。

**许可证更正**：任务原始描述称其为 MIT，实测该模块的 `LICENSE` 文件内容是标准 **BSD-2-Clause**（无"不得用于背书宣传"条款的二条款版本），并非 MIT。两者同属宽松、可商用、GPL 兼容的许可证族，这处出入不影响选型结论，但如实记录这一更正而非照抄未经验证的说法。

## 服务端实现

### 新增 `internal/artwork` 包

零 HTTP/存储依赖的纯函数包：

```go
type Image struct {
    MIMEType string
    Data     []byte
}

func ExtractEmbedded(path string) (Image, bool, error)
func FindSibling(dir string) (Image, bool, error)
```

`ExtractEmbedded` 打开文件、调用 `tag.ReadFrom`、取 `Picture()`。"识别不出格式"或"没有图片"都返回 `(Image{}, false, nil)`——这是符合预期的常见结果，不是错误；只有真实 I/O 失败（文件打不开）才返回非 nil error。

`FindSibling` 对目录做一次 `os.ReadDir`，建立大小写不敏感的文件名查找表，按 `cover` → `folder` → `front` → `album` 的 basename 优先级、`.jpg` → `.jpeg` → `.png` → `.webp` 的扩展名优先级去匹配，命中即返回。

### `internal/storage` 新增 `Service.LocalPath`

```go
func (service *Service) LocalPath(ctx context.Context, backendID, objectKey string) (string, error) {
    backend, err := service.repository.Get(ctx, backendID)
    if err != nil {
        return "", err
    }
    root, ok := localRootPath(backend)
    if !ok {
        return "", fmt.Errorf("%w: backend %s does not support direct filesystem access", ErrProbeUnsupported, backendID)
    }
    return SafeObjectPath(root, objectKey)
}
```

完全复用 `GetObject`/`PutObject` 已有的 `localRootPath`+`SafeObjectPath` 组合（零新逻辑，纯粹的薄封装），本地/NFS/SMB 之外的后端（S3）返回 `ErrProbeUnsupported`。`resolveAlbumArtwork` 靠它拿到音频文件的绝对路径，再用 `filepath.Dir` 得到同目录去找 sibling 文件——`GetObject` 只给字节不给路径，无法满足"找同目录文件"这个需求，这是新增该方法而不是直接复用 `GetObject` 的原因。

### 泛化 `internal/streamsign`，而非另起一套签名

`Signer.Sign`/`Verify` 的参数从 `trackID` 改名为 `resourceID`——纯语义重命名，HMAC 计算逻辑一字未改：

```go
func (s *Signer) Sign(resourceID string) string { ... }
func (s *Signer) Verify(resourceID string, exp int64, sig string) error { ... }
```

`streamTrack`/`getTrackPlayback` 两处既有调用点（`Sign(track.ID)`、`Verify(trackID, exp, sig)`）行为完全不变——Go 里形参名不是函数签名的一部分，调用方按位置传参，重命名对调用点零影响。

新的专辑封面签名 URL 用命名空间化的负载：

```go
func albumArtworkSignaturePayload(albumID string) string {
    return "album:" + albumID
}
```

而不是裸 `albumID`。这保证就算音轨 ID 和专辑 ID 字符串恰好相撞，一个资源的签名 URL 也永远不能被拿去访问另一个资源——`streamsign_test.go` 新增的 `namespaced resource ID does not collide with bare ID` 子测试专门锁住这条性质（互相 Verify 必须失败，各自 Verify 必须成功）。

### 重写 `getAlbumArtwork`，新增 `getAlbumArtworkFile`

```go
func (handler *Handler) getAlbumArtwork(w http.ResponseWriter, r *http.Request) {
    ...
    if url, ok := handler.presignAlbumArtworkURL(r.Context(), album, artworkTTL); ok {
        writeJSON(w, http.StatusOK, albumArtworkResponse{URL: url, ExpiresIn: ...})
        return
    }
    if _, _, found := handler.resolveAlbumArtworkCached(r.Context(), album.ID); !found {
        writeAPIError(w, http.StatusNotFound, "no_artwork", "no artwork")
        return
    }
    base := "/api/v1/catalog/albums/" + album.ID + "/artwork/file"
    url := base + "?" + handler.streamSigner.Sign(albumArtworkSignaturePayload(album.ID))
    writeJSON(w, http.StatusOK, albumArtworkResponse{URL: url, ExpiresIn: ...})
}
```

`presignAlbumArtworkURL` 只在 `ArtworkMediaObjectID` 非空、且其媒体对象所在后端 `Capabilities.PresignedURLs == true` 时才尝试，任何一步失败（媒体对象查不到、后端查不到、能力位为 false、`GeneratePresignedURL` 本身报错）都统一返回 `ok=false`，交给调用方走下一步的按需解析回退，而不是分别映射成不同的 5xx——这是本次修复相对旧代码最大的结构性变化：旧代码只有"预签名成功"和"预签名失败即终止"两种结局，新代码把"预签名失败"变成"再试一条路"。

`resolveAlbumArtwork` 挑选专辑的"代表曲目"：

```go
func lessArtworkTrack(a, b catalog.Track) bool {
    if a.DiscNumber != b.DiscNumber {
        return a.DiscNumber < b.DiscNumber
    }
    if a.TrackNumber != b.TrackNumber {
        return a.TrackNumber < b.TrackNumber
    }
    return a.ID < b.ID // 最终以 track ID 兜底，保证结果与仓库返回顺序无关
}
```

新端点 `getAlbumArtworkFile` 复刻 `streamTrack` 的双重认证结构（Bearer 头或 `?exp=&sig=` 签名查询串），不套 `requireViewerAuth`，因为签名 URL 路径本身就是头部认证的**替代**而非附加——和 `streamTrack` 同一个理由：`<img>` 元素和 `<audio>` 元素一样无法自定义请求头。

### 进程内缓存 + `ETag`/`Cache-Control`

解析封面意味着打开文件、解析标签、可能还要扫目录——代价不该在每次请求都掏一遍。`artworkCache`（`internal/httpapi/artwork_cache.go`）按专辑 ID 做 10 分钟 TTL 缓存，连"确认没有封面"的负结果也一并缓存，避免反复对同一张空专辑做无谓的文件系统访问。只读挂载排除了落盘缓存，所以只能是进程内、随进程重启失效的形态——这是设计约束 2（绝不写媒体挂载）的直接推论,不是遗漏。

字节响应用内容哈希算 `ETag`（`sha256` 截断），`http.ServeContent` 原生处理 `If-None-Match` 生出 304，零手写条件请求逻辑。`modtime` 传零值——ETag 是内容寻址的，比"修改时间"更贴切（一张封面可能来自内嵌 tag 也可能来自 sibling 文件，两者的"修改时间"语义本来就不一致）。

## 客户端半边：为什么这是同一个版本的两半，缺一不可

`services/mobile/lib/src/catalog/artwork_provider.dart` 原来把 `resp.data?['url']` 原样交给图片组件。服务端一旦对本地后端开始返回**相对**签名路径，这条路径会精确复现 v5.37.1 播放那次的故障形状——`Uri.parse('/api/v1/…')` 没有 scheme、没有 host——只是这次是封面图加载失败，不是播放失败。**只发服务端半边会把"无封面占位图"换成"图片加载失败"，比现状更糟**：现状至少有一个诚实的占位符，加载失败的图片组件在不同平台上的表现更难预测。

v5.37.1 已经在 `player_notifier.dart` 解过完全同构的问题：

```dart
String absolutePlaybackUrl(String url, String base) =>
    Uri.parse(base).resolve(url).toString();
```

本次把它泛化搬到 `lib/src/shared/absolute_url.dart`（改名 `absoluteApiUrl`，doc comment 扩写为同时覆盖播放流与专辑封面两种场景），`player_notifier.dart` 保留 `absolutePlaybackUrl` 作为薄别名转调新函数：

```dart
String absolutePlaybackUrl(String url, String base) =>
    absoluteApiUrl(url, base);
```

`test/playback_url_test.dart` **零改动**仍然全绿——这本身就是"泛化没有破坏原有行为"的一次证明，而不是靠承诺。

`artwork_provider.dart` 改用：

```dart
return absoluteApiUrl(url, resp.requestOptions.baseUrl);
```

刻意**没有**引入 `baseUrlProvider`（`player_notifier.dart` 里 `resolvePlaybackUrl` 用的那条 provider 链）。原因：`baseUrlProvider` 最终要摸 `SharedPreferences.getInstance()`/`flutter_secure_storage`，而既有的 4 条 `artwork_url_provider_test.dart` 用例全靠覆盖 `dioProvider` 绕开真实网络/存储，从未在测试里初始化或 mock 过这两个插件；贸然接入会让这批已有测试第一次真正触碰平台通道，在纯 `test()`（非 `testWidgets()`）环境下有炸出 `MissingPluginException` 的风险。`resp.requestOptions.baseUrl` 是 dio 拦截器实际用于**这一次请求**的 base——由 `dioProvider` 的认证拦截器逐请求写入该请求自己的 `RequestOptions`（`options.baseUrl = baseUrl`），而非改写共享的 `Dio.options`（`BaseOptions`）本身；直接读响应自带的 `requestOptions.baseUrl`，语义上比另开一条 provider 读取更准确（它就是这次请求实际用的那个值，不可能出现"provider 读到的值和实际请求不一致"的竞态），也完全不引入新依赖，是本次实现过程中相对最初设想（照搬 `resolvePlaybackUrl` 用法）的一处刻意偏离，如实记录。

## 未做 / 已知限制

- 只覆盖 `dhowden/tag` 支持的格式（FLAC/OGG/MP4/ID3v2/ID3v1/DSF）。WAV 等它不支持的格式会静默落到 sibling 文件回退，两者都找不到则诚实 404，不报错。
- sibling 文件候选名单固定为 `cover`/`folder`/`front`/`album` 四个 basename、`.jpg`/`.jpeg`/`.png`/`.webp` 四个扩展名，不支持用户自定义扩展这份列表。
- **`ArtworkMediaObjectID` + 本地后端组合下，就算手工 PATCH 关联了一个真实的独立封面图片媒体对象，也不会被直接读取/served**——本版本的回退分支统一走"从专辑的曲目重新解析"，没有单独为"本地后端 + 已关联的封面媒体对象"这个组合再实现一条"直接读取该媒体对象字节"的路径。在当前生产数据下这是等价的（`ArtworkMediaObjectID` 目前恒为空，缺口一决定了这一点），但如果未来有人在本地后端上手工关联了一个专门制作的封面媒体对象（而不是复用某条音轨的媒体对象），这条关联会被忽略，转而继续从音轨文件解析——值得记录，留给后续按需处理。
