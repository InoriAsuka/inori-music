# v5.34.0 — 服务端部署前排查：两个真 bug + 两条静态守卫测试

计划把服务端部署到一台 Unraid 主机上。动手部署前先审查代码，发现两个会让部署静默出错的真 bug——都已在源码里逐一核实，不是猜测。本 phase 先修掉两个 bug，再各补一条静态架构测试守卫，防止同类问题第三次发生。纯 Go 服务端改动，`services/api/` 之外只动了仓库根的 `docker-compose.prod.yml`。

---

## Bug 1 — 两个 Postgres migration 从未被调用

### 根因

`services/api/cmd/server/main.go` 里：

- 第 141 行 `psRepo := playerstatepg.NewRepository(pool)`
- 第 151 行 `shRepo := searchhistorypg.NewRepository(pool)`

但 `playerstatepg.Migrate()` 与 `searchhistorypg.Migrate()` 在整个代码库里没有任何调用点。全仓库 grep `.Migrate(ctx` 此前只命中两处：`pgstore.Migrate`（`main.go:281`）与 `userplaylistpg.Migrate`（`main.go:344` 附近）。`NewRepository` 不做惰性建表，只是存了一个 pool 引用。

后果：`user_player_state` 与 `user_search_history` 两张表在真实 Postgres 数据库上永远不会被创建。这两张表正是 v5.4.0「跨设备续播 + 搜索历史同步」整个特性能够落地的前提——功能代码全部写完了，建表这一步从未执行过。

### 为什么四个版本都没被发现

`internal/playerstate/postgres/` 与 `internal/searchhistory/postgres/` 两个包一个测试文件都没有（只有 `repository.go`）。单元测试全部走内存实现（`playerstate.NewMemoryRepository()` / `searchhistory.NewMemoryRepository()`），Postgres 路径从未被真正执行过，所以 `go test` 全绿掩盖了这个问题。

对照组：同目录下的 `internal/userplaylist/postgres/` 同样零测试，但它的 `Migrate` 恰好在 `main.go` 里被调用了——这说明「新增一个 postgres repository 包却忘了接 migration」是一个遗漏，不是刻意的设计决定。

### 修复

在 `main()` 对应的 `if pool != nil` 分支内补上 `Migrate` 调用：

```go
if pool != nil {
    if err := playerstatepg.Migrate(ctx, pool); err != nil {
        log.Printf("player state migration: %v", err)
    }
    psRepo := playerstatepg.NewRepository(pool)
    playerstateSvc = playerstate.NewService(psRepo)
} else {
    ...
}
```

`searchhistorypg` 同构。错误处理照 `userplaylistpg.Migrate` 现有写法——`log.Printf` 记录但不中断启动，不额外发明新的错误处理策略，与本仓库既有风格保持一致。

### 守卫：`migrate_coverage_test.go`

新增 `services/api/cmd/server/migrate_coverage_test.go`（`TestPostgresMigrateFuncsAreCalledInMain`）。用标准库 `go/parser` + `go/ast` 做静态扫描，不连数据库：

1. 扫描 `internal/*/postgres/*.go`，找出所有导出的**包级** `Migrate` 函数（方法不算——`fn.Recv != nil` 直接跳过，因为本仓库现有四个 `Migrate` 全部是可以直接调用的包函数，不是某个类型的方法）。
2. 解析 `main.go` 的 import 声明，建立「`internal/*/postgres` 导入路径 → 本地标识符（别名或包名）」的映射。
3. 用 `ast.Inspect` 收集 `main.go` 里所有形如 `<ident>.Migrate(...)` 的调用表达式。
4. 断言第 1 步找到的每个包，其对应标识符都出现在第 3 步的调用集合里；否则精确报出是「没有被 import」还是「import 了但没被调用」。

这条测试的价值不在于验证一次性的两个 bug 是否修好了（那是普通回归测试就能做的事），而在于**以后任何人新增一个 `internal/X/postgres` 包并写了 `Migrate` 却忘了在 `main.go` 里接线，这条测试会立刻失败**，把「遗漏」变成「编译期就能发现的错误」。

修复前先验证过测试本身有效：临时把新测试文件套在未修复的 `main.go` 上跑，精确报出：

```
migrate_coverage_test.go:166: new PostgreSQL tables would silently never be created — wire the migration in cmd/server/main.go next to where the repository is constructed (see playerstatepg.Migrate / userplaylistpg.Migrate for the pattern):
      inori-music/services/api/internal/playerstate/postgres (imported as "playerstatepg") exports Migrate but main.go never calls playerstatepg.Migrate(...)
      inori-music/services/api/internal/searchhistory/postgres (imported as "searchhistorypg") exports Migrate but main.go never calls searchhistorypg.Migrate(...)
```

证明测试确实能抓住这类 bug，不是摆设。

## Bug 2 — `docker-compose.prod.yml` 的环境变量契约与源码不符

### 根因

`docker-compose.prod.yml:37`（修复前）写的是：

```yaml
INORI_DB_DSN: "postgres://inori:${POSTGRES_PASSWORD}@postgres:5432/inori?sslmode=disable"
```

但源码读的是 `INORI_DATABASE_URL`（`cmd/server/main.go:267`：`dsn := os.Getenv("INORI_DATABASE_URL")`）。`INORI_DB_DSN` 在整个 Go 源码里零命中。

照这份 compose 部署，`openDatabasePool` 读不到 DSN 会直接返回 `nil, nil`，API 走进：

```go
log.Print("INORI_DATABASE_URL is not set; auth service running with in-memory (non-persistent) user/session storage")
```

容器正常启动、健康检查正常通过，然后一重启用户和会话全部丢失——典型的静默失败：没有任何错误、没有崩溃、日志里那一行提示很容易被淹没在正常启动日志里。

compose 里同时还有一个死变量 `INORI_AUTH_SECRET`（第 39 行，标成 required），源码里同样零命中；顶部注释块（第 6 行）也提到了它，一并清理。

### 核对方法

逐一 grep 源码里全部 `os.Getenv("INORI_[A-Z_]+")` 与 `os.Getenv("MEILI_[A-Z_]+")` 字符串字面量调用，得到源码实际读取的完整集合（全部出现在 `cmd/server/main.go`，即 Dockerfile 实际构建进镜像的入口）：

```
INORI_ADMIN_TOKEN, INORI_CORS_ORIGINS, INORI_DATABASE_URL, INORI_HTTP_ADDR,
INORI_INITIAL_ADMIN_PASSWORD, INORI_INITIAL_ADMIN_USER,
INORI_MEDIA_OBJECT_REPOSITORY_FILE, INORI_SESSION_TTL,
INORI_STORAGE_REFRESH_INTERVAL, INORI_STORAGE_REPOSITORY_FILE,
INORI_STREAM_SIGNING_KEY, MEILI_HOST, MEILI_SEARCH_KEY
```

（`INORI_E2E_VIEWER_USER`/`INORI_E2E_VIEWER_PASSWORD` 也在 `main.go` 里，但那是测试夹具专用，生产 compose 不需要，正确地排除在外。）

### 修复

1. `INORI_DB_DSN` → `INORI_DATABASE_URL`（改名，值表达式不变）。
2. 删除死变量 `INORI_AUTH_SECRET`（含顶部注释块里的提及）。
3. 补上源码支持但 compose 未提及的四组变量，全部通过 compose 的 `${VAR:-default}` 插值语法接入 `.env`：
   - `INORI_INITIAL_ADMIN_USER` / `INORI_INITIAL_ADMIN_PASSWORD`：可选，留空即跳过初始管理员创建（`EnsureInitialAdmin` 对空用户名/密码是 no-op，不是错误）；两者都设置才能在全新数据库上完成自助登录。**没有编造任何默认凭据值**——硬编码一个看起来合理的默认密码本身就是安全隐患。
   - `INORI_CORS_ORIGINS`：可选，留空是源码的宽松模式（反射任意来源）。
   - `INORI_SESSION_TTL`：默认值 `24h` 直接取自源码 `sessionTTL()` 的硬编码默认，是核实过的真实值，不是臆测。
   - `INORI_STORAGE_REFRESH_INTERVAL`：可选，留空即关闭周期刷新调度器，与源码默认行为一致。

`docker-compose.prod.yml` 其余部分未改动——这是一份通用参考部署，不是 Unraid 主机的具体实例（共享 postgres、macvlan、网关端口等具体部署形态不在本次范围）。

### 守卫：`compose_env_test.go`

新增 `services/api/cmd/server/compose_env_test.go`（`TestComposeAPIEnvVarsMatchSource`）：

1. 用标准库 `go/parser` + `go/ast` 解析 `cmd/server/main.go`，收集所有 `os.Getenv("INORI_...")` 调用的字符串字面量参数。
2. 用 `gopkg.in/yaml.v3` 解析仓库根的 `docker-compose.prod.yml`，取 `services.api.environment` 映射的 key，过滤出 `INORI_` 前缀的部分。
3. 断言第 2 步的集合是第 1 步集合的子集——compose 里出现源码不读的名字就失败。

只做单向检查（compose → 源码），不反向要求源码支持的每个变量都必须出现在 compose 里，否则会对 E2E 测试专用变量等合理缺省产生误报。

**依赖选择**：`gopkg.in/yaml.v3` 本来就是 `testcontainers-go`（`go.mod` 里已有的直接依赖）拉进来的间接依赖，`go.sum` 里已有完整哈希。直接 import 后跑 `go mod tidy` 把它从 indirect 提升为 direct，**没有引入任何新的外部依赖**——符合任务要求「不要为此引入新依赖」。之所以选真正的 YAML 解析而不是手写文本扫描：`docker-compose.prod.yml` 顶部注释块本身就用散文提到了 `INORI_ADMIN_TOKEN`、`POSTGRES_PASSWORD` 等变量名，朴素的正则扫描会把注释里的提及误判成真实的 environment key；结构化解析天然只看 `services.api.environment` 这个真实映射，不会被注释污染。

`go mod tidy` 顺带把此前遗漏的 `github.com/mozillazg/go-pinyin`（`internal/search/meilisearch.go` 早就直接 import 但 go.mod 一直标成 indirect）也提升为 direct——这是存量 go.mod 卫生问题，不是本次引入的，顺手一并修正。

**路径定位**：`docker-compose.prod.yml` 在 `services/api` 这个 Go module 之外（仓库是 `go.work` 多 module 结构），测试向上查找 `go.work` 文件定位仓库根，不用写死的 `../../../..` 相对路径层数——更不容易因为目录结构调整而悄悄失效。

修复前同样验证过测试本身有效：临时把新测试文件套在未修复的 compose 文件上跑，精确报出：

```
compose_env_test.go:168: docker-compose.prod.yml's api service declares INORI_* variables cmd/server/main.go never reads via os.Getenv — these are dead or misspelled and will silently no-op in production: INORI_AUTH_SECRET, INORI_DB_DSN
```

## 评估但未做：migration 可运行测试

`playerstate/postgres`、`searchhistory/postgres`、`userplaylist/postgres` 三个包全部没有测试文件；其中 `playerstate`、`searchhistory` 连不需要数据库的 service 层单测都没有（`userplaylist` 的 service 层有测试，只是 postgres 子包没有）。

调研发现仓库其实已经具备所需基建：`testcontainers-go/modules/postgres` 已是 `go.mod` 里的**直接**依赖（不是我加的，本来就在），`catalog/postgres`、`storage/postgres`、`history/postgres` 三个包已有 `//go:build integration` 标记的 testcontainers 集成测试作为先例（跑真实的一次性 Postgres 容器）。但 `.github/workflows/build.yml` 的 `go test` 步骤没有传 `-tags=integration`，这类测试目前完全不在 CI 里跑，只是本地手动可用的安全网。

结论：既然基建已经存在，给 `playerstate/postgres`/`searchhistory/postgres`（乃至 `userplaylist/postgres`）补同样模式的集成测试**不需要引入任何新依赖**，技术上完全可行，值得做。但这是一个独立的、有一定体量的工作项（三个文件、需要理解 upsert/JSONB 序列化等各自的读写语义），任务要求评估后「写进汇报，让用户决定」，所以本 phase 没有顺手做，留作候选跟进项。
