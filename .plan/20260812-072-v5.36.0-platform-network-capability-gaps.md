# v5.36.0 — 客户端从未连通过任何服务器：三个平台层联网能力缺口

用户反馈 Flutter 客户端登录不上服务端。诊断结论：**不是应用层 bug**，是 macOS/Android 两个平台的联网能力从一开始就没打开——`flutter create` 生成的平台模板本就不带这些配置，从项目第一次提交起就没人补过。三处缺口都不在 Dart 代码里，`flutter analyze` 和存量 404 个测试没有一个能看到它们，这正是它们潜伏至今的原因。本 phase 补齐三处平台配置，并为每一处写了解析配置文件本身的架构测试，逐一做了「删掉即报错」的空洞性证伪。核实过程中还发现一个原始诊断没有覆盖到的范围外缺口（iOS 播放侧的 ATS 限制），如实记录、未修，见文末。

只动了 `services/mobile/` 下的文件：两个 macOS entitlements、一个 Android manifest、一个新增测试文件。

---

## 根因一：macOS App Sandbox 缺 `com.apple.security.network.client`

`grep -r "network.client" services/mobile/macos/` 在改动前零命中。`Release.entitlements`/`DebugProfile.entitlements` 都设了 `com.apple.security.app-sandbox = true`，且都通过 `CODE_SIGN_ENTITLEMENTS` 真实挂在 Xcode 项目上（`macos/Runner.xcodeproj/project.pbxproj:488/620/640`）——不是没生效的孤立文件。

**独立核实了这条链路的强度**：App Sandbox 是 macOS 内核（Seatbelt / MACF，Mandatory Access Control Framework）对进程发出的**每一个 syscall**做的强制访问控制，不是某个网络库自己选择遵守的约定。没有 `network.client`，`connect()` 这个 syscall 本身就被内核拒绝——发生在任何用户态 HTTP 栈之前。这意味着不管 `dio`（登录用）还是 `just_audio`（播放用）走的是什么网络实现，两者都会被同一道内核闸门挡住，无一幸免。`network.server`（已存在）只管入站连接（调试期的 Dart VM service），不能替代它。

**修复**：两个文件都加了 `com.apple.security.network.client = true`，Debug/Release 各自独立带上完整的原因注释（沙盒下这是出站连接的前提；`network.server` 覆盖的是另一个方向；两个 build 配置都要，没有 debug-only 的例外）。风格照抄该目录已有的「Guest-mode local library (v5.12.0)」注释块——写清楚 why，不丢裸 key。

## 根因二：Android release 构建缺 `INTERNET` 权限

`android/app/src/debug/AndroidManifest.xml` 和 `.../profile/AndroidManifest.xml` 里各有一份 `INTERNET` 权限，注释写着「The Flutter tool needs it... hot reload...」——这是 `flutter create` 模板专门为调试期工具链放的，从来就不是给 release 用的。`android/app/src/main/AndroidManifest.xml`（三种 build type 共享、release 会打包进最终 APK 的那份）里完全没有。

Android 的 `INTERNET` 权限由 Linux 群组机制（安装时把 app 的 UID 加进 `AID_INET` 组）在内核层面控制 socket 创建本身，跟 macOS 的沙盒闸门是同一量级的强制层——不区分是 Java 网络栈还是 Dart VM 自己的原生 socket，release APK 少了它就是零联网能力，无论 Dart 代码写得多正确。

**修复**：在 `main/AndroidManifest.xml` 加了 `<uses-permission android:name="android.permission.INTERNET" />`，紧挨着已有的 `FOREGROUND_SERVICE` 等权限块之上，注释说明它和 debug/profile 里那份不是一回事（那份只覆盖调试期，不会进 release 包）。没有动 debug/profile 的既有声明。

## 根因三：Android 明文 HTTP——以及核实后发现的真实作用机制

任务给我的原始诊断是「`<application>` 没有 `usesCleartextTraffic`，Android 9+ 默认禁明文，服务端是 `http://10.100.121.134`」。这个结论方向对，但**核实下去发现它解释的问题和实际生效的机制并不是同一件事**，值得如实记录：

### 查证：`dio` 的 API 调用（含登录）大概率根本不受这条策略约束

查了 Flutter 官方文档（[Insecure HTTP connections are disabled by default on iOS and Android](https://docs.flutter.dev/release/breaking-changes/network-policy-ios-android)）原文：

> The following only applies to platform native sockets (sockets owned by the Android and iOS platforms). Flutter does not enforce any policy at socket level... If the socket is owned by Dart/Flutter, no policy will be enforced.
>
> Reverted in version: 2.2.0 (proposed)

`dio` 默认走的 `IOHttpClientAdapter` 就是 `dart:io` 自己的 socket 实现（NDK 原生 BSD socket，不经过 Java `java.net.Socket`/OkHttp），属于文档说的「Dart 拥有的 socket」——即使 Flutter 曾经加过的这层策略仍在时也不覆盖它，何况这层策略本身在 2.2.0（2021 年）就撤回了。这不是我的推测：`flutter/flutter#106678`（"Flutter doesn't respect Android's `usesCleartextTraffic="false"` settings"）里有人实测复现——manifest 显式设了 `false`，Java 侧确认 `NetworkSecurityPolicy.isCleartextTrafficPermitted()` 返回 `false`，Dart 侧的 HTTP 请求依然成功——官方以 "not planned" 关闭，明确表示不打算修。

也就是说：**Android 上「登录连不上」这件事，`usesCleartextTraffic` 大概率解释不了**——`dio` 的请求本来就没被这条策略拦过，release 包真正的拦截点是根因二（`INTERNET` 权限缺失，内核层面无差别拦截，dio 也在内）。

### 查证：`just_audio` 的播放路径不一样——它是真正的原生网络栈

`just_audio` 在 Android 上包装的是 `ExoPlayer`，一个真正的平台原生组件，走 Android 自己的网络栈，**确实**受 `NetworkSecurityConfig`/`usesCleartextTraffic` 约束。这不是我的猜测，是 `just_audio` 官方文档自己的说明（pub.dev/packages/just_audio 的 cleartext 章节）：它的本地代理（用于 headers/caching/部分流式音频源）跑在 localhost 的 HTTP 上，这个代理本身就需要 cleartext 权限才能工作，跟远程 URL 是不是 HTTPS 无关；如果要连 `http://` 的远程源，同样需要这个开关。

**修正后的结论**：`usesCleartextTraffic` 这项修复解决的不是「登录连不上」，而是「登录/浏览能成，但一点播放键就失败」——服务端音频走 `http://10.100.121.134`，没有这个开关，`just_audio`/`ExoPlayer` 会拒绝打开这个流。两个问题都要解决客户端才算真正能用，所以这项修复仍然必要，只是原因要归到播放链路，不是连接性本身。已经把这个更准确的归因写回下面的守卫测试和注释里。

### 机制选择：单一开关属性，而非 network security config XML

任务背景里已经点出服务端地址是用户运行时填的（设置 > 服务器），构建期不知道具体域名，没法用 `network_security_config.xml` 精确圈定域名允许 cleartext——那种做法本质上还是要么整体放行、要么走不通。在「整体放行」这个前提确定之后，`android:usesCleartextTraffic="true"` 是能做到「同一件事、且只有一个touch point」的最简形式：一个属性，删掉或改回 `false` 就是完整回退，不需要额外维护一个 XML 文件 + 一条 manifest 引用两处保持同步。已把这条推理写进 `AndroidManifest.xml` 里紧贴 `<application>` 标签的注释块（`<!-- SECURITY TRADE-OFF (v5.36.0) ... -->`），回退条件明确写了：服务端一旦有 HTTPS，删掉这一个属性即可，Android post-P 的默认值本身就是禁止明文。

## 为什么现有测试体系完全覆盖不到

三处改动全部落在 Info.plist 风格的 `.entitlements` 文件和 `AndroidManifest.xml` 里，没有一行是 Dart 源码。`flutter analyze` 不解析这些文件；存量 404 个测试没有一个会去读它们。这正是它们能从项目第一个 commit 存活到现在、经历了 v1 到 v5.34 全部版本、从未被任何一次 CI 绿灯拦下的原因——不是没测过，是这个维度上根本没有测试能触达。跟 memory 里记录过的「silent failure pattern」是同一个坑的另一种表现形式：这次不是「失败了界面零反馈」，而是「配置漏了，没有任何工具会报警」。

## 独立核实：iOS 到底受不受影响

任务原始诊断说 iOS 不受影响，且明确要求不要直接采信、自己查。核实结论分两半：

### 连接性（登录/API 调用）——原始判断成立

- `services/mobile/ios/` 里没有任何 `.entitlements` 文件，`ios/Runner.xcodeproj/project.pbxproj` 里 `grep -n "CODE_SIGN_ENTITLEMENTS"` 零命中——iOS 项目本身不存在 App Sandbox 这个概念，自然也没有对应的「出站连接」entitlement 缺口。
- `ios/Runner/Info.plist` 里没有 `NSAppTransportSecurity` 键——但 `dio` 的默认 adapter 跟 Android 同理，走 `dart:io` 的 socket 实现，前面引用的 Flutter 官方文档同一段话同时覆盖 iOS 9 和 Android API 28，结论一致：Dart 拥有的 socket 不受 ATS 约束（且这层策略本身已撤回）。

**登录、浏览这些 `dio` 调用，iOS 确实不受影响**，这部分原始判断站得住。

### 范围外发现：iOS 的播放路径和 Android 是同一个坑

`just_audio` 在 iOS 上包装的是 `AVPlayer`——跟 Android 上包装 `ExoPlayer`是完全对称的处境：一个真正走系统网络栈（`NSURLSession`/`CFNetwork`）的原生组件，是会被 ATS 卡住的。查证了 ATS 拦截 `AVPlayer` 加载 `http://` 资源的标准报错（`NSURLErrorDomain` code `-1022`，"The resource could not be loaded because the App Transport Security policy requires the use of a secure connection"），以及标准的修复方式——`NSAllowsArbitraryLoadsForMedia`（专为流媒体开的口子，比 `NSAllowsArbitraryLoads` 更精确）。

这个仓库的 `Info.plist` 里没有 `NSAppTransportSecurity` 字典，也就没有这个例外。**服务端是 `http://10.100.121.134`，意味着 iOS 上登录能成、目录能刷出来，但点开一首歌大概率会被 ATS 拦下，报 -1022。** 这跟 Android 上「`usesCleartextTraffic` 修的其实是播放而不是登录」是同一个根因形状——原生媒体播放器组件是唯一真正遵守平台网络安全策略的一环，`dio` 全程都绕过它。

**这不在本次四项任务范围内**（任务只列了 macOS entitlements / Android INTERNET / Android cleartext 三项），按边界要求不擅自扩大改动，**没有修改 iOS `Info.plist`**，仅如实记录在这里。修复方式若要做：`Info.plist` 加

```xml
<key>NSAppTransportSecurity</key>
<dict>
    <key>NSAllowsArbitraryLoadsForMedia</key>
    <true/>
</dict>
```

同样需要配套的守卫测试（复用本次 `_withoutXmlComments` + 结构化正则的思路解析 plist）。留给后续 phase。
