# v5.39.1 — 修复 `TestUpdateAlbumChangesTitle` 间歇性时钟精度 flaky

`internal/catalog/service_test.go` 的 `TestUpdateAlbumChangesTitle` 在满载并行跑全量测试套件时大约 1/5 概率报红，v5.39.0 验证阶段已经确认过这条 flaky 与当次改动无关。本次是它的专项修复，范围严格限定在这一个测试文件内，不做其他改动。

## 缺陷

`TestUpdateAlbumChangesTitle`（`service_test.go:1078`）用 `catalog.NewService(newMemRepo())` 构造 service——`now` 字段默认是真实的 `time.Now`。`CreateArtist` → `CreateAlbum` → `UpdateAlbum` 三次调用背靠背执行，中间没有任何耗时操作，随后断言 `updated.UpdatedAt.After(album.UpdatedAt)`。当两次 `time.Now()` 落在同一个时钟精度粒度内——空跑时罕见，满载并行跑全套件时命中概率显著更高——`After()` 为 false，测试失败。这不是新回归：该测试写法自 v1.27.0（2026-06-20）起就是这样，只是此前没有专项排查过。

## 根因确认与复现（修复前）

用并发施压复现"满载并行跑全套件"的调度竞争：每轮启动 4 份并发的 `go test -count=1 ./...`（`services/api` 全量套件），连续跑了 92 次完整套件。结果：`TestUpdateAlbumChangesTitle` 失败 28 次（约 30%），失败信息全部精确指向同一行：

```
--- FAIL: TestUpdateAlbumChangesTitle (0.00s)
    service_test.go:1095: UpdatedAt must advance
FAIL
```

92 次里没有出现任何其他测试失败——确认这确实是唯一的间歇性问题，不是并发施压引入了新的不稳定因素。

## 修复：接到已有的时钟注入座子上，而不是放宽断言

`catalog.Service` 早已有可注入时钟：

```go
// service.go
type Service struct {
    ...
    now func() time.Time
}

func NewService(repo Repository) *Service {
    return &Service{repo: repo, now: time.Now}
}

func (s *Service) WithClock(fn func() time.Time) *Service {
    s.now = fn
    return s
}
```

与 `storage.Service` 的 `now func() time.Time` 是同一套模式；`catalog_test` 是外部测试包（`package catalog_test`），拿不到未导出字段，所以走公开的 `WithClock` 方法注入。本文件里已经有专门为这个问题准备好的帮助函数：

```go
func newSteppingService(repo catalog.Repository) *catalog.Service {
    base := time.Date(2026, 1, 1, 0, 0, 0, 0, time.UTC)
    tick := 0
    return catalog.NewService(repo).WithClock(func() time.Time {
        tick++
        return base.Add(time.Duration(tick) * time.Second)
    })
}
```

每次调用 `now()` 前进 1 秒的假时钟，`TestUpdateArtistChangesNameAndSortName`、`TestUpdateTrackChangesTitle`、`TestPlaylistUpdateMetadata` 三个姐妹测试都已经在用它做同构的 `.After(` 断言。`TestUpdateAlbumChangesTitle` 只是当初被漏掉了，不是没有现成的解法。

修复是一行改动：

```diff
 func TestUpdateAlbumChangesTitle(t *testing.T) {
 	ctx := context.Background()
-	svc := catalog.NewService(newMemRepo())
+	svc := newSteppingService(newMemRepo())
 	artist, _ := svc.CreateArtist(ctx, "Artist", "")
```

断言本身原样保留 `updated.UpdatedAt.After(album.UpdatedAt)`，验证的仍是"更新真的推进了时间戳"这个真实意图，而不是弱化成一个时间戳从不变化也能通过的更弱条件。没有加 `time.Sleep`——那只会把一个 flaky 测试换成一个更慢的、在足够粗的时钟下依然会 race 的测试。

搜索本文件全部 `.After(` 断言，一致 5 处：

5 处里只有 1 处受影响，其余 4 处已经在用正确的模式，不需要额外改动。另外确认 `internal/catalog/postgres/repository_integration_test.go` 挂了 `//go:build integration` 标签、默认不参与 `go test ./...`，也没有 `.After(` 断言，不在本次排查范围内产生影响。
