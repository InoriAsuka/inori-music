# v5.32.0 — 播放页转场 + 打开卡顿修复 + 进度条 hover 收缩真 bug + 比例重调 + 封面 hover 放大

用户 v5.31.0 实机验收：「这下看起来不违和了」，侧栏齐平化通过。剩两条反馈，都关于**交互手感**：播放页转场太廉价（用户看到「从下往上」其实是 Flutter 默认 `FadeUpwardsPageTransitionsBuilder`，只位移 25% + 淡入）、点击封面展开播放页会先卡顿再弹出；调研过程中另外定位到进度条 hover 收缩真 bug、进度条比例失调、封面缺 hover 视觉提示三项一并处理。

原计划（`smooth-toasting-manatee.md`「批次三：统一设计语言」）把转场排在 v5.33.0、侧栏菜单重做排 v5.32.0。用户新反馈把转场提前，菜单重做顺延到 v5.33.0——这是本 phase 与既定顺序**唯一**的差异，其余范围不变。

## A. 播放页转场：上滑打开 / 下滑关闭

### 路由改造

`lib/src/shared/router.dart` 的 `AppRoutes.player` 路由从 `builder:` 改 `pageBuilder:`，返回 `CustomTransitionPage`：

- `opaque: false`——转场期间/拖拽期间下层 shell 必须保持可见，渐暗遮罩才有东西可遮。
- `transitionDuration`/`reverseTransitionDuration` 取新常量 `playerTransitionDuration`（320ms，二者相等）。
- `transitionsBuilder: playerPageTransitionsBuilder`——实际机制全部搬进新文件 `lib/src/player/player_transition.dart`，不写在路由定义里。
- `child: const FullPlayerScreen()` 只是占位——`CustomTransitionPage.child` 在 `animation` 存在之前就已经构建完毕，没有办法让它携带播放页需要的 `PlayerTransition` 参数；`playerPageTransitionsBuilder` 直接无视这个 `child`，自己重新构造一份挂了 `animation` 的 `FullPlayerScreen`。

### 时长与曲线

`playerTransitionDuration = 320ms`：300–360ms 区间中点。定位参照本仓库已有的两个时长基准——`positionTweenDuration`（260ms，进度条位置补间）与歌词列表自动滚动（300ms）——都是小尺度、高频动作；转场是"整窗内容切换"级别，理应比两者慢一档，但转场本身也是高频交互（一场会话里开关很多次），不宜比区间上限更慢。`playerTransitionReverseDuration` 直接等于同一个值——"对称"指的是曲线形状（进场减速、退场加速），不是时长本身要不同。

曲线：`Curves.easeOutCubic` 直接套在路由 `animation` 的**原始值**上，不经过 `CurvedAnimation` 的 `reverseCurve`。推导（写在 `_PlayerTransitionShellState._openness` 的文档注释里）：`CurvedAnimation.value` 的源码（`animations.dart`）显示 `reverseCurve` 留空时无条件复用 `curve` 本身，不分方向；把同一条 `easeOutCubic` 直接应用在"进场 0→1 线性推进"和"退场 1→0 线性倒退"两种输入上，代入求导后进场读出减速形状（先快后慢），退场读出**镜像**的加速形状（先慢后快）——刚好是用户要的"对称"曲线，不需要另外挑一条 `easeInCubic` 去凑。

### 下滑手势关闭

自建独立 `AnimationController _drag`（值域即"多开"程度，1=全开，0=全关），而非直接操作 `ModalRoute.of(context)!.controller`：后者是 `TransitionRoute` 上标了 `@protected` 的成员，Cupertino 内建的边缘返回手势能碰它是因为那段代码本身混入在路由类自己身上（`CupertinoRouteTransitionMixin`），本仓库的拖拽手柄只是路由树里一个普通后代 widget，直接碰会触发分析器 `invalid_use_of_protected_member`——而本仓库的 `flutter analyze --no-fatal-infos` 门槛是任何新增 warning 都算失败。

- 拖动跟手：`_handleDragUpdate` 直接赋值 `_drag.value -= deltaY / referenceHeight`，不套曲线（"拖动跟手"要求 1:1，曲线只用在两个*松手后*的收敛动画上）。
- 松手判定二选一：位移超过 30%（`_dismissExtentThreshold`）或速度超过 700px/s（`_flingVelocityThreshold`，直接复用 Flutter `Dismissible` 自己的 `_kMinFlingVelocity` 常量，不另起一个数字）→ 关闭；否则回弹。
- 关闭时：本地 `_drag` 先自己播完到 0 的收尾动画，**播完之后**才真正调用 `Navigator.maybePop()`。这是刻意的顺序，不是随手一个 `whenComplete`——如果提前 pop，路由自身独立的 reverse 过渡（一个完全不同的时间轴）会在本地动画播到一半时闯进来，产生肉眼可见的跳变；等本地动画先归零，`_openness` 的 `min()` 组合逻辑会一直钉在 0（因为本地值已经最小），路由自己那条 reverse 过渡不管跑多久都不会被实际渲染出来。
- 手柄范围：只有顶栏标题区（`FullPlayerScreen._dragHandle`），不含关闭/队列等按钮，也不含封面/歌词/队列面板等可能可滚动的区域。把整屏都做成拖拽区会让内部 `ListView`（歌词、队列）跟外层下滑手势挤在同一个手势竞技场里——"滚动到顶再接管下滑"式的全屏协调是 `DraggableScrollableSheet` 那个量级的独立功能，本批不做，只在确定没有滚动内容的顶栏区域开放手柄。这是一处主动的范围收窄，供复核。

### 数据流

新增 `PlayerTransition`（`full_player_screen.dart`）打包 `progress`（路由 `animation`）+ 三个拖拽回调，作为 `FullPlayerScreen` 唯一新增的可选构造参数（`transition`）。两件事绑成一个对象而非两个独立可空参数，因为它们总是一起提供或一起省略；省略时（每一个既有测试的构造方式）两件事都退化成安全默认：`_backdropSettled` 直接判定"已完成"，`_dragHandle` 直接透传 child、不包手势。

## B. 打开时的卡顿

### 验证

读 `cover_fluid_background.dart` 源码确认：`CoverFluidBackground` 第一帧要做——四份封面图像分别绘制（`_QuadrantTile` ×4）→ `ColorFiltered`（5×4 矩阵）→ 64-sigma `BackdropFilter` 全屏模糊。这些全部落在转场最需要流畅的头几帧上，跟用户猜测的方向一致。

同时验证了一处**不是**问题的猜测：怀疑窄屏 `PageView`（封面/歌词两页）会预先构建歌词页触发 `lyricsProvider` 网络请求。读 Flutter SDK `page_view.dart` 源码确认：`allowImplicitScrolling` 默认 `false` 时 `scrollCacheExtent` 为 0（`ScrollCacheExtent.viewport(0.0)`），非当前页不会被实际构建。这条路径原本就是安全的，不需要处理。

### 修法

- `LyricsBackground` 新增 `useFluidBackground`（默认 `true`）。为 `false` 时走新增的 `_CheapBackdrop`——用已缓存的封面强调色画一个双色线性渐变，零图像合成、零滤镜、零 Ticker。两个分支共享同一段 `artworkOverlaySkin` 计算并套用同一个 `SkinScope`，切换时前景色（播放键强调色等）不会跳变。`KaraokeScreen`（`LyricsBackground` 的另一个调用点）不传这个参数，维持默认 `true`，不受影响。
- `FullPlayerScreen` 新增的 `transition` 参数携带路由 `animation`，`_FullPlayerScreenState` 单向锁存 `_backdropSettled`：进场动画一旦报告 `AnimationStatus.completed` 就永久置真，之后即使发生下滑关闭又回弹，也不会再翻回假——已经付过一次的建立成本没必要在每次关闭路径上重付。
- **取色提前**：`coverPaletteProvider` 是 `FutureProvider.autoDispose.family`，此前只有桌面 shell 的 `_LayoutAccentGradient`（v5.31.0 新增，仅 ≥1200dp 存在）持续订阅它；窄于 1200dp 的布局下没有任何常驻订阅者，每次打开播放页都要现跑一次 `PaletteGenerator.fromImageProvider`。`MiniPlayerBar`（所有平台、只要有东西在播放就常驻）现在也订阅同一个 provider（只为预热缓存，不使用取值结果），保证不论窗口多宽，播放页一打开就能命中缓存。
- **验证到但决定不处理的次要贡献者**：`GlassPanel` 自己的 `BackdropFilter`（sigma 18，只处理一张图，比 `CoverFluidBackground` 的 64-sigma/四图轻得多）也会在首帧参与合成。推迟它意味着控制面板在滑入过程中完全没有毛玻璃质感——这比"稍重一点的定格帧"更容易读成"看起来是坏的"，权衡后本批只处理 `CoverFluidBackground`。

### 验证修复生效

`test/full_player_transition_test.dart`：用一个短 `transitionDuration`（100ms）的 `PageRouteBuilder`，`transitionsBuilder` 直接指向生产用的 `playerPageTransitionsBuilder`，断言：

1. 推入路由、pump 一帧（转场刚开始）→ 树里没有 `CoverFluidBackground`。
2. 再 pump 过 `transitionDuration`→ 树里有 `CoverFluidBackground`。

不用 `pumpAndSettle()`——`CoverFluidBackground` 一旦挂载就会起两个 60s/150s 的 `repeat()` controller，永远不会 `AnimationStatus.completed`，`pumpAndSettle` 会挂起。

## C. 进度条 hover 收缩（真 bug）

### 根因（比最初定位的范围略大）

`GlowingSliderThumbShape.getPreferredSize` 此前直接 `return Size.fromRadius(enabledThumbRadius)`，而 `enabledThumbRadius` 在桌面播放条宽形态（`_MiniPlayerSeekRow`）里 hover 时从 0 跳到 7。Flutter `BaseSliderTrackShape.getPreferredRect`（`slider_parts.dart`）按 `math.max(thumbWidth, overlayWidth)` 在轨道两端各留白——留白量跟着 hover 状态跳变，正是轨道跟着"收缩"的根因。

核对同一处代码时，另外发现紧邻的 `RoundSliderOverlayShape(overlayRadius: active ? 16 : 0)` 是**第二个**同类来源：这是 Flutter SDK 自带的形状（`slider_value_indicator_shape.dart`），它的 `getPreferredSize` 同样无条件返回 `Size.fromRadius(overlayRadius)`，跟着 `active` 切换 0/16 会喂给同一个 `max(thumbWidth, overlayWidth)` 项。这是用户给的定位之外调研时补充确认的一处，一并修。

### 修法

- `GlowingSliderThumbShape` 拆成 `radius`（当帧实际画的半径，随 hover 变）与 `maxRadius`（`getPreferredSize` 恒定返回，构造后不再变化）两个字段。两个调用点：`full_player_screen.dart:588`（原来 `enabledThumbRadius: 6` 恒定不变，改成 `radius: 6, maxRadius: 6`，本来就没有 hover 收缩的问题，只是跟着改签名）、`mini_player_bar.dart` 的 `_MiniPlayerSeekRow`（`radius: active ? 7 : 0, maxRadius: 7`，真正修复的地方）。
- `RoundSliderOverlayShape` 是 SDK 类改不了源码，做法是**恒定传 16**，不再跟着 `active` 切 0/16——画出来的实际大小交给 Flutter 自己内建的 hover/press 激活动画（`paint()` 内部对 `overlayRadius` 按 `activationAnimation` 做 tween，不依赖这个字段本身的取值随时间变化）。

### 测试

- 新文件 `test/seek_bar_effects_test.dart`：直接单测 `GlowingSliderThumbShape.getPreferredSize`，证明返回值只取决于 `maxRadius`、与 `radius` 无关；覆盖播放页恒定半径与播放条 hover 半径两种构造方式。
- `test/mini_player_bar_desktop_test.dart` 新增集成测试：读取 hover 前、hover 后**真实生效**的 `SliderThemeData`（`SliderTheme.of`），调用同一个 `trackShape.getPreferredRect`（框架布局时调用的那个方法），断言两次算出的轨道宽度完全相同——这比单测 `getPreferredSize` 更接近"用户看到的轨道到底会不会缩"，也会连带覆盖 `overlayRadius` 那部分。

## D. 进度条比例失调

现状：桌面播放条约 1200px 宽，进度条却贴着 `_transportBlockWidth`（248，按 5 个传输图标的紧凑排布反推）来，两侧大片空白。

### 修法

新增两个纯函数（`mini_player_bar.dart`）：

- `miniPlayerMiddleColumnWidth(rowWidth)`：中段列宽 = 该行实测可用宽度（不是窗口宽度）的 0.46，钳 `[290, 640]`。290 这个下限比 248 留了余量，保证传输键组居中嵌进去后两侧还有空隙；`_wideBreakpoint`（640，宽形态出现的最窄场景）代入公式已经有 294，比传输键组的 248 宽；1400px 桌面窗口代入约 644，被 640 上限拦住，避免中段吃光整行、不给曲目信息/操作区留活路。
- `miniPlayerSeekRowWidth(middleColumnWidth)`：进度条宽 = 中段列宽的 0.7，钳 `[220, 460]`。取用户给的 55%–75% 区间偏宽端，因为进度条自身内容（两个定宽时间标签 + 间距）已经吃掉一截固定宽度，实际轨道比这个比例数字直观看起来要窄。
- 传输键组维持自己原有的紧凑宽度（`_transportBlockWidth` 不变），`Center` 居中嵌进新的更宽中段列——只有进度条本身变宽，五个图标不会被拉开间距。

### 时间标签定宽

`_timeLabelWidth`：用 `TextPainter` 量出**当前曲目总时长**格式化后的文本宽度（而非已播时间自己的文本）——已播时间任何时刻都不会比总时长需要更多位数，用总时长的宽度做两个标签共享的固定槽位，足够覆盖已播时间从任何位数跳到任何位数的情况。已播标签右对齐、总时长标签左对齐，让数字始终贴着轨道那一侧，多余空间留在远离轨道的一侧。v5.30.6 的 `FontFeature.tabularFigures()` 只解决"同位数redraw 抖动"（如 `9:58→9:59`），这次解决的是"位数本身变化"（`9:59→10:00`）会偷走轨道宽度的问题，两者互补不重叠。

### 测试

- `miniPlayerMiddleColumnWidth`/`miniPlayerSeekRowWidth` 各 3 例（中段取值、下限夹取、上限夹取），跟 `full_player_screen.dart` 的 `playerArtworkSize`/`playerControlWidth` 走同一套"抽纯函数 + 直接单测"的既有约定。
- 集成测试：同一曲目（时长 15 分钟，覆盖两位数分钟）内，`position` 从 `9:59` 推到 `10:00`，两次测出的 `Slider` 渲染宽度断言相等。

## E. 封面 hover 放大

仿 EchoMusic `PlayerBar.vue` 的 `group-hover:scale-110`（`transition-transform duration-500`）。新增 `_HoverScaleCover`（`mini_player_bar.dart`），`MouseRegion` + `AnimatedScale` 包住既有的 `MiniPlayerArtwork` + 点击手势：

- 放大倍数 1.08——用户给的 1.06–1.10 区间偏轻端，因为本仓库播放条里的封面（56px）比 EchoMusic 参考实现更小、更贴近标题/艺术家文字，同样的绝对放大量在这个尺度下视觉占比更明显，选区间轻端避免跟旁边文字视觉打架。
- 动画时长 200ms，不跟 EchoMusic 原版的 500ms——那个时长是为点按驱动的过渡设计的，hover 反馈套用会显得迟钝，200ms 足够读出"有意的过渡"而不snap。
- 承接 v5.30.7 已确定的"只有封面能展开播放页"手势范围（`MouseRegion` + `GestureDetector` 包法沿用），本次只补视觉提示，不改交互范围。

测试：`mini_player_bar_test.dart` 新增一例，鼠标移入封面前后分别读 `AnimatedScale.scale`，断言中间态落在 [1.06, 1.10]、移出后回到 1.0。

## 调研中发现的两个测试基础设施陷阱

写测试过程中踩到、供以后参考：

1. **Flutter 测试默认视口只有 800×600（逻辑像素）**。`SizedBox(width: 900)` 之类的请求会被父级约束（`BoxConstraints.tighten` 遇到更小的 incoming maxWidth 时钳到那个值）静默钳制到 800，而不是报错。`mini_player_bar_desktop_test.dart` 里既有的 `_appAtWidth(900)`/`_appAtWidth(964)` 长期活在这个被钳制的隐含值下仍然通过（差值不够大，两边断言都恰好成立），本批新增/调整的宽形态阈值测试改用显式 `tester.view.devicePixelRatio = 1.0; tester.view.physicalSize = Size(...)` 设定真实视口，不再依赖这个此前无人察觉的钳制。
2. **从裸测试代码（不是 widget 的 `build()`/事件回调）里调用 `AnimationController.animateTo()`，紧接着就用 `pump(duration)` 推进模拟时钟，第一次推进会部分耗在 Ticker 自身的基准校准时刻上，而不是全部用于动画本身**——实测一个从 0.6 动画到 0.0、标称 320ms 的 `animateTo` 调用，若中间不插一次空 `pump()`，需要推进到约 500ms 模拟时间才会真正 `AnimationStatus.completed`。修法是调用 `animateTo()` 后先过一遍空 `pump()`（零时长）校准 Ticker 基准，再开始推进真实时长，且预留比标称值宽松的时间预算（本批用 2 倍），而不是卡着标称值算。`test/player_transition_test.dart` 的 `_settleAfterRelease` helper 落地了这个模式。
