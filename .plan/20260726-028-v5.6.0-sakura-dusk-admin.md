# v5.6.0 — 樱花薄暮浅色主题（Admin 后台对齐）

日期：2026-07-28
状态：completed

## 背景

v5.5.0 已在 Web 端确立「樱花薄暮」浅色 ACG 色板，并把权威 token 落到
`packages/ui/src/styles/sakura-dusk.css`。`services/admin/app/globals.css` 目前仍是
旧 Neon Shrine 深色主题（电紫 `#9b5cff` + 近黑 `#070711`），且它与 web 端的 globals.css
是**复制粘贴关系**而非 import 共享包。本阶段把 admin 端对齐到同一色板。

## 关键差异：后台需要降饱和

Admin 是长时间阅读的数据管理界面，不能照搬 Web 播放器的氛围感：

- 樱粉**仅**用于主操作按钮与导航选中态；数据表格、表单、筛选器保持中性
  （用 `--color-text` / `--color-border-strong` 构建层次，不铺粉底）
- **不引入** `PetalDrift` 花瓣与 `.aurora-veil` 氛围渐变——管理界面需要安静的背景
- 保留 `.card-soft` 柔和阴影，但表格行不用 hover 缩放（数据密度高，缩放会造成视觉抖动）
- 画布仍用 `--color-void` 奶油白，避免纯白长时间阅读的刺眼感

## 实现范围

1. **`services/admin/app/globals.css`** —— 移植 v5.5.0 的完整 `@theme` block
   （token 值与 `packages/ui/src/styles/sakura-dusk.css` 保持一字不差）；
   `color-scheme: light`；保留 admin 端已有的向后兼容别名。
   注意：**必须先审计 admin 端引用了哪些 token**，web 端有的别名 admin 未必有，
   反之亦然——v5.5.0 就是在这里发现了 `--color-primary-foreground` 从未定义的缺陷。

2. **`packages/ui/src/components/*`** —— `Badge` / `LifecyclePill` /
   `StorageHealthBadge` / `EmptyState` / `Skeleton` 逐个检查浅色适配。
   这些组件同时被 admin 消费（`services/admin/components/admin/StorageHealthBadge.tsx`
   直接 re-export），改动会影响两端。
   `NeonCard` 的 glow 已在 v5.5.0 改为 CSS 变量，无需再动。

3. **审计既有缺陷** —— 按 v5.5.0 的经验重点排查：
   - `grep -rn "bg-opacity\|text-opacity\|ring-opacity"` —— Tailwind v4 下已失效，
     web 端有 3 处导致提示文字近乎不可读
   - `grep -rnE "bg-(black|white)|text-white|bg-(gray|slate|green|red)-[0-9]"` ——
     绕过主题的硬编码色
   - `grep -rn "var(--color-"` 提取全部引用，与 `@theme` 定义做差集，找未定义 token

4. **`services/admin/app/layout.tsx`** —— `themeColor` 与 `statusBarStyle` 同步浅色。

## 验证

- `npm --prefix services/admin run type-check` → 0 errors
- `npm --prefix services/admin run lint` → 0 errors（注意排除 `playwright-report/`
  等构建产物目录，它们含压缩 JS 会触发大量误报）
- `npm --prefix services/admin run test:e2e` → 全绿
- Chrome DevTools MCP 实机走查 + **注入对比度脚本逐页扫描实时 DOM**。
  这是 v5.5.0 唯一发现「樱粉字压樱粉底 4.2:1」的手段，离线色板计算会漏掉组合态，
  admin 端表格/徽章的配色组合更多，此步不可省略。
- 数据密集页面（媒体对象列表、存储后端、用户管理）需在 1440px 下确认长时间阅读舒适度。

## 非目标

- 不重构 admin/web globals.css 的复制粘贴关系（牵动两个 Dockerfile 的 symlink 处理）
- 不改 admin 端业务逻辑与 API 调用
