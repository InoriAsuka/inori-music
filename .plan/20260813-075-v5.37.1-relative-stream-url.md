# v5.37.1 — `-1002 unsupported URL`：服务端给的是相对路径，客户端原样交给了 AVPlayer

v5.37.0 之后用户实测反馈两点：

> 1. 第一次登录弹出授权窗口，需要允许授权，这个在 macOS 应该属于正常，但是登录操作没等登录授权，自己先失败了，然后点击系统弹窗"允许"后，再登录，就登录成功了。
> 2. 登录成功后，进入主页，封面没有显示，播放也无法播放，提示 "unsupported url"。

**登录已通，v5.37.0 的 keychain 诊断被实机证实**——那个授权弹窗正是旧版文件式 keychain 的标志行为，说明代码确实切到了新路径。

## 主缺陷：`streamUrl` 是相对路径

对生产实例实测 `/api/v1/catalog/tracks/{id}/playback`：

```json
{
  "trackId": "4977b05d33167cff",
  "mimeType": "audio/flac",
  "backendType": "local",
  "streamUrl": "/api/v1/catalog/tracks/4977b05d33167cff/stream?exp=1786592689&sig=DeALC--dO9le1LdAYCMSH1GAdRp4lwGCkQk019L6WOM"
}
```

**没有 scheme，没有 host。** 这对 Web 端是正确的——同源，浏览器自己补全；对原生播放器则完全不可用。

`player_notifier.dart` 的 `resolvePlaybackUrl` 拿到它之后原样返回，注释写的是「streamUrl already carries HMAC signature from the server — **use as-is**」。签名那半句是对的（`exp`+`sig` 意味着不需要 Authorization header，这很重要，因为引擎确实一个 header 都不带）；**「use as-is」是错的：签过名不等于可寻址。**

`Uri.parse('/api/v1/…')` 得到一个相对 URI，`ProgressiveAudioSource` 交给 AVPlayer，返回 `NSURLErrorUnsupportedURL (-1002)`。

**加重情节**：这个分支排在**会拼 base 的兜底分支之前**，所以那段正确的拼接代码永远不可能被执行到。

修复：新增顶层纯函数 `absolutePlaybackUrl(url, base) => Uri.parse(base).resolve(url).toString()`，`presignedUrl` 与 `streamUrl` 两条分支都过它。`Uri.resolve` 同时覆盖两种形状——对象存储返回的 presigned URL 本就是绝对的（常在完全不同的主机上），原样透传不会被改写。所有播放入口（`playTrack` / `_buildConcatQueue` / `enqueue` / `enqueueNext`）都经由 `resolvePlaybackUrl`，改一处全覆盖。

顺带修掉兜底分支上的另一句假注释：「Fallback: construct stream URL; **Flutter sends Authorization: Bearer <token>**」——不发。`ProgressiveAudioSource(Uri.parse(u))` 不带任何 header，这条兜底真被走到只会拿 401。改成如实说明它会失败以及为什么。

## 封面：不是客户端问题

对全部 5 张专辑逐个查 `/api/v1/catalog/albums/{id}/artwork`，**无一例外返回 `{"error":{"code":"no_artwork","message":"no artwork"}}`**。

服务端库里根本没有封面数据。客户端 `artwork_provider.dart` 正确地把 404/错误处理成 `null`，`TrackArtwork` 正确地退回音符占位图——**行为完全正确，只是没有东西可显示**。

FLAC 文件本身元数据齐全（stream 端点的前几百字节里能直接读到完整 Vorbis comment：album / ALBUMARTIST / artist / composer / ISRC / UPC…），说明**入库时没有提取内嵌封面**。这是媒体摄取的缺口，按路线图属于 **v6**，不在本次范围。

## 授权弹窗：不做自动重试

v5.37.0 把 macOS 切到旧版文件式 keychain 后，OS 开始就 keychain 访问弹窗授权。而本应用是 **ad-hoc 签名，每次构建的代码签名都不同**——所以这个弹窗**每装一个新版本都会再出现一次**，不只是首次安装。触发它的写入正好在 `login()` 里，于是「安装新版后的第一次登录」必然输给这个弹窗。

**没有实现自动重试**：那需要猜「用户多久会点允许」，而本机无完整 Xcode、无法复现验证，猜出来的等待时长既可能不够也可能白白卡住 UI。

改为把报错变成可执行指令：识别 macOS keychain 的授权类 OSStatus（`-25293` errSecAuthFailed / `-25308` errSecInteractionNotAllowed / `-25315` errSecInteractionRequired / `-128` errSecUserCanceled），给出「点击系统弹窗的『允许』，然后再按一次登录」。表单内容不会被清空，重试就是一次点击。

## 守卫测试

`test/playback_url_test.dart`（6 条）：相对路径补全主机、**签名必须存活**（引擎不带 header，`exp`+`sig` 是唯一凭证，修主机时把 query 丢了就会把 -1002 换成 401、看起来像另一个 bug）、绝对 presigned URL 原样透传、带端口的 base、base 末尾斜杠不重复、结果恒有 scheme 与 host。

`test/login_failure_visibility_test.dart` 加一条：授权类 OSStatus 必须产出含「Allow」「Sign In again」的指令式文案。

### 非空洞证明

把 `absolutePlaybackUrl` 退回恒等函数（即修复前的 use-as-is 行为），实测精确失败，`Actual` 打印出的正是 AVPlayer 拒绝的那个字符串：

```
Expected: 'http://10.100.121.134/api/v1/catalog/tracks/…/stream?exp=…&sig=…'
  Actual: '/api/v1/catalog/tracks/…/stream?exp=…&sig=…'
```
