# Phase v5.12.4 — GitHub Release 附带 Flutter 构建产物

**版本**: v5.12.4
**状态**: done（workflow 静态校验完成；远端实际运行结果待本次 tag 推送后确认）
**方向**: CI/CD 基础设施

## 背景

用户在验证 v5.12.x 期间反馈：每次都要用 `gh run download` 从 workflow 运行记录下载构建产物太麻烦，应该像既有的 Go server 二进制一样直接发布到 GitHub Release（`release.yml` 在 `v*.*.*` tag 推送时已经会创建 Release，此前只挂了 Go 二进制）。

## 目标

推送版本 tag 后，GitHub Release 除了 5 个平台的 Go 二进制外，同时附带 Android APK、macOS 应用、Windows 应用（均已打包成可直接分发的单文件）。

## 任务清单

- [x] `.github/workflows/release.yml` 新增 `build-flutter-apk` job：构建 release APK，重命名为 `inori-music-<tag>.apk`
- [x] 新增 `build-flutter-macos` job：`flutter build macos` 后用 `ditto -c -k --sequesterRsrc --keepParent` 打包 `.app` 为 zip
- [x] 新增 `build-flutter-windows` job：`flutter build windows` 后用 PowerShell `Compress-Archive` 打包 Release 目录为 zip
- [x] `publish` job 的 `needs` 加上三个新 job，复用既有的 `download-artifact merge-multiple` + `softprops/action-gh-release` 逻辑，不改 publish 本身
- [x] 刻意排除 IPA（未签名，不具备直接分发给普通用户的可用性）

## 非目标

- 不改动现有 Go 二进制发布逻辑
- 不给 IPA 做签名/分发（超出本次范围）

## 验证记录

`actionlint` 对修改后的 `release.yml` 及全部 workflow 文件通过（无新增问题，pre-existing 的 `build.yml` shellcheck 提示与本次改动无关）；YAML 语法另用 Ruby `YAML.load_file` 复核。工作流本身此前从未在任何 tag 推送上跑过 Flutter 构建 job，新增 job 是否真的在远端跑通、Release 页面产物是否正确挂载，待本次推送打 tag 后现场确认。
