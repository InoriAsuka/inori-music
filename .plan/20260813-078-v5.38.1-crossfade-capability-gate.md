# v5.38.1 — 切歌淡入淡出滑块补能力位门控（v5.38.0 遗留 gap，如实报告后的后续修复）

v5.38.0 接入第二个 `PlaybackEngine` 实现（`MediaKitEngine`，Windows 专用）时，逐一核对了接口在两个引擎下的真实语义，其中一条明确写进了"已知但本次不修"：`MediaKitEngine` 诚实报 `capabilities.crossfade: false`，`crossfadeSeconds` setter 是文档化的空操作——但 `settings_screen.dart` 的"切歌淡入淡出"滑块本身从 v5.27.0 引入至今，从来没有读过 `playbackCapabilitiesProvider`。

本次任务只做一件事：把这个记录在案的 gap 补上。范围刻意收得很窄，不顺带碰其他任何东西。

## 缺陷

`settings_screen.dart` 的 `// Crossfade slider` 这个 `Consumer`（约 289–314 行）：

```dart
Consumer(
  builder: (context, ref, _) {
    final seconds = ref.watch(crossfadeProvider);
    return ListTile(
      leading: const Icon(Icons.swap_horiz),
      title: const Text('切歌淡入淡出'),
      subtitle: Column(children: [
        Text(seconds == 0 ? '关闭' : '$seconds 秒'),
        Slider(value: seconds.toDouble(), ..., onChanged: (v) => ...),
      ]),
    );
  },
),
```

无条件渲染。对比同一个文件里的 `_EqSection`（`settings_screen.dart:1034`）——均衡器区块严格按 `playbackCapabilitiesProvider.equalizer` 门控，不支持时换成禁用态说明 tile；crossfade 滑块从引入起就没有这道检查。四个版本以来（v5.27.0–v5.37.2）只有 `JustAudioEngine` 一个实现在跑，且它支持 crossfade，这个 gap 完全没有暴露的机会。v5.38.0 把 `MediaKitEngine` 接上后，Windows 用户会看到一个能拖动、数字会变、看起来一切正常的滑块——底层的 `crossfadeSeconds` setter 什么也不做。

这是本仓库反复出现的头号缺陷形态（`silent-failure-pattern`：界面零反馈的失败）的一次新鲜实例，而且是上一个版本亲手引入的。

## 修复：照抄 `_EqSection` 已经定好的门控形状

不是发明新模式，是把均衡器区块已经决定好的答案原样搬过来。在滑块的 `Consumer.builder` 顶部加一道早返回：

```dart
if (!ref.watch(playbackCapabilitiesProvider).crossfade) {
  return const ListTile(
    leading: Icon(Icons.swap_horiz),
    title: Text('切歌淡入淡出'),
    subtitle: Text('当前播放引擎不提供切歌淡入淡出'),
    trailing: Icon(Icons.lock_outline),
    enabled: false,
  );
}
```

禁用态保留原图标（`Icons.swap_horiz`）、原标题，换成中文说明文案，加 `Icons.lock_outline` 尾部图标，`enabled: false`——与均衡器禁用态同一套视觉语言。刻意不做的是"直接隐藏这个 tile"：一个无声消失的控件只比说谎的控件好一点点，用户完全不知道这个功能存在过、也不知道为什么消失了；均衡器区块已经替这个问题定过调，这次跟它保持一致而不是另开一套。

`playbackCapabilitiesProvider` 已经是这个文件的既有 import（`playback_engine_provider.dart`），不需要新增依赖。

## 守卫测试及证伪

`test/settings_screen_test.dart` 原有 `_buildApp` 测试夹具固定用 `FakePlaybackEngine()`（默认 `PlaybackCapabilities.none`）。新增 `capabilities` 参数透传给 `FakePlaybackEngine`，与均衡器测试同一条已建立的路子，不新起一套夹具：

```dart
Widget _buildApp(
  AuthNotifier Function() authNotifier, {
  Widget? shellChrome,
  PlaybackCapabilities capabilities = PlaybackCapabilities.none,
}) => ProviderScope(
  overrides: [
    authProvider.overrideWith(authNotifier),
    playbackEngineProvider.overrideWithValue(
      FakePlaybackEngine(capabilities: capabilities),
    ),
  ],
  ...
);
```

新增两条测试（`Crossfade slider capability gate (v5.38.1)` 组）：

1. `crossfade: false` → 断言禁用态 tile 的标题、说明文案、`Icons.lock_outline` 都在场，且 `ListTile.enabled == false`；同时断言树上 `find.byType(Slider)` 结果为空——不只是"看到了说明文字"，还要"真的没有一个能拖的控件藏在别处"。
2. `crossfade: true` → 断言可拖动的 `Slider` 仍正常渲染，说明文案不在场。这条防的是另一个方向的回归：门控写错了方向，把 just_audio 路径（Windows 之外的所有平台）也一起锁死。

实现过程中发现一个与本次修复无关但会让测试假失败的细节：crossfade 滑块所在的"音频"区块排在 Account / Appearance / Offline Library / 歌词几个区块之后，而设置页的根容器是 `ListView`——Flutter 的 sliver 机制只会构建视口 + cache extent 范围内的子项，直接 `find.text('切歌淡入淡出')` 在默认测试视口下找不到东西（不是断言错，是控件还没被构建）。两条新测试都先 `tester.scrollUntilVisible(find.text('切歌淡入淡出'), 300)` 滚动到位，再做后续断言。

**证伪（按要求执行，非形式主义）**：临时把门控代码退回 v5.38.0 的原样（删掉 `if` 分支，`Consumer` 直接从 `final seconds = ref.watch(crossfadeProvider);` 开始），重新运行这两条新测试：

- `crossfade: false` 用例**精确失败**：
  ```
  Expected: exactly one matching candidate
    Actual: _TextWidgetFinder:<Found 0 widgets with text "当前播放引擎不提供切歌淡入淡出": []>
  ```
- `crossfade: true` 用例**依然通过**——退回后两种能力状态都无条件渲染滑块，这条测试单独并不能抓出门控缺失，必须两条搭配才是完整证据链，这也是任务本身要求两条都写的原因。

确认失败信息准确指向"门控消失"而非环境噪音后，恢复修复代码，`diff` 确认与证伪前的版本逐字节相同，重新跑绿。

## 记录但不修：播放速度控件同样没有能力位门控，但目前还不是活跃缺陷

排查过程中一并确认"播放速度"控件——`settings_screen.dart` 约 239 行的入口 tile（点击弹出速度选择 bottom sheet）与约 395 行 `_showSpeedSheet` 内的选择列表、以及 `full_player_screen.dart` 约 1046 行同一个 bottom sheet 的另一处入口——同样从未读过 `playbackCapabilitiesProvider`，形状和 crossfade 滑块的原始缺陷完全一样。

但 `PlaybackCapabilities.speedControl` 在两个现存引擎上都是 `true`：

- `just_audio_engine.dart:71` — `speedControl: true`
- `media_kit_engine.dart:16` — `speedControl: true`

今天没有任何引擎会走到"不支持"分支，所以这不是一个活跃缺陷，只是一个潜伏的同类 gap。触发条件写清楚：**第一个报告 `speedControl: false` 的引擎出现时**，播放速度控件会变成和这次修的 crossfade 一模一样的静默失败，到时候需要照本次同一个模式补门控（入口 tile 换禁用态说明、bottom sheet 整体不弹出或同样给出禁用态提示）。

这次不加门控：没有引擎能产生 `speedControl: false` 分支，加了就是一段没有任何测试能真正验证到 false 路径的死代码——`media_kit_engine_capabilities_test.dart`/`just_audio` 侧都无法构造出一个"支持播放但不支持调速"的真实引擎实例来跑绿这条假设中的禁用态分支。等第三个引擎真的报出 `speedControl: false` 那天再补,不是现在猜。
